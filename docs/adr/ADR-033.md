# ADR-033: Structure / Raw Regime implementation-language allocation — Python analytical core

**Context:** [ADR-008](./ADR-008.md) (Approved, 2026-07-18) allocates implementation language by **layer/capability nature**, not by module name: Python for Feature Engineering, Strategy, Decision logic, Backtest Engine (I-2 Decision-Parity ergonomics + numerical/analytical ecosystem); Go for Market Data Ingestion, Risk Gateway, Execution Engine (concurrency/I-O/reliability at the edge); Rust reserved for a future measured sub-ms latency need. `structure-engine` and `raw-regime-engine` are named nowhere in ADR-008's decision text — they did not exist as registered `module_id`s at ADR-008's boundary (2026-07-18); both were registered later, at Package 1.1 (`module-registry.yaml`, verified current state: `module_type: compute_engine`, `depends_on: [market-data-ingestion]`, `structure-engine.forbidden_dependencies: []`, `raw-regime-engine.forbidden_dependencies: [structure-engine]`, neither carries a Product-Owner-approved `quality_tier`).

[`docs/architecture/engine/structure-regime-architecture.md`](../architecture/engine/structure-regime-architecture.md) (Package 1.3-A, v0.4, `status: Draft`, `Consolidated Stable` package lifecycle for its four-module architecture baseline only) elaborates responsibility/data-flow/event-contract boundary for exactly these two modules and explicitly disclaims language selection as out of its own scope: **"§14. Explicit non-goals" states verbatim "KHÔNG chọn programming language/framework."** This ADR is the governed decision Package 1.3-A itself identifies as still open.

[ADR-032](./ADR-032.md) (Approved, v0.2) already establishes, as controlling precedent for exactly this kind of language-allocation decision, the operative framing: it names *"the Decision Pipeline's Research/Production dual-execution surface (Structure/Regime/Feature/Strategy/Decision/Backtest)"* as the surface where ADR-008's I-2-driven Python rationale applies, and explicitly rules Go correct for `market-reference-service` precisely *because* that module is **not** part of that surface. `structure-engine` and `raw-regime-engine` are named in ADR-032's own list as members of that surface — ADR-032 states this as descriptive framing, not as itself deciding Structure/Regime's language (it decides only `market-reference-service`'s).

Independently, [Chapter 13 §13.4](../constitution/13-quality-gates.md)'s illustrative Tier table lists **"Tier 1 — Core Logic | Strategy Engine, Feature Engine, Structure Engine, Regime Engine"**, requiring a mandatory **Parity Test ("Replay khớp Live tại tầng Decision") explicitly cross-referencing I-2** for that tier — the same parity mechanism ADR-008 cites as Python's rationale for Feature/Strategy/Decision/Backtest. The [reference pipeline](../architecture/README.md) (draft, not itself an architecture decision) places `Structure Engine`/`Raw Regime Engine` immediately upstream of `Feature Engine -> Context Projection -> Strategy -> Decision`, consuming the same canonical Candle facts and feeding the same downstream parity-relevant chain.

I-2's own **declared `Scope:`** field ([Chapter 2](../constitution/02-platform-invariants.md)) reads narrowly — "Decision pipeline; cả 4 execution mode" — and this ADR does **not** claim that field itself names Structure/Regime (widening a Locked invariant's own declared Scope is not this ADR's authority, [Chapter 13 §13.5](../constitution/13-quality-gates.md)). The decision below rests instead on the **capability-nature analysis ADR-008 itself uses** (deterministic analytical transformation requiring one authoritative implementation reused unmodified across Replay/Backtest/Paper/Live — [Chapter 3 §3.1](../constitution/03-engineering-principles.md), "One Authoritative Implementation per Business Capability," a general principle not limited to Strategy/Decision), reinforced by ADR-032's explicit framing and Chapter 13's own Tier-1/Parity-Test cross-reference for these exact two modules — not on a reinterpretation of I-2's Scope field.

This decision satisfies [Chapter 0 §4b](../constitution/00-governance.md) ADR Scope Rule under, at minimum, the **">1 module"** trigger: one shared language-allocation reasoning resolves both `structure-engine` and `raw-regime-engine` simultaneously (both are `compute_engine` analytical-inference modules with the same capability nature — deterministic transformation over canonical Candle facts, no external side effect, required Research/Production code-path reuse — evaluated together for exactly this reason, without merging their independent authority). It is also, independently, **"khó đảo ngược" (hard-to-reverse)**: once either engine's algorithm/test suite/tooling is authored in a language, changing it later means re-authoring the analytical core and its full parity/regression evidence from scratch, not a mechanical port. **ADR Scope Rule result: `ADR_REQUIRED`.**

**Decision:**

```text
structure-engine:    Python
raw-regime-engine:   Python
```

**Rationale — applying ADR-008's actual capability-nature test, not module-name similarity:**

*Structure Engine* — deterministic analytical transformation of canonical Candle facts into Swing/BOS/CHoCH structure facts (`structure.md`, `swing.md`, verified `consumes: [candle-closed, candle-corrected]` — grep-confirmed in `docs/domain/structure.md`); zero external venue/network/credential side effect (`module-registry.yaml`: `security_classification: none`); the same analytical algorithm must produce the same output whether invoked from Replay, Backtest, Paper, or Live orchestration — Go's ADR-008 rationale (many-simultaneous-WS-connection concurrency, I/O reliability at an external edge) does not describe this module's profile at all; rapid research iteration and the numerical/statistical ecosystem ADR-008 already cites for Feature/Strategy/Decision (Polars/Pandas/NumPy/TA-Lib-class tooling) are materially more relevant to pivot/break-detection research than to Go's strengths.

*Raw Regime Engine* — deterministic analytical classification (trending/ranging/volatile) over the same canonical Candle evidence (`regime.md`, verified `consumes: [candle-closed, candle-corrected]`); explicitly, permanently independent from Structure Engine (ADR-003/ADR-014, unchanged — see "Independence preservation" below); its own registered responsibility text requires it stay reusable by non-price-action strategies (arbitrage, market making) as well as price-action ones — a capability profile with the identical Research/Production parity requirement and identical absence of a direct external network/custody/execution boundary as Structure Engine.

Both facts support Python more strongly than Go under ADR-008's own test: neither module has Go's cited edge-concurrency/I-O profile, and both have the exact Research/Production single-code-path requirement ADR-008 already used to allocate Python to the rest of the analytical/decision chain.

**I-2 / parity consequence — explicit, binding on any future implementation — corrected v0.2 (closes `ADR033-A-MAJ-01`, Major, Review A): v0.1 overstated this rule in two ways — (1) it read as a blanket prohibition on any second implementation existing at all, and (2) it described the mitigation as "one authoritative implementation/service instance," conflating the authoritative-implementation concept with a runtime-instance-count limit. Neither matches Locked [Chapter 3 §3.1](../constitution/03-engineering-principles.md), which this correction now aligns with exactly:**

```text
For structure-engine and for raw-regime-engine, independently: exactly ONE
authoritative implementation/version is permitted to produce authoritative
output for all execution modes (Backtest, Replay, Paper, Live) under the
applicable governed state — per Chapter 3 §3.1's actual rule. A second,
independently-maintained Research/Production implementation MUST NOT
simultaneously act as competing authoritative logic for the same capability.

Chapter 3 §3.1 explicitly PERMITS alternative, experimental, shadow,
migration, or candidate-replacement implementations to exist CONCURRENTLY
with the authoritative one — this ADR does not prohibit them, and v0.1's
wording is corrected here to stop implying otherwise. Such implementations
remain non-authoritative and MUST NOT produce authoritative output until
they pass required parity validation and are promoted through the proper
governance process (Chapter 3 §3.1) — the same rule already governs Risk
Gateway under ADR-008, applied here to Structure/Raw Regime.

Chapter 3 §3.1 does NOT limit the number of runtime processes/instances/
replicas of the SAME authoritative implementation/version — multiple
replicas of one authoritative Python implementation, horizontally scaled or
run for HA, are explicitly compatible with this rule. This ADR creates NO
singleton-service-instance requirement; the canonical unit Chapter 3 §3.1
governs is implementation/version/semantics, not a count of runtime
instances. (v0.1's "one authoritative implementation/service instance"
phrasing is removed — it wrongly conflated these two distinct concepts.)

When execution modes are compared for parity, or the same run identity is
being reconstructed, implementation version + configuration + policy
version + canonical contract must be pinned consistently across the modes
being compared (Chapter 3 §3.1). Outside that comparison, independent
experiments/canaries (e.g. a candidate algorithm version tried in Backtest)
may use a different version/configuration, provided they do not claim parity
with the authoritative baseline while doing so and do not themselves produce
authoritative output.

The normal authoritative implementation selected by this ADR, for each
engine, remains Python — this correction does not weaken, reopen, or narrow
that decision. It only removes an over-broad prohibition v0.1 stated beyond
what Chapter 3 §3.1 actually requires, and makes explicit that no SECOND
AUTHORITATIVE implementation (Go or any other language) may compete with the
Python authoritative implementation for either engine without first passing
parity validation and governance promotion.

This is Chapter 3 §3.1 ("One Authoritative Implementation per Business
Capability") applied to these two capabilities, precisely as written —
reinforced by, not newly derived from a reinterpretation of, I-2's own
declared Scope.
```

**Alternatives considered:**

**Option A — Python for both structure-engine and raw-regime-engine (SELECTED).**
Strengths: strongest match to ADR-008's own capability-nature test (deterministic analytical/inference logic, not edge I/O); Research/Production same-code-path ergonomics for I-2-adjacent parity concerns (Chapter 13 §13.4's Tier-1/Parity-Test cross-reference to I-2 for exactly these modules); mature numerical/statistical ecosystem for regime/structure research; fast algorithm iteration; consistent analytical-language boundary with the Feature/Strategy/Decision/Backtest direction ADR-008 already set.
Risks: Python runtime performance/concurrency ceiling relative to Go/Rust; deterministic-numerical discipline is not automatic in Python (must be actively engineered, not assumed); accidental dependency on mutable/data-science-global state (common Python anti-pattern); cross-language runtime/serialization boundary with the Go Data Layer remains undecided until a future topology ADR.
Mitigations: deterministic pure/core engine boundaries enforced at design time (no implicit global mutable state); explicit version-pinned definitions (swing/structure/regime definition versions, mechanism deferred per above, but the *requirement* to pin is not deferred); immutable/cursor-bounded Candle inputs (Chapter 5 bitemporal discipline, already established for the Data Layer, must carry forward); profiling before optimization (no premature Rust move without measured evidence); Rust remains reserved and available via a new ADR if real sub-ms latency evidence later emerges, exactly as ADR-008 already provisioned.

**Option B — Go for both.**
Strengths (assessed fairly): same language as the current Data Layer (`market-data-ingestion`, and `market-reference-service`), which could simplify in-process integration *if* a future topology decision chose a shared-process/shared-binary deployment (not itself decided here); Go's concurrency/reliability/tooling maturity.
Weakness: ADR-008's Go rationale is explicitly "concurrency (nhiều WS connection đồng thời), I/O, độ tin cậy" at an external system edge — neither Structure Engine nor Raw Regime Engine has that profile (zero external venue/network side effect, verified `security_classification: none` for both in the registry). Rejected not because "Python is generically preferred" but because the specific capability-nature test ADR-008 itself established does not support Go for an internal deterministic analytical-inference capability with a Research/Production parity requirement.

**Option C — mixed languages (e.g. Structure Python, Regime Python-or-Go independently).**
Assessed: both engines share an identical capability-nature profile under ADR-008's test (deterministic Candle-fact transformation, no external I/O edge, Research/Production parity requirement, ADR-014-independent-but-parallel role in the pipeline) — there is no capability-nature difference between them substantial enough to justify a different language allocation. Splitting would only add cross-language tooling/CI/parity-validation complexity (two toolchains instead of one, for two modules that are otherwise architecturally symmetric) without a corresponding capability benefit. Rejected.

**Option D — Rust.**
ADR-008 explicitly reserves Rust for "critical path tương lai nếu latency profile thay đổi" — a future, separately-ADR'd decision, gated on a measured sub-ms requirement. No such measured requirement exists for Structure/Raw Regime at this boundary (current latency profile: vài trăm ms, non-HFT, unchanged from ADR-008's own current-scale finding). Selecting Rust now would be introducing it without the evidence ADR-008 itself requires. Rejected at this boundary; the re-evaluation path remains available through a new ADR if a real measured latency requirement emerges later.

**Consequences:**

- Structure Engine's and Raw Regime Engine's analytical business logic (Swing/BOS/CHoCH inference; volatility/directional-persistence/statistical regime classification) will be implemented in Python.
- Exactly one authoritative implementation/version may produce authoritative output for each engine independently, reused unmodified across Replay, Backtest, Paper, and Live (Chapter 3 §3.1, I-2-adjacent parity discipline). Chapter-3-permitted alternative/experimental/shadow/migration implementations may exist concurrently but remain non-authoritative until required parity validation and governance promotion complete; multiple runtime replicas of the one authoritative implementation are unrestricted. No second implementation — in Go or any other language — may act as competing authoritative logic for either engine without that promotion.
- The current Go Data Layer (`market-reference-service`, `market-data-ingestion`) is unchanged by this decision — no code, dependency, or authority touched.
- No language-driven dependency edge is added between Structure Engine and Raw Regime Engine, or between either engine and any other module; ADR-014's independence rule (Structure MUST NOT consume Regime, Regime MUST NOT consume Structure) is preserved exactly.
- Cross-language runtime/transport boundary between the future Python engines and the existing Go Data Layer remains an undecided, deferred topology question — to be resolved by its own future ADR if/when it meets Chapter 0 §4b, not silently assumed here.
- Future performance profiling is required before any reconsideration of Rust for either engine — no such reconsideration is triggered or implied by this decision.
- Any future Python implementation of either engine must preserve the deterministic decimal/time/order semantics already established as authoritative elsewhere in this repository (I-9's Scope does not itself extend to these modules, but the underlying discipline — no lossy float round-trip for values that feed financial computation, correct bitemporal/no-look-ahead handling per Chapter 5/I-3, deterministic ordering per ADR-009 — is a general engineering discipline these engines must uphold on their own merits, to be verified at their own future Quality Gate evaluation, not asserted as already satisfied by this ADR).
- This ADR's Product Owner approval (see "Product Owner decision" above) makes the Python/Python language allocation authoritative and removes the language-allocation blocker to the Structure Engine/Raw Regime Engine implementation tranche (Chapter 14 §14.2 order).
