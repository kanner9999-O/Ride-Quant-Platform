# ADR-035: Feature Computation Cursor — Durable, Bounded Evidence for Authoritative Feature Facts

**Context:** [ADR-034](./ADR-034.md) (Approved) authorizes `FeatureFactInvalidated.invalidation_cause: eligible_swing_selection_superseded`, but pins it fail-closed: the cause is semantically defined yet **operationally NOT EMITTABLE** until `R_original` — the computation cursor `R` under which the invalidated `FeatureComputed` originally evaluated [`feature.md`](../domain/feature.md) §9a's Eligible-Swing eligibility — can be proven from **durable, replay-reconstructable authoritative evidence**, surviving process restart and reconstructable identically by every execution mode (Live/Backtest/Paper Trading/Replay, §13). ADR-034 explicitly forbids substituting `FeatureComputed.recorded_time` or any process-local/in-memory tracking for `R_original`. No field or artifact in current authoritative Feature event schema durably records `R`. This is `P3-FEATURE-A-MAJ-06`'s architecture prerequisite.

**Ground-truth confirmation (direct code inspection, `swing_distance.py`, commit `07eb8ecf475cdb6ab6ef7ac6f63283520c99111a`):** the engine already takes an explicit `cursor` keyword argument on `on_candle`/`on_swing_confirmed`/`on_swing_invalidated` — but this alone does not satisfy the durability requirement. `FeatureComputed` (`contracts.py`) has no cursor field at all. Redelivery of an identical `EventRecordRef` on `on_candle` short-circuits to `return []` (dedup, feature.md §3 rule) before any as-of computation runs, so the same stored Candle cannot be re-evaluated under a different cursor through that path. `_SwingState` retains only the current revision, and `on_swing_invalidated` destructively sets `state.invalidated = True` in place — later-ingested Swing knowledge overwrites the exact state an earlier-cursor evaluation would need to reconstruct. The explicit `cursor` parameter is necessary but not sufficient: it changes *how eligibility is computed at call time*, not *what is durably provable afterward*.

**Scope classification — `ADR Required`.** Same Chapter 0 §4b "Event Schema" trigger as ADR-034, independently sufficient per the disjunctive reading ADR-034 established (citing [ADR-025](./ADR-025.md)). A durable cursor requires adding required payload structure to `FeatureComputed`/`FeatureFactInvalidated` — a schema change to authoritative Feature events, not a mechanism-only/implementation-detail choice. No existing higher-authority mechanism resolves this without an Event-Schema change: `recorded_time` is a distinct axis (append time, not evaluation-boundary time — [Chapter 5](../constitution/05-time-model.md) §5.1/§5.4, and the exact substitution ADR-034 already forbids); `input_fact_refs`/`causation_refs` record only facts that *were* selected, never the boundary that determined what was visible-but-rejected (the winning-later `SwingConfirmed` that triggers the new cause is, by construction, absent from the original fact's `input_fact_refs`); and no in-memory/process-local value can be durable by definition. This ADR does not relitigate ADR-034's own classification, and confirms — after direct inspection, not assumption — that no non-schema-changing option closes this specific gap.

**Decision:** Feature's authoritative `FeatureComputed` and `FeatureFactInvalidated` events (`feature.md` §3/§4) each carry one new **required** payload field, `computation_cursor` — a **Feature-Domain-Contract-owned, bounded evidence structure**, modeled on [Chapter 5](../constitution/05-time-model.md) §5.3's general Replay Cursor principle ("Recorded Time boundary + opaque ordering position") but **deliberately not** an instance of [Chapter 8](../constitution/08-event-model.md) §8.4/§8.5's `decision_context_cursor`/canonical `replay_cursor` schema — Chapter 8 is not touched, remains Locked and byte-identical.

```yaml
computation_cursor:
  type: object
  required: true
  properties:
    recorded_time: {type: timestamp, required: true}
    stream_positions:
      type: map                # <stream_id> -> <sequence>
      required: true
      description: >
        Bounded to EXACTLY the upstream stream(s) this feature_type's Feature
        Definition is authorized to consume (feature.md §14) — never open-ended,
        never a global cross-stream sequence (consistent with ADR-009's "no
        global total order").
```

**Why bounded, not Chapter 8's full `decision_context_cursor` schema:** Decision needs `input_contract_ref`/`stream_registry_version`/`lifecycle_frontier` because its upstream universe is declared by a *versioned, evolvable* Input Contract (Chapter 8 §8.3.4) spanning a multi-stream, cross-mode boundary that itself changes over time. Feature has no equivalent: `feature.md` §14 pins a small, fixed, closed upstream-contract enumeration directly in the Domain Contract, and `subject_ref.scope.feature_definition_version` already plays the exact disambiguating role `input_contract_ref` plays for Decision (an immutable Referenced Authoritative Artifact, §8.1.1). Feature never needs a Lifecycle Frontier because it does not reconstruct a Decision-style evolving stream *universe* — its universe is closed by its own Domain Contract, not by a separate versioned registry. Requiring the full Decision-grade vector would force premature commitment to Phase-1 infrastructure (`stream-registry.yaml`, Input Contract registry) that does not exist yet in this repository and that Feature's bounded 1–2-stream surface does not need.

**Where it applies and how `R_original`/`R_later` are recovered:**

- `computation_cursor` is required on **every** `FeatureComputed` — original and replacement alike (§3's "no shortcut" and correction-lineage invariants are unaffected; each computation event, original or replacement, pins the exact `R` under which *it* evaluated eligibility). `R_original` for an invalidated fact is read directly off that fact's own `computation_cursor` — no external state, no process memory.
- `computation_cursor` is required on **every** `FeatureFactInvalidated`, pinning the `R_later` under which the re-evaluation that produced *this* invalidation was performed — this is exactly the evidence ADR-034's conditions (a)/(b) need to prove a winning `SwingConfirmed` was invisible at `R_original` and visible at `R_later`.
- This makes `computation_cursor` universal across all three founding feature types (`feature.md` §12 already states recorded-time visibility, condition (a), applies to *every* Feature input, not only `distance_to_last_confirmed_swing`) — the field is not scoped narrowly to the one feature type ADR-034's new cause targets, since the underlying evaluation-boundary concept it records is already universal in the Domain Contract.

**Relationship to other time/ordering axes — no field is redefined, one relational invariant is added, directly modeled on [Chapter 8](../constitution/08-event-model.md) §8.5.2's existing Cursor↔Position pattern:**

```text
computation_cursor.recorded_time  ≠  envelope.recorded_time (append time, unaffected)
computation_cursor.recorded_time  ≠  effective_time / effective_window (§12, unaffected)
computation_cursor.recorded_time  ≠  any single upstream event's own recorded_time
                                      (the exact substitution ADR-034 already forbids)

New invariant (Cursor → Fact, mirrors Chapter 8 §8.5.2's "Cursor → Decision"):
  computation_cursor.recorded_time <= FeatureComputed.recorded_time
  computation_cursor.recorded_time <= FeatureFactInvalidated.recorded_time

New invariant (Position → Cursor, mirrors Chapter 8 §8.5.2's "Position → Cursor",
anti-look-ahead):
  every event referenced by stream_positions must have
  recorded_time <= computation_cursor.recorded_time — a cursor entry pointing to an
  event from the future relative to its own recorded_time boundary is invalid and
  must be rejected at append.

feature.md §9a step 2 / §12's existing eligibility test is restated using the durable
field, not a new rule:
  SwingConfirmed.recorded_time <= computation_cursor.recorded_time
```

**Implementation consequence (architecture requirement, not a mandated data structure):** an implementation satisfying this ADR must be able to reproduce, for any `computation_cursor` value appearing on a durable authoritative Feature event, the correct as-of eligibility answer for the upstream fact(s) that cursor governs — i.e. engine-internal upstream state must be **cursor-aware and history-preserving**, not single-current-revision. Ingesting a later Swing revision or invalidation must never destroy the ability to correctly answer an earlier-cursor query. The two ground-truth symptoms above (identical-ref dedup short-circuiting recomputation; destructive single-revision Swing state mutation) are concrete instances of this gap and must be resolved by the follow-on implementation remediation — but the *specific* internal representation (revision history list, event-sourced replay, or another mechanism) is implementation-level and is deliberately **not** dictated here.

**Append-only/determinism preserved:** `computation_cursor` is populated once, at construction, exactly like every other payload field (I-3 append-only, unaffected); no existing field is mutated; a replacement fact's `computation_cursor` is independent of the fact it supersedes, reflecting that specific replacement's own re-evaluation boundary.

**Alternatives considered:**

1. **Explicit cursor evidence added directly to the Feature event payload (chosen).** Minimal, durable-by-construction (same append-only log the fact already lives on), directly precedented by Decision's `decision_context_cursor` (Chapter 8 §8.4) solving the identical problem class, and bounded to Feature's own small closed upstream surface rather than importing Decision-scale machinery Feature does not need.
2. **A separate authoritative cursor/provenance artifact referenced by Feature events (a new event type, Event Contract, and stream).** Rejected — adds an entire new authoritative-artifact class, causation hop, and stream/registry surface area for information that fits directly on the fact that already needs it; Chapter 8 §8.4 made the identical choice for Decision (embed `decision_context_cursor` in the envelope, not a separate referenced event). Violates this ADR chain's own established minimality principle (ADR-034 Alternative 2's identical rejection logic).
3. **Deriving the cursor from existing envelope/evidence fields (`recorded_time`, `input_fact_refs`, `causation_refs`).** Rejected — `recorded_time` is append time, not evaluation-boundary time (the exact substitution ADR-034 forbids); `input_fact_refs`/`causation_refs` record only facts that *were* selected, never the boundary that determined what was visible-but-rejected, so they cannot answer the visibility question for a `SwingConfirmed` absent from those refs — precisely the case `eligible_swing_selection_superseded` needs to prove.
4. **Overloading `correlation_id` or `invalidation_reason`.** Rejected — `correlation_id` already has a distinct, Locked Chapter 8 §8.2.1 semantic (workflow-correlation, not knowledge-boundary); `invalidation_reason` is optional, free-text, and not machine-validated (`feature.md` §4 payload). Conflating either with cursor evidence violates I-12/Chapter 6's one-concept-one-field discipline — the same reasoning Chapter 8 §8.4 gives for why `decision_context_cursor` needed its own field rather than reusing `decision_time`.
5. **Relying on process-local/in-memory engine state alone.** Rejected — explicitly the exact gap ADR-034 already closed the loophole on; not durable, not restart-survivable, not independently reconstructable by a second process or a different execution mode.
6. **A new global cross-stream sequence/order.** Rejected — would contradict [ADR-009](./ADR-009.md)'s decision that no global total order exists across independent streams; `stream_positions` stays a bounded per-stream map, never a cross-stream ordinal.

**Consequences:** This ADR resolves the durable-cursor **architecture prerequisite** only. It does not itself amend `feature.md`, does not implement `feature-engine`, does not remediate `swing_distance.py`, and does not close `P3-FEATURE-A-MAJ-04` or `P3-FEATURE-A-MAJ-06`. Three bounded, separate, ordered follow-on transactions are required: (1) a versioned `feature.md` amendment adding `computation_cursor` to `FeatureComputed`/`FeatureFactInvalidated` §3/§4 payload with the invariants above — Review A/B on that Domain Contract delta; (2) a bounded `feature-engine` implementation remediation making engine-internal upstream state cursor-aware/history-preserving and populating `computation_cursor` on every emitted fact, which then satisfies ADR-034's evidence prerequisite and unblocks `eligible_swing_selection_superseded` emission, with accompanying tests proving the exact `A -> invalidate -> B(temporary) -> A(N+1)-wins` scenario now durably provable across a simulated restart; (3) a bounded Review-A re-review of `P3-FEATURE-A-MAJ-04`/`P3-FEATURE-A-MAJ-06` against the corrected representation. This ADR does not change ADR-034's decision, its new invalidation cause, Eligible-Swing ordering (`feature.md` §9a), Feature subject identity (§1), Feature-to-Feature dependency (§10, still deferred), the module dependency graph, or any ownership boundary — Structure/Raw-Regime/Context/Strategy ownership, `module-registry.yaml`, and Chapter 8 (Locked) are all unaffected and unreferenced by this decision.
