# ADR-037: Feature Computation Dependency Content Identity Evidence

**Context:** [`02-platform-invariants.md`](../constitution/02-platform-invariants.md) I-5 requires that Replay execution depend only on already-persisted events and materialized/immutable artifacts, and explicitly names a checksum-bearing, content-addressed reference as the sanctioned mechanism for large/external dependencies — and explicitly forbids treating materialization alone as sufficient proof: *"Coi content-addressed reference là đủ để đảm bảo offline... nếu artifact chưa materialize trước khi Replay execution, Replay vẫn có thể fail khi cắt mạng"* (I-5, Prohibited behavior). [`08-event-model.md`](../constitution/08-event-model.md) §8.1.1 rule 5 requires every Referenced Authoritative Artifact to have a *verifiable content identity* — not necessarily inline on every event, but resolvable — and §8.5.1 fixes the canonical Chapter 8 Replay Cursor (`replay_cursor`) as a **closed**, five-field structure (`recorded_time`, `input_contract_ref`, `stream_registry_version`, `lifecycle_frontier`, `stream_positions`) that does not itself carry content identity.

[ADR-035](./ADR-035.md) (Approved v0.2) decided that Feature's `computation_cursor` payload field on `FeatureComputed`/`FeatureFactInvalidated` is the canonical §8.5 Replay Cursor **verbatim** — required on every fact, captured independently at each fact's own evaluation. ADR-035's own "Fail-closed consequence" paragraph already named today's exact gap without solving it: *"a `computation_cursor` value cannot genuinely satisfy §8.1.1's five conditions... until the referenced Stream Registry/Input Contract artifacts are genuinely persistently resolvable."* `P3-FEATURE-QG-EVID-05` (Chapter 13 Quality Gate finding, I-5 dimension) was split into two independently-tracked parts by `feature-engine-chapter13-remediation-plan-001.md`: part (a), self-contained Replay execution, is `SATISFIED` (Review-A-validated, `tests/test_replay_isolation.py`); part (b), persisted content-identity evidence for the Input Contract/Stream Registry artifacts a computation actually used, remains `OPEN` — this ADR resolves part (b)'s architecture.

**Ground truth, independently confirmed (repository HEAD `122433cea77925414da8d223b07fce3efbcab72d`):** `VerifiedInputContractAuthority` (`contracts.py`) already computes `input_contract_content_id: str` and `stream_registry_content_id: str` — SHA-256 hex digests of the real Input Contract/Stream Registry artifact bytes, computed exactly once in `authority_resolver.resolve_input_contract_authority_from_repository`, at construction/Replay-preparation time, never recomputed by any runtime handler. `ComputationCursor` currently carries exactly the five canonical §8.5.1 fields, nothing more. Neither `input_contract_content_id` nor `stream_registry_content_id` is threaded into any persisted, replay-relevant event field today — they exist only on the in-memory authority object, discarded once the process holding it exits. This ADR adopts, without redesign, the reviewed design candidate `docs/governance/quality-gate/feature-engine-evid05b-content-identity-design-candidate-001.md` (content identity `3a1378ab298220f678291e616e0aac4fc63a59f4`), whose Option 2 — after two bounded Review A re-review rounds closing `P3-FEATURE-QG-EVID05B-A-MAJ-01` and `-MAJ-02` — is the reviewed, minimum-existing-authority recommendation.

**Scope classification — `ADR Required`.** [Chapter 0 §4b](../constitution/00-governance.md) lists "thay đổi Event Schema" as one of several independently sufficient ADR-required triggers — confirmed disjunctive by direct Approved-ADR precedent ([ADR-025](./ADR-025.md), cited verbatim in [ADR-034](./ADR-034.md)'s own scope classification: satisfying `Event Schema` alone is sufficient, independent of any `>1 module`/`khó đảo ngược` clause). Adding one new **required** payload value to two authoritative Feature events (`FeatureComputed`, `FeatureFactInvalidated`) is exactly this trigger — the same class of change ADR-034 (`invalidation_cause`) and ADR-035 (`computation_cursor`) each independently classified `ADR Required` for themselves. No higher-authority mechanism resolves this without an Event-Schema change: the content identities in question are artifact-provenance evidence, not something any existing field (`recorded_time`, `input_fact_refs`, `causation_refs`, `computation_cursor`) already carries or could be reinterpreted to carry.

**Decision:** Feature's authoritative `FeatureComputed` and `FeatureFactInvalidated` events (`feature.md` §3/§4) each carry one new **required** payload value, `computation_dependency_content_evidence`, structurally separate from — never nested inside, never merged into — `computation_cursor`:

```yaml
computation_dependency_content_evidence:      # sibling to computation_cursor, NOT part of it —
                                               #   artifact-content evidence, never a replay
                                               #   ordering/visibility/cursor concept
  input_contract_content_id:                  # Required — SHA-256 content identity of the exact
                                               #   Input Contract artifact bytes this computation's
                                               #   own computation_cursor.input_contract_ref resolved to
  stream_registry_content_id:                 # Required — SHA-256 content identity of the exact
                                               #   Stream Registry artifact bytes this computation's
                                               #   own computation_cursor.stream_registry_version
                                               #   resolved to
```

Both values are copied **verbatim** from the same genuine `VerifiedInputContractAuthority` instance the computation engine resolved and cached for that exact fact's own evaluation — never recomputed, invented, or sourced from any other instance.

**Binding rules (required semantics):**

- **Exact artifact bytes determine content identity.** `input_contract_content_id`/`stream_registry_content_id` are content hashes of the referenced artifacts' real bytes (SHA-256, the same algorithm `authority_resolver.py` already uses) — never a derived, truncated, or approximate identity.
- **Logical version/name alone is insufficient.** `computation_cursor.input_contract_ref {contract_id, contract_version}` and `.stream_registry_version` remain the logical/version identity (unchanged, ADR-035); `computation_dependency_content_evidence` adds the content proof beyond that identity — a version string silently repointed at different bytes (a Chapter 8 §8.1.1 rule 2 violation: "Immutable sau khi được tham chiếu") becomes detectable instead of structurally unverifiable, exactly the gap ADR-035's own "Fail-closed consequence" paragraph left open.
- **Each fact independently persists its own computation-time dependency evidence.** `computation_dependency_content_evidence` is populated once, at construction, exactly like `computation_cursor` and every other payload field (I-3 append-only) — for every `FeatureComputed`, original and replacement alike, and for every `FeatureFactInvalidated`.
- **Original/replacement/invalidation facts must not inherit stale evidence from another evaluation.** A replacement fact's `computation_dependency_content_evidence` is independent of the fact it supersedes; an invalidation's is independent of the fact it invalidates — mirroring `computation_cursor`'s own already-established "never inherited/copied from the fact it supersedes" discipline (ADR-035). No fact may copy, reference, or derive its evidence from a sibling fact's own evidence.
- **Evidence must correspond relationally to the fact's own `computation_cursor`.** `input_contract_content_id` MUST be the content identity of the exact artifact `computation_cursor.input_contract_ref` on that SAME fact resolved to; `stream_registry_content_id` MUST correspond identically to that same fact's own `computation_cursor.stream_registry_version`. Evidence carrying a content identity for a *different* `input_contract_ref`/`stream_registry_version` than the one that same fact's own `computation_cursor` names is malformed and MUST be rejected wherever validated — never accepted merely because both fields are individually well-formed (the identical class of error Chapter 8 §8.5.2's own relational-invariant tables already guard against for `computation_cursor` itself).
- **Replay preparation resolves, recomputes, and compares — before Replay execution begins.** For a given fact, Replay preparation resolves the exact Input Contract/Stream Registry artifacts named by that fact's own `computation_cursor.input_contract_ref`/`.stream_registry_version` (the same mechanism `authority_resolver.py` already implements), recomputes their current content identities from the real current bytes, and compares each against that same fact's own `computation_dependency_content_evidence`.
- **Fail closed before Replay execution on any of: missing artifact, malformed evidence, reference mismatch, or content-ID mismatch.** A referenced artifact that cannot be resolved; a `computation_dependency_content_evidence` missing either required value or not well-formed; a `computation_dependency_content_evidence` that does not relationally correspond to that fact's own `computation_cursor` (previous bullet); or a recomputed content identity that does not exactly equal the persisted one — each independently and unconditionally prevents Replay execution from starting. None of these may be treated as a warning, a best-effort continuation, or silently defaulted.
- **Replay execution uses only already-verified, already-materialized authority — `EVID-05(a)` preserved.** The resolve/recompute/compare sequence above happens entirely during Replay preparation; once it succeeds, Replay execution proceeds exactly as `EVID-05(a)`'s own validated evidence (`tests/test_replay_isolation.py`) already proves — no further filesystem/network access, no re-resolution of any kind. This decision adds a precondition Replay preparation must satisfy; it adds nothing to what Replay execution itself is permitted to do, and does not reopen or revisit `EVID-05(a)`'s own disposition.
- **No process-local/cache/object identity qualifies as durable evidence.** `computation_dependency_content_evidence`'s two values are content hashes carried on the durable, append-only event log itself (Chapter 8 §8.1, I-12's own authoritative source for runtime facts) — never a Python object identity, an in-memory cache key, a process-local pointer, or any value that does not survive process restart and independent reconstruction by a different execution mode (feature.md §13 mode parity, unaffected and unextended by this decision beyond what it already required for `computation_cursor`).

**Does not alter Chapter 8's canonical Replay Cursor, and does not amend ADR-035.** [`08-event-model.md`](../constitution/08-event-model.md) §8.5's closed five-field `replay_cursor` cardinality table is unchanged, byte-for-byte; `ComputationCursor`'s shape is unchanged; ADR-035's own decision content, semantics, and Approved status are unchanged and unedited — `computation_dependency_content_evidence` is a sibling payload value on the *event*, never a change to the *cursor* value type ADR-035 fixed. Fresh authority review for this ADR found no basis on which this decision alters any ADR-035 semantic; ADR-035 is therefore cited via `depends_on` (below), not superseded or amended.

**Alternatives considered:**

1. **Extend the canonical Chapter-8 `replay_cursor` itself with artifact content identities.** Rejected — correct mechanism, wrong owner/scope. Every event carrying any `replay_cursor`-shaped value (`decision_context_cursor` per §8.4, any future Decision/Strategy/Risk/Execution consumer) would inherit the new fields regardless of whether that consumer's own artifacts even have a content-identity story yet; requires reopening **Locked** Chapter 8 §8.5's own closed cardinality table — a chapter-level, platform-wide amendment (independently `>1 module` under Chapter 0 §4b), not a Feature-scoped decision Feature Engine's own remediation can make.
2. **Keep `computation_cursor` unchanged; persist content-identity evidence adjacent to it, directly on `FeatureComputed`/`FeatureFactInvalidated` (chosen).** Satisfies I-5/§8.1.1 rule 5 without touching Chapter 8's owned schema or ADR-035's decision content; the only cost is a single, well-precedented Event Schema addition (this ADR), identical in class and scale to ADR-034/ADR-035's own already-approved changes to these same two events.
3. **Extend/redefine the Input Contract/Stream Registry reference mechanism so content identity is carried by the referenced artifact's own identity.** Rejected — does not actually close the gap. Artifact-level content identity is already fully computable today (`authority_resolver.py` hashes the artifact's *current* bytes on every resolution); what is missing is a durable, per-computation historical comparison point, which redefining the artifact's own identity mechanism does not create — it would still need an Option-2-shaped persisted record layered on top. Also `>1 module, platform-wide`: Input Contract/Stream Registry are Chapter-8-owned artifact classes (§8.1.1's own named taxonomy), not Feature's to redefine, affecting every current/future consumer of those classes.
4. **(4A) A genuinely new, dedicated run/replay content-identity manifest.** Not constitutionally invalid — Chapter 8 §8.1.1 rule 5's "identity có thể nằm ở run manifest thay vì lặp trên mọi event" explicitly sanctions an off-event mechanism of this general shape, and a purpose-built one could in principle satisfy every §8.1.1 condition. Rejected for **current scope**, not on principle: no such governed authority, ownership, versioning, retention, or resolution mechanism exists anywhere in this repository today (independently confirmed — a repository-wide search for `run_manifest`/`replay_manifest` found zero authoritative schema; `raw_regime_engine.RegimeDefinition.content_identity()` is a hash-producing capability whose own docstring explicitly disclaims inventing "definition registry/storage/lifecycle authority"). Building one requires inventing an entire new authoritative-artifact class — including a self-reference problem the manifest artifact itself would need to solve — before any of EVID-05(b)'s own invariants could be met; larger design footprint than option 2, not smaller, under current authority. Remains available as a future superseding architecture should circumstances change (e.g. a second consumer of the same content-identity evidence emerges).
5. **(4B) Extend governance `docs/MANIFEST.md` into a runtime checksum authority.** Also not constitutionally invalid in principle, but rejected for current scope: this assigns `docs/MANIFEST.md` a **new authoritative responsibility** — a runtime dependency-verification source Replay preparation would depend on for a fail-closed decision — which is materially different from, and not a natural reading of, MANIFEST's current Chapter 0 §5b/§7 scope (Decision Log; document version/status; ADR lifecycle/supersession; OQ status). Direct, on-point repository precedent confirms this is not "ordinary bookkeeping": [ADR-022](./ADR-022.md) assigned MANIFEST.md canonical authority for a comparable new role only through a full governed ADR, and explicitly limited that designation to "Phase 1 architecture-only," stating it does **not** carry MANIFEST forward as a runtime activation authority — reserving exactly this kind of runtime extension for "một ADR successor... riêng." Concrete structural gaps also remain unresolved under this option: MANIFEST rows are routinely mutated in place today (a new per-row immutability rule would be needed), MANIFEST tracks current state per document rather than a durable per-historical-version ledger, and a replay-verification lookup would need to pin an as-of-MANIFEST-commit identity MANIFEST has no existing mechanism for.

**Compatibility/versioning under Chapter 10 (explicit assessment, not waived by pre-production status):** Per [`10-compatibility-capability-contract.md`](../constitution/10-compatibility-capability-contract.md) §10.3.1's own minimal classification rule — *"thêm element **required** không có fallback → **breaking**"* — adding `computation_dependency_content_evidence` as a required field to `FeatureComputed`/`FeatureFactInvalidated` is a **breaking change** on the backward-compatible axis (an old consumer reading a new event gains a field it didn't expect, generally tolerable; a consumer *validating against the old required-field set* would reject the new shape, and symmetrically a consumer expecting the new required field cannot validate old-shaped data — forward compatibility fails outright, since pre-this-ADR events have no such field at all). This is classified as breaking here **regardless of** the fact that Feature Engine has zero production events today (Phase 3, pre-production) — pre-production status is not used to waive the classification itself, only to note that no live migration burden currently exists because there is no historical data to migrate. §10.3's three independent version axes apply: this decision requires the Feature Output **Event Contract version** (`event_contract_ref.contract_version`, Chapter 8 §8.2.5) to be bumped (major, per the breaking classification) once this field is actually implemented and emitted — `schema_version` and Plugin Version are unaffected, distinct axes. Per `contracts.py`'s own already-established discipline (`P3-FEATURE-A-MAJ-02` remediation), feature-engine itself never invents this version value — `resolve_output_contract_refs` requires it be caller-supplied — so this ADR does not mint one; minting the correct bumped version identity is a follow-on responsibility of whichever transaction actually implements this field, not decided here.

**Consequences:** This ADR resolves the `EVID-05(b)` architecture decision only. It does not itself amend `feature.md`, does not implement `feature-engine`, and does not close `P3-FEATURE-QG-EVID-05(b)` or `EVID-05` overall. Three bounded, separate, ordered follow-on transactions are required: (1) a versioned `feature.md` amendment adding `computation_dependency_content_evidence` to `FeatureComputed`/`FeatureFactInvalidated` §3/§4 payload with the binding rules above, including the Feature Output Event Contract version bump this ADR's Compatibility assessment requires — Review A/B on that Domain Contract delta; (2) a bounded `feature-engine` implementation populating the field on every emitted fact from the engine's own already-cached `VerifiedInputContractAuthority`, plus the Replay-preparation resolve/recompute/compare/fail-closed check, with accompanying tests proving genuine fail-closed behavior on each of the four named failure modes; (3) a bounded Review-A re-review closing `P3-FEATURE-QG-EVID-05(b)` (and, if all four conditions are then met, `EVID-05` overall) against the corrected representation. This ADR does not change ADR-034's decision, ADR-035's decision, Chapter 8's canonical `replay_cursor`, Feature subject identity, Feature-to-Feature dependency (`feature.md` §10, still deferred), the module dependency graph, or any ownership boundary — Structure/Raw-Regime/Context/Strategy ownership, `module-registry.yaml`, and Chapter 8 (Locked) are all unaffected and unreferenced by this decision. `EVID-05(a)`'s `SATISFIED` disposition is unaffected and unrevisited.
