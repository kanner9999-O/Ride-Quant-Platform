# ADR-036: Genesis Stream Registry Topology — Phase-3 Core Analytical Chain Writer Authority

**Context:** [Chapter 8](../constitution/08-event-model.md) §8.3.1 requires every authoritative event to belong to exactly one ordered stream, and vests stream identity/topology/writer authority/lifecycle/sequence policy/genesis position **solely** in `docs/architecture/stream-registry.yaml` — "KHÔNG có version namespace riêng cho từng stream," Event Contract may only declare eligibility (`allowed_streams`), never define stream existence. [ADR-009](./ADR-009.md) (Approved) §2.6 requires the Genesis Registry to define "đúng MỘT canonical Lifecycle Stream và đúng MỘT canonical Audit Stream," both protected (never retired). No `stream-registry.yaml` exists anywhere in this repository (verified directly, `find` returns nothing). Chapter 8 §8.3.1/§8.5 and ADR-009 §6 explicitly defer the **concrete** topology/writer/genesis mechanics to "Phase 1 design specification" — they decide the *mechanism*, not the *instance*.

**Ground-truth confirmation (direct code inspection, not architecture authority):** the four writer modules of the currently-implemented Phase-3 analytical chain use mutually inconsistent, unauthoritative stream-identity placeholders. `market-data-ingestion` (Go, `internal/publish/memory.go`) uses a single hardcoded `fakeStreamID = "candle-events-fake"`, explicitly commented "placeholder single-stream topology." `structure-engine` (Python) is internally inconsistent with itself: `swing.py` defaults `stream_id: str = "swing"` (flat, module-level) while `structure.py`'s own `_structure_stream_id()` instead derives `f"structure:{structure_subject_id}"` (subject-scoped) — two different partitioning models inside one module, neither pinned by any authority. `raw-regime-engine` defaults `stream_id: str = "regime"` (flat). `feature-engine` defaults `stream_id: str = "feature"` (flat) for both its Regime-passthrough and Swing-distance paths. All of these are constructor-default, caller-overridable Python/Go values — not fixed identities, not registered anywhere, not resolvable under [Chapter 8 §8.1.1](../constitution/08-event-model.md)'s five conditions for a Referenced Authoritative Artifact (versioned; immutable-once-referenced; non-reused identifier; persistently resolvable; verifiable content identity). This is exactly the gap [ADR-035](./ADR-035.md) (Approved) already relies on existing and already refuses to paper over with an invented stand-in for Feature's own `computation_cursor.input_contract_ref`/`stream_registry_version`/`lifecycle_frontier`/`stream_positions` — that ADR's fail-closed posture is only as good as this genuinely-unresolved prerequisite being resolved by real architecture, not by any single module quietly picking its own convention.

**Scope classification — `ADR Required`, independently triggered.** This ADR is **not** justified by "`P3-FEATURE-A-MAJ-06` needs another ADR" — it is triggered because establishing which concrete non-protected streams exist and which module holds sole writer authority over each is, per [Chapter 0 §4b](../constitution/00-governance.md) and Chapter 8 §8.3.1's own text ("Tạo/xóa/tách stream, hoặc đổi writer authority, là thay đổi Event Model → ADR Required"), a genuine Event-Model change: it affects four already-registered modules simultaneously (`>1 module`) and is hard to reverse once event data accumulates under a given topology (changing stream boundaries later requires a new ADR plus a registry-version transition affecting every consumer's `stream_positions`/`lifecycle_frontier` bookkeeping). No already-Approved authority pins the concrete stream identities/topology/writers needed here — Chapter 8/ADR-009 explicitly defer this to Phase 1 design work, and no such design has been authored. This v0.2 correction additionally introduces a new module identity (`stream-registry-authority`, §"Protected streams" below) — independently and equally sufficient to satisfy the disjunctive-OR §4b test under its Module Taxonomy trigger (same reading ADR-025 already established for this repository), not a second reason to author a second ADR. `ADR_REQUIRED` confirmed by direct inspection, not assumption.

**Decision:** Establish the minimum Genesis Registry topology for the currently-implemented analytical chain (`Market Data Ingestion → Structure/Swing → Raw Regime → Feature`) as **one logical stream per authoritative fact family a writer module owns**, never scoped/partitioned by instrument/venue/timeframe/strategy, **plus** the two Genesis-mandatory protected control-plane streams, whose exact identity and initial writer authority this ADR now pins in full (not deferred):

**1. Partitioning rule (item 1/3):** exactly one stream per writer module per authoritative fact family it owns — `structure-engine` owns two streams (Swing, Structure) because they are two distinct Domain Contracts (`swing.md`/`structure.md`) with different consumer sets (Feature consumes only Swing, per `feature.md` §14's exclusion list; a future Context module would consume Structure) — keeping them separate lets a future Feature-scoped Input Contract include exactly the Swing stream without needing to filter Structure events out of a shared stream. No stream is partitioned by `instrument_id`/`venue_id`/`timeframe`/`strategy` — see Alternative 2 for why.

**2/8. Protected streams — exact identity and initial writer authority, pinned (items 2, 8):** Chapter 8 §8.3.5 requires the Genesis Registry itself to "định nghĩa writer authority ban đầu" (define initial writer authority) for the canonical Lifecycle Stream and canonical Audit Stream — this is Stream Registry architecture authority, not a fact a later mechanical registry-authoring transaction may invent. ADR-036 therefore decides it here, in full:

- **Canonical Lifecycle Stream `stream_id`:** `platform-lifecycle` — adopted as the actual decision (not merely recommended), for direct consistency with every worked example already used consistently across Chapter 8 §8.3.1/§8.3.5/§8.4/§8.5.
- **Canonical Audit Stream `stream_id`:** `platform-audit` — Chapter 8 gives no existing illustrative literal name for this stream; this ADR originates the identity.
- **Initial writer authority for both protected streams:** a new dedicated module, `stream-registry-authority` (Type 3 Runtime Service per Chapter 7 §7.1 — "sở hữu runtime interaction, orchestration, coordination, hoặc control"). **No existing registered module is assigned this responsibility**: none of the modules currently registered in `module-registry.yaml` — including the four analytical writer modules this same ADR names above — carry stream-lifecycle/registry-governance among their registered responsibilities (Chapter 3 §3.1). Assigning it to, say, `market-data-ingestion` merely because it is the earliest-running module would be an unregistered secondary responsibility used to bypass responsibility ownership, exactly the god-module pattern Chapter 7 §7.2's guardrail forbids. `stream-registry-authority`'s sole responsibility, decided here, is: exclusive writer authority over the two Genesis-protected streams, and — per §8.3.1/§8.3.5/§8.4.1 — sole authority permitted to author stream lifecycle boundaries (Genesis activation, stream activation/retirement, writer-authority handoff, registry-version transition) on the Lifecycle Stream, and audit-preservation facts on the Audit Stream. One module legitimately holds writer authority over two distinct streams (Chapter 8 §8.3.1: "Một module có thể ghi vào nhiều stream, nhưng mỗi stream chỉ có 1 writer authority") — the same pattern this ADR already uses for `structure-engine`.
- **Required post-approval consequence (not performed by this ADR):** Declaration-tier registration of `stream-registry-authority` in `module-registry.yaml` (module identity, `module_type: runtime_service`, the responsibility stated above, `depends_on: []`) — a separate **governed semantic module-registry alignment: an EXACT mechanical transcription of Approved ADR-036**, containing no new architecture choice, following the same precedent module-registry.yaml already records for `contract-compatibility-authority` ("genuine semantic registry change — EXACT mechanical transcription of Approved ADR-023 ... NOT a new architecture decision, NOT a new ADR"). Per Chapter 7 §7.5, `module-registry.yaml` remains the sole authority for concrete module identity/taxonomy/mapping, and that transcription transaction remains subject to the applicable package-lifecycle/review rules governing that registry — this ADR does not prescribe bypassing them. This ADR does not itself edit `module-registry.yaml` and does not create a second ADR to accomplish this — the architecture decision is complete here; only the registry transcription is deferred (Consequences step 4).
- Protected-stream semantics are otherwise **unchanged**: exactly one Lifecycle Stream and one Audit Stream, stable identities, never retired (§8.3.5), and any future writer-authority handoff for either must follow the ordinary handoff invariants (§8.3.1) already Locked — this ADR does not alter them.

Each of the five analytical streams above likewise has **exactly one** writer authority — the module already registered in `module-registry.yaml` as sole authoritative owner of that fact family (Chapter 3 §3.1). This introduces no new writer-coordination mechanism; it simply names the writer each of those four modules already is.

**4. Stable/non-reusable identity, genesis position (item 4):** each stream_id above — all seven, the five analytical streams and the two protected streams alike — is a Logical Stream Identity (Chapter 8 §8.3.1) — stable across all future `registry_version` transitions, never reused even if retired (protected streams are additionally never retired at all, §8.3.5). All seven begin at `genesis_position: 0` (Chapter 8 §8.3.1's own registry schema, and §8.3.5's Genesis Registry exception) since they are all introduced at the same Genesis Registry with no pre-existing data.

**5. `stream_ref.registry_version` resolution (item 5):** once the concrete Genesis Registry is authored (Consequences step 5) with its own immutable `registry_version` identifier, every future event any of the seven streams' writers emit (the five analytical writer modules, and `stream-registry-authority` for the two protected streams) pins that exact value. This repository has **no production authoritative event log today** (Phase 3 development, LIVE `NOT_AUTHORIZED`) — there is no real historical data requiring migration. The `"v0"`/`"swing"`/`"regime"`/`"feature"`/`"candle-events-fake"` placeholders in current code (item 9) are **implementation assumptions, never grandfathered authority**: they must be *replaced* by the genuine Genesis `registry_version` and stream_ids once the concrete registry exists (Consequences step 5), not reinterpreted as already-valid Genesis values.

**6. Boundary vs. Event Contract `allowed_streams` (item 6):** per Chapter 8 §8.3.1's own already-Locked rule ("Stream Registry KHÔNG chứa `allowed_event_types`... khai báo MỘT CHIỀU tại Event Contract"), this ADR pins **only** which module writes to which stream (topology) and each stream's bounded architectural purpose/domain family — it does **not** decide, and neither the Decision table's "Domain family" column above nor the future concrete `stream-registry.yaml` may contain, which event *types* may target each stream. That eligibility is declared exclusively by each event type's own future Event Contract `allowed_streams` field (Domain-Contract-level work, out of this ADR's scope, unauthored for any module's events today, protected streams included).

**7. No global ordering introduced (item 7):** per-stream sequence remains contiguous, atomically allocated by the single named writer (ADR-009 §2.1, unchanged). No cross-stream sequence comparison and no global ordinal is introduced by this topology — seven independent per-stream counters (five analytical, two protected), exactly as ADR-009 §2.3 already requires.

**9. Migration treatment (item 9):** see item 5 above — no data migration exists to perform; code/test stream-identity assumptions are replaced, not migrated, once concrete artifacts exist.

**Scale invariance (directly supports Scale check):** under this topology, growth in instrument/venue/timeframe/strategy count changes **event volume within** the five analytical streams (the two protected streams are structurally independent of that growth axis entirely) — it never creates a new stream, never bumps `registry_version`, and never requires a new ADR. A `registry_version` bump is reserved for genuine structural changes (a new writer module, a stream retirement, a writer handoff) — rare, deliberate Event-Model decisions, not routine data growth.

**Alternatives considered:**

1. **One stream per writer module per authoritative fact family (chosen).** Matches each module's already-registered "one authoritative implementation per capability" status (Chapter 3 §3.1) with trivial single-writer satisfaction; keeps the five-stream (seven including protected) topology scale-invariant with respect to instrument/venue/timeframe/strategy growth; cleanly separates Stream Registry topology authority from `subject_ref`/Event-Contract payload-scoping authority (Chapter 8 §8.2.2), which this ADR does not touch.
2. **Scope-partitioned streams (module + instrument/venue/timeframe).** Rejected — would require creating (and registering, per §8.3.1's "creating a stream is an Event-Model change") a new stream for every new instrument/venue/timeframe combination, growing stream count combinatorially rather than the "hàng trăm" total ADR-009 §5 anticipates for the *entire platform*; also conflates Stream Registry topology with `subject_ref` scoping, which Chapter 8 explicitly separates.
3. **One shared analytical stream for all four modules.** Rejected — directly violates Chapter 8 §8.3.1's single-writer-per-stream invariant: four independent writer modules cannot atomically share one contiguous sequence counter without an unauthorized new cross-module coordination component, and would either require inventing one or silently create multiple de facto writers on one stream (an explicit integrity violation, §8.3.2).
4. **Preserving current arbitrary caller-supplied/default stream IDs as authority.** Rejected — these are unauthoritative, mutually inconsistent even within one module (`structure-engine`'s own flat-vs-subject-scoped split), caller-overridable rather than fixed, and never satisfy Chapter 8 §8.1.1's Referenced-Authoritative-Artifact conditions. This is precisely the gap this ADR exists to close, not a valid alternative to closing it.
