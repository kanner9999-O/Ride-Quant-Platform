# ADR-040: Platform-wide Retention/Archive Policy Semantics for Referenced Authoritative Artifacts

**Context:** [`08-event-model.md`](../constitution/08-event-model.md) §8.1.1 requires every Referenced Authoritative Artifact — Stream Registry, Event Contract, Input Contract, and any artifact added later, named as an auto-applying general rule, not a per-artifact-type discovery — to be persistently resolvable through the platform's own **committed replay/audit horizon**, and requires an **explicit retention/archive policy** governing what happens past that horizon, such that no artifact is ever lost unintentionally. [`10-compatibility-capability-contract.md`](../constitution/10-compatibility-capability-contract.md) §10.4.4 states the identical resolvability/retention distinction specifically for Compatibility Result and Policy (immutable ≠ retained online forever), and §10.9 explicitly defers the **concrete** retention/archive protocol — storage/format/schema, matching mechanism, tooling — to Phase 1/mechanism decisions, locking only the *requirement*, not the *mechanism*. No artifact anywhere in this repository currently supplies that explicit policy at any level, architecture or mechanism.

**Ground truth, independently confirmed at the current boundary:** direct search across `docs/constitution/*.md`, `docs/adr/*.md`, and every other tracked artifact confirms every existing mention of "retention"/"archive" either (a) restates §8.1.1/§10.4.4's own requirement without resolving it, or (b) explicitly defers the concrete mechanism as future/out-of-scope work (`ADR-009` §"archive/retention implementation → cần retention/archive design"; `ADR-016`/`ADR-027`/`ADR-030` each separately defer storage/retention backend specifics as implementation detail; `10-compatibility-capability-contract.md` §10.9 explicitly lists "retention/archive protocol cụ thể" as deferred). `ADR-039` (Approved) is the most recent artifact to name this exact gap directly, recording it as an unresolved Consequences prerequisite: a version-artifact "must not be treated as satisfying §8.1.1 in full, and must not become a usable `event_contract_ref` target for a real, persisted authoritative event, until an authoritative retention/archive policy is separately established." No policy — at the architecture-semantics level this ADR addresses, or at the concrete-mechanism level §10.9 defers — exists anywhere in this repository today. This gap predates `ADR-039` (it is a direct, general consequence of Chapter 8 §8.1.1 rule 4 and Chapter 10 §10.4.4, both already Locked); `ADR-039` is treated here strictly as the **Feature use-case that most recently exposed** it, not its origin.

**Scope classification — `ADR Required`.** [Chapter 0 §4b](../constitution/00-governance.md) lists both "quyết định ảnh hưởng >1 module" and "khó đảo ngược" as independently sufficient triggers. §8.1.1's own retention/archive requirement applies, by explicit textual design, to **every current and future artifact actually referenced by an event or cursor envelope field** — today: Stream Registry (`docs/architecture/stream-registry.yaml`, Chapter 8 §8.3.1, Approved), Event Contract version-artifacts (`ADR-039`), and Input Contracts (`docs/architecture/input-contracts/*.yaml`, `input_contract_ref`) — already a strictly broader footprint than any single ADR decided in this series so far (spanning every current writer/reader module across all three), definitionally a >1-module decision. (ADRs, Constitution chapters, and Domain Contracts are governed by their own separate immutability authority — Chapter 11 §11.3; Chapter 0 §5.1 — and are not swept into this scope unless a future decision actually designates one of them as event/cursor-referenced; none currently is.) It is also hard to reverse: once any artifact is archived, pruned, or has its retention commitment relied upon by a replay/audit/compliance operation under one set of semantics, changing those semantics later requires reinterpreting or re-establishing guarantees for everything already archived under the old rule — the exact class Chapter 0 §4b treats as ADR-required independent of the module-count trigger. This is **not** an ADR merely because `ADR-039` left follow-on work open — `G-ADR-003`/`G-ADR-001`/`G-ADR-004` (`docs/governance/execution-rules.md`) forbid authoring an ADR just to "complete" a prior one, and require running the inflation/scope check first (recorded in full below, per this transaction's own prompt). `ADR-039` is treated here strictly as the exposing use-case; this ADR's own decision content is derived independently from Chapter 8 §8.1.1 and Chapter 10 §10.4.4/§10.9 directly, not from `ADR-039`'s own decision content — `depends_on: []` accordingly.

**Decision:** This ADR fixes the **architecture-level retention/archive semantics** every Referenced Authoritative Artifact must satisfy — the contract any future concrete mechanism (numeric horizon values, storage tier, archival tooling) must be built against — **without inventing that concrete mechanism**, consistent with the requirement/mechanism split Chapter 10 §10.9 already draws and does not override. Artifacts are classified into exactly two storage classes, determined by where their canonical authoritative content actually lives today (not per-artifact-type, avoiding fragmenting semantics per §8.1.1's own general-rule framing):

- **Class G (git-repository-resident):** any Referenced Authoritative Artifact — in the §8.1.1 sense: actually pinned by an event/cursor envelope field — whose canonical authoritative content is a file tracked in this git repository. Today, exactly three artifact types qualify, each per its own already-Approved/Locked authority, not by assumption: **Stream Registry** (`docs/architecture/stream-registry.yaml`, Chapter 8 §8.3.1, `status: Approved`), **Event Contract version-artifacts** (`ADR-039`), and **Input Contracts** (`docs/architecture/input-contracts/*.yaml`, `input_contract_ref`, Chapter 8 §8.1.1). ADRs, Constitution chapters, and Domain Contracts are **not** included here — they are git-resident documents with their own separate immutability treatment (Chapter 11 §11.3; Chapter 0 §5.1), but are not currently pinned by any event/cursor envelope field, so §8.1.1's Referenced-Authoritative-Artifact retention rule does not currently apply to them; this ADR does not extend it to them.
- **Class R (runtime-resident):** any Referenced Authoritative Artifact whose canonical authoritative content is recorded as data within the running platform itself, not as a git file. Class R **currently has zero realized members** — Stream Registry, the only artifact previously assumed to belong here, is Class G (above), per its own actually-designated canonical authority. Class R is retained purely as a policy class for any future non-git-resident Referenced Authoritative Artifact, should one ever be designated. Compatibility Result/Policy (Chapter 10 §10.4.4) is **not** assigned to either class by this ADR: §10.9 still defers its own canonical storage/format/schema designation, and classifying it here would assign a storage class before that designation exists — this ADR takes no position on Compatibility Result/Policy's eventual class.

**Class G retention/archive policy (fixes `P3-ADR040-A-MAJ-02`):** every current Class G artifact type (Stream Registry, Event Contract version-artifacts, Input Contracts) already has its own Approved/Locked **canonical direct-path resolver** — Stream Registry resolves to the single fixed path `docs/architecture/stream-registry.yaml` (Chapter 8 §8.3.1); Event Contract version-artifacts resolve by pure literal substitution to `docs/architecture/event-contracts/<contract_id>/<contract_version>.yaml` (`ADR-039`); Input Contracts resolve by the equivalent established file-per-instance path convention. This ADR's retention commitment for Class G is: **for the full committed retention horizon, the canonical file must remain present and resolvable at its own canonical path at current `HEAD`** — no renaming, moving, or removal while any reference to it remains within horizon. Git commit/blob history remains available strictly as **content-identity/audit evidence** (confirming a file's hash/history integrity over time) — it is explicitly **not** a fallback resolver: an implementation must never substitute git-history search, checkout-of-an-old-commit, or any equivalent archaeology for the already-Approved/Locked canonical path function above; doing so would be exactly the kind of aliasing/new-resolver-mechanism `ADR-039` already prohibits for its own resolution mechanism, one level down. **Removal** — permanently destroying resolvability of any commit or blob that has ever been referenced by an authoritative event, Decision, replay run, cursor, or governance record, or any history-rewriting operation (force-push over shared history, `filter-branch`/`filter-repo`, rebase of already-pushed commits) that would make a previously-resolvable commit/blob unresolvable — is prohibited. Past the committed retention horizon, if archival is ever pursued for these three artifact types, it must preserve resolution at the same canonical path/identity already established by their own governing authority; this ADR does not invent a concrete archive-tier locator or assume git history silently substitutes for one — that mechanism, like Class R's, is deliberately deferred (see below), not assumed satisfied.

**Class R retention/archive policy (architecture-level floor only, for if/when a member is ever designated):** Class R has no realized members today (above), so this paragraph fixes a standing floor for any future non-git-resident Referenced Authoritative Artifact, without picking a concrete number, storage tier, or tooling — the same requirement/mechanism split §10.9 already draws for Compatibility Result/Policy specifically (a separate, still-unclassified case, not an instance of this paragraph): (a) **fail-closed floor** — whatever committed horizon a future Class R artifact's owning chapter/contract declares, it must never be shorter than the longest currently-active binding that still depends on it (no shortening a horizon out from under a live reference); (b) **archival, not removal, by default** — past its committed horizon, a future Class R artifact may move to a distinct, documented archive path/mechanism, but must remain resolvable through it; true removal (ending resolvability entirely) is not authorized by this ADR and would require its own separate, bounded, future governed decision — this ADR takes no position on whether that is ever appropriate and defaults to "never" absent one.

**Resolvability while active vs. archived:** for both classes, a correctly-implemented resolver must succeed identically for the same artifact identity (commit SHA/content hash, or `{contract_id, contract_version}`-style pin resolving to one) regardless of whether that identity is currently "active" (within the committed horizon, primary storage) or "archived" (past horizon, archive-tier storage) — archival changes storage locality and potentially latency, never the resolved content, its identity, or whether resolution succeeds. A caller does not need to know in advance which state a historical reference is in for correct resolution to succeed.

**Immutable content-identity preservation:** archival is a storage-locality operation only. It must never alter an artifact's content, hash, or identity (§8.1.1 rule 5); a content-identity mismatch discovered after archival is a policy violation, not an acceptable side effect, for either class.

**Fail-closed behavior when an exact referenced artifact cannot be resolved:** if any consumer — replay, audit, compliance, or a runtime reader — requests resolution of an exact, historically-referenced Referenced Authoritative Artifact identity and that resolution fails for any reason (missing, corrupted, hash-mismatched), whether within or past the committed horizon, this is a **hard failure**: the requesting operation must abort and report the specific unresolvable reference. Silently substituting a "nearest" version, skipping the record, or proceeding under degraded/default semantics is prohibited — the same fail-closed, no-aliasing principle `ADR-039` already established for `contract_id`/`contract_version` path resolution, applied one level up to artifact resolvability in general.

**Canonical policy scope/authority:** this ADR is the canonical architecture authority for retention/archive **semantics** applicable to every current and future Referenced Authoritative Artifact platform-wide (Class G today: Stream Registry, Event Contract version-artifacts, Input Contracts; Class R: currently no members). It does not itself become an operational registry/service, does not author `docs/architecture/event-contracts/**` content, and does not implement anything runtime. A future, separate governed decision may author the concrete mechanism for any artifact this ADR leaves deferred — the Class G archival mechanism past-horizon for its three current member types, and the full Class R mechanism whenever a member is first designated — the same requirement/mechanism boundary `10-compatibility-capability-contract.md` §10.9 already draws for Compatibility Result/Policy, left undisturbed here (Compatibility Result/Policy remains unclassified by this ADR, per above, pending its own storage designation).

**Relationship to Chapter 8 §8.1.1 and Chapter 10 §10.4.4/§10.9:** this ADR is the architecture-level artifact §8.1.1 rule 4's "explicit retention/archive policy" requirement and §10.4.4's identical resolvability/retention distinction point to. For Class G's three current member types, it fixes the within-horizon resolvability commitment (canonical path must remain live at `HEAD`) concretely, while leaving past-horizon archival mechanism deferred rather than assuming git history already resolves it. For Class R, it fixes only the architecture-level floor/archival-not-removal/fail-closed semantics for whenever a member is first designated. Neither resolves §10.9's own explicitly deferred concrete protocol/format/tooling, nor Compatibility Result/Policy's own still-pending storage designation — this ADR narrows what remains deferred without touching what §10.9 already, correctly, reserves for a later mechanism decision.

**Alternatives considered:**

1. **(A) Architecture-level retention/archive semantics ADR, two storage classes determined by each artifact's own already-designated canonical authority, Class G within-horizon resolvability fixed concretely via each type's existing canonical resolver, past-horizon archival mechanism and the (currently empty) Class R floor left deferred (chosen).** Minimum architecture that fully satisfies §8.1.1 rule 4's within-horizon resolvability for every artifact type that concretely qualifies today (Stream Registry, Event Contract version-artifacts, Input Contracts, all Class G), without inventing a new resolver/aliasing mechanism or storage-vendor/deployment infrastructure for archival mechanism no current artifact type needs yet; reuses each artifact's own already-Approved/Locked resolver rather than introducing a new one; preserves, rather than overrides, Chapter 10 §10.9's own requirement/mechanism split.
2. **(B) Fully concrete retention/archive protocol authored now — pick actual numeric horizons, storage tiers/vendors, archival tooling for every artifact class.** Rejected — exceeds this architecture decision's proper scope and directly contradicts §10.9's explicit deferral of exactly this ("retention/archive protocol cụ thể... storage/format/schema... tooling, CI gate, báo cáo"); would very likely require rework once real archival deployment constraints (none of which exist yet for any current artifact type) are known — premature, hard-to-reverse commitment in the wrong direction.
3. **(C) No dedicated ADR — let each artifact-owning Domain Contract/ADR define its own retention/archive rule independently, ad hoc.** Rejected — §8.1.1 frames retention as a general rule auto-applying to every current and future Referenced Authoritative Artifact, explicitly "không cần lặp lại ở từng mục" (not to be rediscovered per-item); deciding it piecemeal would fragment fail-closed/archival/resolvability semantics across artifact types and would itself independently qualify as ADR-required per-instance under the same >1-module/hard-to-reverse triggers, multiplying transactions instead of resolving the shared prerequisite once.
4. **(D) Governance `docs/MANIFEST.md` as the retention/archive policy owner.** Rejected on the same grounds already established for the structurally identical question in `ADR-038`'s own corrected reasoning and reused in `ADR-039`: `MANIFEST.md`'s current scope (Decision Log; document version/status; ADR lifecycle/supersession; OQ status) has no natural extension to owning a required, every-artifact-class runtime/architecture retention responsibility; `ADR-022`'s own precedent explicitly declined this exact extension without its own dedicated governed decision — this is not that decision, and nothing here makes it one.

No materially better existing-authority option was identified beyond these four; the chosen mechanism (A) was preferred specifically because it fully resolves within-horizon resolvability for every artifact type that concretely qualifies today, using only each type's own already-Approved/Locked resolver, while explicitly declining to invent archival infrastructure no current artifact type needs yet.

**Consequences:** This ADR fixes platform-wide retention/archive semantics for Referenced Authoritative Artifacts only. It does not itself author or modify any `docs/architecture/event-contracts/**` file, does not implement `event_contract_ref`, does not modify `ADR-039` (remains Approved, immutable, unaffected — `P3-ADR039-B-MIN-01` remains accepted/non-blocking, unaffected by this ADR), does not modify any Locked Constitution chapter or any other Approved ADR, does not modify `module-registry.yaml`/`context-map.yaml`, and does not modify production source/tests/tooling. Bounded, separate follow-on work remains: (0) `ADR-039`'s own Consequences item (0) — establishing that an authoritative retention/archive policy exists before any Event Contract version-artifact becomes a usable `event_contract_ref` target — is now satisfied at the architecture-semantics level for Class G by this ADR (Event Contract version-artifacts are Class G); (1) each Class G artifact-owning document/ADR (Stream Registry's Chapter 8, `ADR-039`, Input Contracts' owning Domain Contracts) may cite this ADR as its within-horizon retention authority instead of restating semantics; (2) a separate governed decision must author the concrete past-horizon archival mechanism for Class G's three member types, and the full Class R mechanism whenever a first Class R member is ever designated, both bound by this ADR's floor/archival-not-removal/fail-closed requirements; (3) `ADR-039`'s own remaining follow-on work (authoring/publishing first `Published` version-artifacts, Feature's own first version snapshots, `event_contract_ref` implementation) is entirely separate, bounded, later work, untouched by this ADR. This ADR does not change Feature Chapter 13 QG evidence, Feature module approval, the Phase 3 Approval Gate, or `LIVE` authorization — all remain exactly as they stood before this transaction, explicitly not granted/not authorized by anything decided here.
