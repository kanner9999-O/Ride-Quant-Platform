# ADR-040: Platform-wide Retention/Archive Policy Semantics for Referenced Authoritative Artifacts

**Context:** [`08-event-model.md`](../constitution/08-event-model.md) §8.1.1 requires every Referenced Authoritative Artifact — Stream Registry, Event Contract, Input Contract, and any artifact added later, named as an auto-applying general rule, not a per-artifact-type discovery — to be persistently resolvable through the platform's own **committed replay/audit horizon**, and requires an **explicit retention/archive policy** governing what happens past that horizon, such that no artifact is ever lost unintentionally. [`10-compatibility-capability-contract.md`](../constitution/10-compatibility-capability-contract.md) §10.4.4 states the identical resolvability/retention distinction specifically for Compatibility Result and Policy (immutable ≠ retained online forever), and §10.9 explicitly defers the **concrete** retention/archive protocol — storage/format/schema, matching mechanism, tooling — to Phase 1/mechanism decisions, locking only the *requirement*, not the *mechanism*. No artifact anywhere in this repository currently supplies that explicit policy at any level, architecture or mechanism.

**Ground truth, independently confirmed at the current boundary:** direct search across `docs/constitution/*.md`, `docs/adr/*.md`, and every other tracked artifact confirms every existing mention of "retention"/"archive" either (a) restates §8.1.1/§10.4.4's own requirement without resolving it, or (b) explicitly defers the concrete mechanism as future/out-of-scope work (`ADR-009` §"archive/retention implementation → cần retention/archive design"; `ADR-016`/`ADR-027`/`ADR-030` each separately defer storage/retention backend specifics as implementation detail; `10-compatibility-capability-contract.md` §10.9 explicitly lists "retention/archive protocol cụ thể" as deferred). `ADR-039` (Approved) is the most recent artifact to name this exact gap directly, recording it as an unresolved Consequences prerequisite: a version-artifact "must not be treated as satisfying §8.1.1 in full, and must not become a usable `event_contract_ref` target for a real, persisted authoritative event, until an authoritative retention/archive policy is separately established." No policy — at the architecture-semantics level this ADR addresses, or at the concrete-mechanism level §10.9 defers — exists anywhere in this repository today. This gap predates `ADR-039` (it is a direct, general consequence of Chapter 8 §8.1.1 rule 4 and Chapter 10 §10.4.4, both already Locked); `ADR-039` is treated here strictly as the **Feature use-case that most recently exposed** it, not its origin.

**Scope classification — `ADR Required`.** [Chapter 0 §4b](../constitution/00-governance.md) lists both "quyết định ảnh hưởng >1 module" and "khó đảo ngược" as independently sufficient triggers. §8.1.1's own retention/archive requirement applies, by explicit textual design, to **every current and future Referenced Authoritative Artifact platform-wide** — Stream Registry (Chapter 8), Event Contract version-artifacts (`ADR-039`), Input Contracts (`docs/architecture/input-contracts/*.yaml`), Domain Contracts, ADRs, and Constitution chapters themselves — a strictly broader footprint than any single ADR decided in this series so far, definitionally a >1-module decision. It is also hard to reverse: once any artifact is archived, pruned, or has its retention commitment relied upon by a replay/audit/compliance operation under one set of semantics, changing those semantics later requires reinterpreting or re-establishing guarantees for everything already archived under the old rule — the exact class Chapter 0 §4b treats as ADR-required independent of the module-count trigger. This is **not** an ADR merely because `ADR-039` left follow-on work open — `G-ADR-003`/`G-ADR-001`/`G-ADR-004` (`docs/governance/execution-rules.md`) forbid authoring an ADR just to "complete" a prior one, and require running the inflation/scope check first (recorded in full below, per this transaction's own prompt). `ADR-039` is treated here strictly as the exposing use-case; this ADR's own decision content is derived independently from Chapter 8 §8.1.1 and Chapter 10 §10.4.4/§10.9 directly, not from `ADR-039`'s own decision content — `depends_on: []` accordingly.

**Decision:** This ADR fixes the **architecture-level retention/archive semantics** every Referenced Authoritative Artifact must satisfy — the contract any future concrete mechanism (numeric horizon values, storage tier, archival tooling) must be built against — **without inventing that concrete mechanism**, consistent with the requirement/mechanism split Chapter 10 §10.9 already draws and does not override. Artifacts are classified into exactly two storage classes, determined by where their canonical authoritative content actually lives today (not per-artifact-type, avoiding fragmenting semantics per §8.1.1's own general-rule framing):

- **Class G (git-repository-resident):** any artifact whose canonical authoritative content is a file tracked in this git repository — ADRs, Constitution chapters, Domain Contracts, Event Contract version-artifacts (`ADR-039`), Input Contracts. This is every Referenced Authoritative Artifact type that concretely exists in this repository today.
- **Class R (runtime-resident):** any artifact whose canonical authoritative content is recorded as data within the running platform itself, not as a git file — today, only the Stream Registry (recorded via control-stream events, Chapter 8 §8.3.1), which has no running implementation yet.

**Class G retention/archive policy (concrete, effective immediately):** the committed replay/audit horizon for every Class G artifact is **the full lifetime of this git repository's own commit history** — as long as the repository (with complete history, not merely current `HEAD`) is retained, every Class G artifact version ever referenced remains resolvable by commit SHA + path, indefinitely, using infrastructure this repository already runs (no new storage system introduced). "Archival" for Class G is exactly what git already does: a file superseded, renamed, or removed from current `HEAD` remains fully resolvable through prior commits. **Removal — permanently destroying resolvability of any commit or blob that has ever been referenced by an authoritative event, Decision, replay run, cursor, or governance record — is prohibited.** History-rewriting operations (force-push over shared history, `filter-branch`/`filter-repo`, rebase of already-pushed commits, or any operation that would make a previously-resolvable commit/blob unresolvable) are not permitted against any commit range containing a referenced Class G artifact version. This concretely and fully satisfies §8.1.1 rule 4 for every Class G artifact today, using only already-existing repository infrastructure.

**Class R retention/archive policy (architecture-level floor only; mechanism deliberately deferred):** for Class R artifacts, this ADR fixes two architecture-level requirements without picking a concrete number, storage tier, or tooling (both remain Phase-1/mechanism decisions, exactly as §10.9 already defers for the structurally identical Compatibility Result/Policy case — this ADR makes explicit that the same deferral scope applies uniformly to every Class R artifact, not solely Compatibility Result, closing an ambiguity §8.1.1's auto-apply framing left implicit): (a) **fail-closed floor** — whatever committed horizon a Class R artifact's owning chapter/contract eventually declares, it must never be shorter than the longest currently-active binding that still depends on it (no shortening a horizon out from under a live reference); (b) **archival, not removal, by default** — past its committed horizon, a Class R artifact may move to a distinct, documented archive path/mechanism, but must remain resolvable through it; true removal (ending resolvability entirely) is not authorized by this ADR and would require its own separate, bounded, future governed decision — this ADR takes no position on whether that is ever appropriate and defaults to "never" absent one.

**Resolvability while active vs. archived:** for both classes, a correctly-implemented resolver must succeed identically for the same artifact identity (commit SHA/content hash, or `{contract_id, contract_version}`-style pin resolving to one) regardless of whether that identity is currently "active" (within the committed horizon, primary storage) or "archived" (past horizon, archive-tier storage) — archival changes storage locality and potentially latency, never the resolved content, its identity, or whether resolution succeeds. A caller does not need to know in advance which state a historical reference is in for correct resolution to succeed.

**Immutable content-identity preservation:** archival is a storage-locality operation only. It must never alter an artifact's content, hash, or identity (§8.1.1 rule 5); a content-identity mismatch discovered after archival is a policy violation, not an acceptable side effect, for either class.

**Fail-closed behavior when an exact referenced artifact cannot be resolved:** if any consumer — replay, audit, compliance, or a runtime reader — requests resolution of an exact, historically-referenced Referenced Authoritative Artifact identity and that resolution fails for any reason (missing, corrupted, hash-mismatched), whether within or past the committed horizon, this is a **hard failure**: the requesting operation must abort and report the specific unresolvable reference. Silently substituting a "nearest" version, skipping the record, or proceeding under degraded/default semantics is prohibited — the same fail-closed, no-aliasing principle `ADR-039` already established for `contract_id`/`contract_version` path resolution, applied one level up to artifact resolvability in general.

**Canonical policy scope/authority:** this ADR is the canonical architecture authority for retention/archive **semantics** applicable to every current and future Referenced Authoritative Artifact platform-wide. It does not itself become an operational registry/service, does not author `docs/architecture/event-contracts/**` content, and does not implement anything runtime. A future, separate governed decision may author the concrete Class R mechanism (numeric horizon values, storage tier, archival tooling, CI/reporting) when a real running Stream-Registry-class implementation makes that decision non-speculative — the same requirement/mechanism boundary `10-compatibility-capability-contract.md` §10.9 already draws for Compatibility Result/Policy, left undisturbed here, only clarified as to which artifact classes it covers.

**Relationship to Chapter 8 §8.1.1 and Chapter 10 §10.4.4/§10.9:** this ADR is the architecture-level artifact §8.1.1 rule 4's "explicit retention/archive policy" requirement and §10.4.4's identical resolvability/retention distinction point to. It fully resolves that requirement today for Class G (concrete, effective, using existing git infrastructure) and fixes the architecture-level floor/archival-not-removal/fail-closed semantics for Class R without resolving §10.9's own explicitly deferred concrete protocol/format/tooling — this ADR narrows what remains deferred (numbers, storage, tooling) without touching what §10.9 already, correctly, reserves for a later mechanism decision.

**Alternatives considered:**

1. **(A) Architecture-level retention/archive semantics ADR, two storage classes, Class G resolved concretely via existing git infrastructure, Class R floor-only with mechanism deferred (chosen).** Minimum architecture that fully satisfies §8.1.1 rule 4 for every artifact type that concretely exists today (all Class G), without inventing storage vendor/deployment infrastructure for the one artifact type (Stream Registry) that has no running implementation yet; reuses existing repository infrastructure rather than introducing a new one; preserves, rather than overrides, Chapter 10 §10.9's own requirement/mechanism split.
2. **(B) Fully concrete retention/archive protocol authored now — pick actual numeric horizons, storage tiers/vendors, archival tooling for every artifact class.** Rejected — exceeds this architecture decision's proper scope and directly contradicts §10.9's explicit deferral of exactly this ("retention/archive protocol cụ thể... storage/format/schema... tooling, CI gate, báo cáo"); would very likely require rework once real Class R deployment constraints (a system that does not exist yet) are known — premature, hard-to-reverse commitment in the wrong direction.
3. **(C) No dedicated ADR — let each artifact-owning Domain Contract/ADR define its own retention/archive rule independently, ad hoc.** Rejected — §8.1.1 frames retention as a general rule auto-applying to every current and future Referenced Authoritative Artifact, explicitly "không cần lặp lại ở từng mục" (not to be rediscovered per-item); deciding it piecemeal would fragment fail-closed/archival/resolvability semantics across artifact types and would itself independently qualify as ADR-required per-instance under the same >1-module/hard-to-reverse triggers, multiplying transactions instead of resolving the shared prerequisite once.
4. **(D) Governance `docs/MANIFEST.md` as the retention/archive policy owner.** Rejected on the same grounds already established for the structurally identical question in `ADR-038`'s own corrected reasoning and reused in `ADR-039`: `MANIFEST.md`'s current scope (Decision Log; document version/status; ADR lifecycle/supersession; OQ status) has no natural extension to owning a required, every-artifact-class runtime/architecture retention responsibility; `ADR-022`'s own precedent explicitly declined this exact extension without its own dedicated governed decision — this is not that decision, and nothing here makes it one.

No materially better existing-authority option was identified beyond these four; the chosen mechanism (A) was preferred specifically because it fully resolves the requirement for every artifact type that concretely exists today, using only infrastructure already in place, while explicitly declining to invent infrastructure for a system (Class R/Stream Registry) that is not built yet.

**Consequences:** This ADR fixes platform-wide retention/archive semantics for Referenced Authoritative Artifacts only. It does not itself author or modify any `docs/architecture/event-contracts/**` file, does not implement `event_contract_ref`, does not modify `ADR-039` (remains Approved, immutable, unaffected — `P3-ADR039-B-MIN-01` remains accepted/non-blocking, unaffected by this ADR), does not modify any Locked Constitution chapter or any other Approved ADR, does not modify `module-registry.yaml`/`context-map.yaml`, and does not modify production source/tests/tooling. It does not pick a concrete Class R numeric horizon, storage tier, or archival tooling (deliberately deferred, per Alternative B's rejection above). Bounded, separate follow-on work remains: (0) `ADR-039`'s own Consequences item (0) — establishing that an authoritative retention/archive policy exists before any Event Contract version-artifact becomes a usable `event_contract_ref` target — is now satisfied at the architecture-semantics level for Class G by this ADR (Event Contract version-artifacts are Class G); (1) each Class G artifact-owning document/ADR may cite this ADR as its retention/archive authority instead of restating semantics; (2) when a real Stream Registry implementation is built, a separate governed decision must author its concrete Class R mechanism (numeric horizon, storage tier, archival tooling), bound by this ADR's floor/archival-not-removal/fail-closed requirements; (3) `ADR-039`'s own remaining follow-on work (authoring/publishing first `Published` version-artifacts, Feature's own first version snapshots, `event_contract_ref` implementation) is entirely separate, bounded, later work, untouched by this ADR. This ADR does not change Feature Chapter 13 QG evidence, Feature module approval, the Phase 3 Approval Gate, or `LIVE` authorization — all remain exactly as they stood before this transaction, explicitly not granted/not authorized by anything decided here.
