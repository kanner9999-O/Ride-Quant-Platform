# ADR-038: Feature Output Event Contract Compatibility Commitment

> **Bounded Review A correction**, addressed/remediated pending re-review (not self-closed by the correction executor — closure is a Review A re-review determination, never asserted here): `P3-ADR038-A-MAJ-01` — the Decision/Alternatives rationale treated an ungoverned tolerant-reader behavior as established fact (asserting backward-only was "achievable precisely because it only requires a permissive/tolerant reader discipline") and overstated the absence of existing consumer protection (rejecting no-commitment on the ground that `context-aggregator` has "no other governed protection"), when Chapter 10 §10.3.1 explicitly reserves format-specific reader/schema rules to Domain Contract/Phase 1 authority not yet authored, and §10.5 already establishes that an immutable consumer binding is unaffected by a provider publishing a newer contract version. Alternatives 2/3 also overclaimed forward compatibility as impossible for every possible future architecture, rather than for ADR-037's current, as-defined delta specifically. **Corrected:** the `backward-only` decision is preserved, reframed as an explicit **policy commitment** (a requirement the platform adopts) rather than a conclusion derived from assumed reader behavior; actual backward compatibility of any concrete schema delta is now stated as requiring evaluation against authoritative reader/format rules once those rules exist, never assumed while absent; the immutable-binding principle (§10.5: publishing a newer contract does not alter a consumer's existing pinned binding) is now cited to correctly frame WHAT backward-only actually protects — a consumer that *intentionally* advances/upgrades its binding across versions claimed compatible, not a baseline the current pinned consumer otherwise lacks; Alternative 4's rejection now rests on the absence of a cross-version compatibility guarantee for advancing consumers, not on a false "zero protection" claim; Alternatives 2/3 are narrowed to ADR-037's current required/no-fallback delta as currently defined, not a categorical claim about every possible future schema-evolution architecture. **No change to:** the `backward-only` decision itself, the `ADR_REQUIRED` scope classification, the real `>1`-module impact finding, ADR-037 (unchanged/Approved), `depends_on: [ADR-037]`, the commitment/classification/Compatibility-Result distinction, the absence of any evaluator/grant/result mechanism, or any lifecycle/QG state. `version: "0.1"`, `status: Draft` unchanged — no implementation, no Product Owner approval.
>
> `P3-ADR038-A-MAJ-01: REMEDIATED — PENDING BOUNDED REVIEW A RE-REVIEW`

**Context:** [ADR-037](./ADR-037.md) (Approved v0.1) authorized `computation_dependency_content_evidence` as a new required, no-fallback payload value on `FeatureComputed`/`FeatureFactInvalidated`. Its own "Compatibility/versioning under Chapter 10" section, corrected under `P3-ADR037-A-MAJ-01`, established that a schema delta can only be classified breaking-or-not **relative to a compatibility direction the publishing contract explicitly declares** ([`10-compatibility-capability-contract.md`](../constitution/10-compatibility-capability-contract.md) §10.3.1), and that no such declaration currently exists for the Feature Output Event Contracts (`feature-computed`/`feature-fact-invalidated`) — recording that absence as a named, required downstream prerequisite (ADR-037 Consequences, step (1)) rather than inventing one. This ADR resolves that named prerequisite: it decides the Feature Output Event Contracts' own compatibility commitment. It does not re-litigate any part of ADR-037's own decision content.

**Ground truth, independently confirmed at the current boundary:** `feature.md`, `contracts.py`, and every Event Contract-adjacent artifact searched declare no required backward/forward compatibility direction for `feature-computed`/`feature-fact-invalidated` — confirmed absent, not merely undiscovered (same finding ADR-037 already established, re-verified here). `module-registry.yaml` registers `context-aggregator.depends_on` including `feature-engine`, a genuine, current module dependency edge — not a hypothetical future one. [`context.md`](../domain/context.md) §7.3/§8 confirms `context-aggregator` directly consumes both `FeatureComputed` and `FeatureFactInvalidated` (pinning `required_volatility_metric_feature_definition_version`/`required_directional_persistence_metric_feature_definition_version`/`required_distance_to_last_confirmed_swing_feature_definition_version` per role) to build `MarketContextSnapshot`. `feature-engine` is these two Event Contracts' sole writer authority. Separately, direct inspection of this repository's own history for these exact two Event Contracts shows three consecutive Approved ADRs — [ADR-034](./ADR-034.md) (`invalidation_cause`), [ADR-035](./ADR-035.md) (`computation_cursor`), ADR-037 (`computation_dependency_content_evidence`) — each adding one new **required, no-fallback** payload value, with no field ever removed, renamed, retyped, or reinterpreted. This is the established evolutionary pattern for these events, not a one-time event.

**Scope classification — `ADR Required`.** This is not a gap-implies-ADR inference: Chapter 10 §10.3.1 defines the valid choice space for a compatibility commitment (backward-only / forward-only / bidirectional / explicit no-commitment) and mandates that every published contract declare one, but does not itself select a value for any specific contract — that selection is a genuine semantic decision this repository has not yet made for Feature's own events. No existing alignment, evaluator grant, or configuration resolves it (confirmed above). [Chapter 0 §4b](../constitution/00-governance.md)'s ">1 module" trigger is independently sufficient, confirmed disjunctive by the same repeated Approved-ADR precedent ADR-034/035/037 each already relied on (ADR-025's disjunctive reading): `feature-engine` publishes `FeatureComputed`/`FeatureFactInvalidated`; `context-aggregator` consumes both (confirmed edge, `module-registry.yaml` + `context.md`, above) — a compatibility commitment governing what future schema evolution may assume about that already-active consumer relationship affects more than one module by construction.

**Decision:** The Feature Output Event Contracts (`feature-computed`, `feature-fact-invalidated`) commit to **backward compatibility only** — *"consumer CŨ vẫn đọc/validate đúng dữ liệu MỚI"* (§10.3.1). This is an explicit **policy commitment this ADR adopts**, not a conclusion derived from any assumed reader behavior: it obligates the platform to evolve these two Event Contracts only in ways that a consumer who *intentionally* binds to, or advances its pinned reference to, a later contract version claimed compatible can correctly read/validate — it does not itself assert that any concrete schema delta already satisfies this, and it does not assert or require any particular unknown-field-tolerance behavior of any consumer's reader.

**Reader/format rules govern actual compatibility — not assumed here.** §10.3.1 reserves format-specific compatibility rules (JSON Schema, Avro, Protobuf, or an equivalent) to Domain Contract/Phase 1 authority: *"Quy tắc theo từng format cụ thể... thuộc Domain Contract/Phase 1 — Constitution chỉ khóa semantic trên."* No such rule currently exists for the Feature Output Event Contracts. Whether a *concrete* schema delta (e.g. a specific required-field addition) actually preserves backward compatibility under this commitment therefore cannot be evaluated, and is not evaluated here, until that Domain Contract/Phase-1 reader/format policy exists — unknown-field tolerance is never assumed while it is absent. Establishing that policy is a separate, named downstream Domain Contract alignment prerequisite (see Consequences), not decided or inferred by this ADR.

**What this commitment protects — and what it does not.** [`10-compatibility-capability-contract.md`](../constitution/10-compatibility-capability-contract.md) §10.5 already establishes that a provider publishing a newer contract version is not itself a trigger against an existing binding: *"Nếu consumer vẫn pin một immutable reference cũ thì binding của nó không đổi, và sự tồn tại của version mới không làm activation cũ trở nên stale"* (if a consumer still pins an old immutable reference, its binding does not change, and the existence of a newer version does not make the old binding stale) — `Consumer pin Contract v2 · Provider publish Contract v3 → binding vẫn là v2 → KHÔNG revalidate activation cũ`. A consumer that never advances its pinned reference is therefore already unaffected by any later Feature Output Event Contract evolution, with or without this ADR. **Backward-only exists to protect the different, real scenario this commitment is actually for: a consumer that *does* intentionally bind or upgrade to a later contract version it is told is compatible** — for that consumer, this commitment obligates the platform not to have broken it. Forward compatibility (new consumer reading old data) remains **not committed** — left explicitly undeclared-as-a-commitment, distinct from asserting it holds or fails.

**Distinguishing three separate Chapter-10 concepts (required by this decision, decided here only for the first):**

1. **Compatibility commitment (§10.3.1) — decided by this ADR.** A contract-level declaration of which direction(s), if any, the published contract requires. This is the sole subject of this ADR.
2. **Compatibility classification of a concrete schema delta (§10.3.1's minimal-classification principles) — NOT decided here.** Given a specific schema change (e.g. ADR-037's own `computation_dependency_content_evidence` addition), whether that specific delta satisfies the commitment this ADR establishes is a separate, per-change determination. This ADR does not classify ADR-037's delta, does not amend ADR-037, and does not itself conclude whether ADR-037's field addition is or is not compatible under the commitment decided here — that classification is follow-on work.
3. **Compatibility Result (§10.4) — NOT decided here, and out of scope entirely.** A Compatibility Result is a heavy, immutable, provenance-pinned artifact requiring a registered, granted evaluator (Declaration → Grant → Enforcement → Verification, Chapter 9 §9.6) and pinning subject/input/policy-version/grant/evaluation-boundary evidence in full (§10.4.1). This ADR creates no evaluator, grant, or policy-registry mechanism, and issues no Compatibility Result for any subject.

**Alternatives considered:**

1. **Backward-only (chosen).** Adopted as an explicit policy commitment protecting a consumer (such as `context-aggregator`, the one real, already-registered dependency confirmed above) that intentionally advances its binding to a later, claimed-compatible Feature Output Event Contract version — without promising a direction (forward) that ADR-037's own current, as-defined delta cannot satisfy. This is a forward-looking obligation on how the contract may evolve, not a claim that unknown-field-tolerant reader behavior already exists or is assumed anywhere today.
2. **Forward-only.** Rejected for ADR-037's current, as-currently-defined delta: `computation_dependency_content_evidence` is required with no fallback, so a new consumer cannot validate that requirement against old data where the value is genuinely absent, absent an authorized migration/fallback mechanism this repository has not adopted. This rejection is scoped to the delta as it currently stands, not asserted as impossible for every possible future Feature schema-evolution architecture — a future governed decision could adopt a migration/fallback discipline that makes forward compatibility achievable for later deltas; that is not this ADR's decision to make now.
3. **Bidirectional.** Rejected on the same currently-scoped ground as forward-only (bidirectional requires both directions; the forward leg is not satisfiable by ADR-037's current delta without an authorized migration/fallback mechanism), compounded by the strictly larger commitment surface.
4. **Explicit no-compatibility commitment.** Not constitutionally invalid — §10.3.1 explicitly permits a contract to commit to no direction, provided the choice is itself an explicit, auditable declaration, never an absent field. Rejected not because the current, already-pinned `context-aggregator` binding otherwise lacks protection — per §10.5, an existing pinned binding is already unaffected by later contract publication regardless of this ADR's decision — but because no-commitment provides **no cross-version compatibility guarantee for a consumer that intentionally advances its binding** to a later Feature Output Event Contract version. Since a real, registered consumer of these events exists, and this platform's own evolutionary practice for them anticipates future required-field additions, leaving that advancing-consumer scenario entirely unprotected would not reflect the platform's actual dependency topology or Chapter 10 §10.7's downstream-impact-assessment purpose.

**ADR-022 note (precedent only, not authority for this decision):** [ADR-022](./ADR-022.md) decided a backward-only commitment for Package 1.4's `command-query-api-surface`, a structurally different published contract (command/query surface, not an authoritative event stream) governed by its own context. ADR-022's specific choice is cited here only as process/precedent evidence that this repository has previously resolved an analogous "real consumer + evolving contract" situation the same way — it is not treated as binding authority for Feature's own Event Contracts, and this ADR's reasoning above is derived independently from Feature's own consumer topology and evolutionary history, not inherited from ADR-022's decision content.
