# ADR-038: Feature Output Event Contract Compatibility Commitment

**Context:** [ADR-037](./ADR-037.md) (Approved v0.1) authorized `computation_dependency_content_evidence` as a new required, no-fallback payload value on `FeatureComputed`/`FeatureFactInvalidated`. Its own "Compatibility/versioning under Chapter 10" section, corrected under `P3-ADR037-A-MAJ-01`, established that a schema delta can only be classified breaking-or-not **relative to a compatibility direction the publishing contract explicitly declares** ([`10-compatibility-capability-contract.md`](../constitution/10-compatibility-capability-contract.md) §10.3.1), and that no such declaration currently exists for the Feature Output Event Contracts (`feature-computed`/`feature-fact-invalidated`) — recording that absence as a named, required downstream prerequisite (ADR-037 Consequences, step (1)) rather than inventing one. This ADR resolves that named prerequisite: it decides the Feature Output Event Contracts' own compatibility commitment. It does not re-litigate any part of ADR-037's own decision content.

**Ground truth, independently confirmed at the current boundary:** `feature.md`, `contracts.py`, and every Event Contract-adjacent artifact searched declare no required backward/forward compatibility direction for `feature-computed`/`feature-fact-invalidated` — confirmed absent, not merely undiscovered (same finding ADR-037 already established, re-verified here). `module-registry.yaml` registers `context-aggregator.depends_on` including `feature-engine`, a genuine, current module dependency edge — not a hypothetical future one. [`context.md`](../domain/context.md) §7.3/§8 confirms `context-aggregator` directly consumes both `FeatureComputed` and `FeatureFactInvalidated` (pinning `required_volatility_metric_feature_definition_version`/`required_directional_persistence_metric_feature_definition_version`/`required_distance_to_last_confirmed_swing_feature_definition_version` per role) to build `MarketContextSnapshot`. `feature-engine` is these two Event Contracts' sole writer authority. Separately, direct inspection of this repository's own history for these exact two Event Contracts shows three consecutive Approved ADRs — [ADR-034](./ADR-034.md) (`invalidation_cause`), [ADR-035](./ADR-035.md) (`computation_cursor`), ADR-037 (`computation_dependency_content_evidence`) — each adding one new **required, no-fallback** payload value, with no field ever removed, renamed, retyped, or reinterpreted. This is the established evolutionary pattern for these events, not a one-time event.

**Scope classification — `ADR Required`.** This is not a gap-implies-ADR inference: Chapter 10 §10.3.1 defines the valid choice space for a compatibility commitment (backward-only / forward-only / bidirectional / explicit no-commitment) and mandates that every published contract declare one, but does not itself select a value for any specific contract — that selection is a genuine semantic decision this repository has not yet made for Feature's own events. No existing alignment, evaluator grant, or configuration resolves it (confirmed above). [Chapter 0 §4b](../constitution/00-governance.md)'s ">1 module" trigger is independently sufficient, confirmed disjunctive by the same repeated Approved-ADR precedent ADR-034/035/037 each already relied on (ADR-025's disjunctive reading): `feature-engine` publishes `FeatureComputed`/`FeatureFactInvalidated`; `context-aggregator` consumes both (confirmed edge, `module-registry.yaml` + `context.md`, above) — a compatibility commitment governing what future schema evolution may assume about that already-active consumer relationship affects more than one module by construction.

**Decision:** The Feature Output Event Contracts (`feature-computed`, `feature-fact-invalidated`) commit to **backward compatibility only** — *"consumer CŨ vẫn đọc/validate đúng dữ liệu MỚI"* (§10.3.1): an already-deployed consumer built to this contract's current declared shape must continue to correctly read/validate events produced under a later, compatible-additive version of the contract. Forward compatibility (new consumer reading old data) is **not committed** — left explicitly undeclared-as-a-commitment, distinct from asserting it holds or fails.

**Distinguishing three separate Chapter-10 concepts (required by this decision, decided here only for the first):**

1. **Compatibility commitment (§10.3.1) — decided by this ADR.** A contract-level declaration of which direction(s), if any, the published contract requires. This is the sole subject of this ADR.
2. **Compatibility classification of a concrete schema delta (§10.3.1's minimal-classification principles) — NOT decided here.** Given a specific schema change (e.g. ADR-037's own `computation_dependency_content_evidence` addition), whether that specific delta satisfies the commitment this ADR establishes is a separate, per-change determination. This ADR does not classify ADR-037's delta, does not amend ADR-037, and does not itself conclude whether ADR-037's field addition is or is not compatible under the commitment decided here — that classification is follow-on work.
3. **Compatibility Result (§10.4) — NOT decided here, and out of scope entirely.** A Compatibility Result is a heavy, immutable, provenance-pinned artifact requiring a registered, granted evaluator (Declaration → Grant → Enforcement → Verification, Chapter 9 §9.6) and pinning subject/input/policy-version/grant/evaluation-boundary evidence in full (§10.4.1). This ADR creates no evaluator, grant, or policy-registry mechanism, and issues no Compatibility Result for any subject.

**Alternatives considered:**

1. **Backward-only (chosen).** Protects the one real, already-registered consumer dependency (`context-aggregator`, confirmed above) against exactly the class of change this repository has already used three consecutive times for these events — additive, required, no-fallback fields — without promising a direction (forward) that is structurally undischargeable given that same established pattern (a required field genuinely absent from older data cannot be validated against a schema that now requires it, regardless of reader policy — ADR-037's own already-established finding). Backward-only is achievable precisely because it only requires a permissive/tolerant reader discipline on the consumer side (ignore fields not recognized), never requiring the old-shaped data itself to satisfy a newer required-field set.
2. **Forward-only.** Rejected — structurally undischargeable given the established evolutionary pattern for these two Event Contracts. A new consumer reading old, pre-required-field data cannot validate a required, no-fallback element that is genuinely absent from that data; committing to this direction would be a promise this repository could not keep without abandoning the required-no-fallback-field evolution style ADR-034/035/037 already established, which is not this ADR's decision to make.
3. **Bidirectional.** Rejected on the same structural ground as forward-only (bidirectional requires both directions; the forward leg is undischargeable), compounded by the strictly larger commitment surface.
4. **Explicit no-compatibility commitment.** Not constitutionally invalid — §10.3.1 explicitly permits a contract to commit to no direction, provided the choice is itself an explicit, auditable declaration, never an absent field. Rejected here specifically because a real, already-registered consumer exists (`context-aggregator`) with no other governed protection for its integration continuity — declaring no commitment for a contract that genuinely has an active, registered consumer would supply that consumer nothing to rely on and would not reflect the platform's actual current dependency topology, undermining Chapter 10 §10.7's own downstream-impact-assessment purpose for a dependency edge that already exists, not a hypothetical one.

**ADR-022 note (precedent only, not authority for this decision):** [ADR-022](./ADR-022.md) decided a backward-only commitment for Package 1.4's `command-query-api-surface`, a structurally different published contract (command/query surface, not an authoritative event stream) governed by its own context. ADR-022's specific choice is cited here only as process/precedent evidence that this repository has previously resolved an analogous "real consumer + evolving contract" situation the same way — it is not treated as binding authority for Feature's own Event Contracts, and this ADR's reasoning above is derived independently from Feature's own consumer topology and evolutionary history, not inherited from ADR-022's decision content.

**Consequences:** This ADR resolves the Feature Output Event Contract compatibility-commitment prerequisite ADR-037 named. It does not itself amend `feature.md`, does not modify ADR-037, does not add the `computation_dependency_content_evidence` payload field, does not mint any Event Contract/schema version, does not create a Compatibility Result or any evaluator/grant/policy-registry mechanism, and does not modify production source/tests/tooling. Bounded, separate follow-on work remains: (1) classifying ADR-037's own `computation_dependency_content_evidence` schema delta against the backward-only commitment decided here (a compatibility-classification exercise, §10.3.1, distinct from this ADR's own commitment decision); (2) the `feature.md` amendment and Event Contract/schema version minting ADR-037's own Consequences already named; (3) should a future governed decision ever require issuing a formal Compatibility Result for a specific consumer/subject, that decision must separately establish the evaluator/grant chain Chapter 10 §10.4 requires — nothing here authorizes or pre-empts that. This ADR does not change ADR-034's decision, ADR-035's decision, ADR-037's decision, Chapter 8's canonical `replay_cursor`, the module dependency graph, or any ownership boundary — Structure/Raw-Regime/Context ownership, `module-registry.yaml`'s registered edges, and Chapter 8 (Locked) are all unaffected and unreferenced beyond the already-existing `feature-engine`/`context-aggregator` edge cited as evidence. `EVID-05(a)`'s `SATISFIED` disposition and `EVID-05(b)`'s `OPEN` status are both unaffected and unrevisited by this ADR.
