**Context:** [`08-event-model.md`](../constitution/08-event-model.md) §8.2.5 requires every authoritative event to pin `event_contract_ref: {contract_id, contract_version}` to an **exact, immutable Event Contract snapshot** — deliberately independent of `schema_version` (payload schema may repeat across contract versions; `event_class`/`allowed_streams`/`merge_constraints` do not). §8.1.1 additionally requires every Referenced Authoritative Artifact — Event Contract included, named explicitly in its own taxonomy — to be: **versioned**; **immutable once referenced**; **identifier non-reused**; **persistently resolvable through the committed replay/audit horizon**; and **verifiable by content identity**.

**Ground truth, independently confirmed at the current boundary:** Event Contract semantics (payload shape, invariants, `event_class`-adjacent description) are currently embedded directly inside each owning Domain Contract's own prose/YAML (`feature.md` §3/§4, and identically in `candle.md`/`swing.md`/`structure.md`/`regime.md` for their own events) — every one of them declares `event_contract_ref: {contract_id, contract_version}` as a **required envelope field**, and **not one of them pins a concrete `contract_version` value anywhere**. [`context-map.yaml`](../domain/context-map.yaml) pins `contract_id` only, never `contract_version`, for every `published_language` relationship it records (`feature-computed`, `feature-fact-invalidated`, and every other cross-context contract reference). No dedicated Event Contract registry/artifact directory exists in this repository (confirmed by direct search). `feature.md` v0.6's own text records exactly this gap for its own two events, explicitly deferring resolution — the same pattern independently confirmed here across every current Domain Contract, not a Feature-specific problem. Test-only fixture constants (e.g. a hardcoded `"fv1"`-shaped string used only to satisfy a function signature in test setup) are not, and have never been, cited anywhere as authoritative — the owning engine's own construction code requires this value be caller-supplied precisely because it is not authorized to invent one.

**Scope classification — `ADR Required`.** [Chapter 0 §4b](../constitution/00-governance.md) lists both "quyết định ảnh hưởng >1 module" and "khó đảo ngược" as independently sufficient triggers. `event_contract_ref` is a mandatory field on **every** authoritative event **any current or future module** appends (§8.2.5 applies platform-wide, not per-module) — a canonical resolution mechanism for it is definitionally a >1-module decision, strictly broader than any single producer/consumer edge (e.g. `feature-engine`/`context-aggregator`, ADR-038's own narrower footprint). It is also hard to reverse: once real authoritative events begin persisting `event_contract_ref` values under whichever mechanism is chosen, changing that mechanism later requires reinterpreting or migrating every historical event's own reference — the exact class of decision Chapter 0 §4b treats as ADR-required independent of the module-count trigger. This is **not** an ADR merely because `ADR-037`/`ADR-038` left follow-on work open — `G-ADR-003`/`G-ADR-001` (`docs/governance/execution-rules.md`) forbid authoring an ADR just to "complete" a prior one by default. `ADR-037`/`ADR-038` are treated here strictly as the **Feature use-case that exposed** an already-platform-wide gap (confirmed above to predate and extend beyond both) — this ADR's own decision content is derived independently from Chapter 8 §8.1.1/§8.2.5 and Chapter 10 directly, not from `ADR-037`/`ADR-038`'s own decisions.

**Decision:** The canonical authority for an Event Contract's exact, immutable, versioned snapshot is a **dedicated, per-`{contract_id}`, per-`{contract_version}` artifact file**, one file per exact published version, living under `docs/architecture/event-contracts/<contract_id>/<contract_version>.yaml` — the same "one dedicated file per instance, under a named `docs/architecture/` subdirectory" pattern this repository already uses for Feature-scoped Input Contracts (`docs/architecture/input-contracts/*.yaml`), applied here to a different, previously-unaddressed artifact class rather than inventing a new pattern. Each such file is the **one complete, self-contained authoritative snapshot** of that exact Event Contract version — not a pointer or a thin index into some other document.

```yaml
# docs/architecture/event-contracts/<contract_id>/<contract_version>.yaml — illustrative shape only,
# not authored by this ADR (see Boundaries)
contract_id: <matches the canonical contract concept ID the owning Domain Contract already declares
               as its own `id:`, e.g. feature-computed>
contract_version: <this exact snapshot's own identifier, e.g. v1.0 — major.minor, monotonically
                    increasing per contract_id, chosen at publication time>
event_class: <inlined in full at publication time; for candle/swing/structure/regime/feature this
               field does not yet exist in the owning Domain Contract today and must be governed-
               authored, not mechanically copied, before a first version can Publish>
allowed_streams: <inlined in full at publication time; same governed-authoring requirement as
                   event_class above — absent from every current Domain Contract, not just Feature's>
merge_constraints: <inlined in full at publication time; same governed-authoring requirement as
                     event_class above — absent from every current Domain Contract, not just Feature's>
payload_shape: <inlined in full at publication time — the exact field-by-field payload structure
                 this contract_version defines, not a pointer to any other document>
payload_semantics_and_invariants: <inlined in full at publication time — what each payload field
                                    means, why it exists, and its complete binding invariants; for
                                    candle/swing/structure/regime/feature this is governed-authored
                                    from the owning Domain Contract's current §3/§4 content at
                                    publication time, not merely referenced by pointer>
provenance: <optional citation back to the owning Domain Contract's own §3/§4-equivalent section,
             at the exact commit this snapshot was drafted from — recorded for drafting-history
             traceability ONLY; never required to interpret this Published snapshot's own meaning,
             which is fully self-contained above>
status: Draft | Published   # Published = frozen, immutable, Referenced Authoritative Artifact
```

**Canonical authority/source (fixes `P3-ADR039-A-MAJ-01`, round 2):** the **version-artifact file itself**, once `Published`, is the sole authority for that exact Event Contract version's `event_class`/`allowed_streams`/`merge_constraints`, **and** its full `payload_shape`/`payload_semantics_and_invariants` — every one of these inlined directly in the artifact, not referenced by pointer — consistent with Chapter 8 §8.3.1's own authority table (*"Event class / payload / semantic / stream eligibility → Event Contract"*). A reader resolving a historical Event Contract version's own meaning at replay/audit time never needs to separately consult the owning Domain Contract, for payload shape/invariants or for anything else — the artifact is genuinely self-contained, not merely for its envelope fields. The owning **Domain Contract** (`feature.md`, `candle.md`, etc.) retains authority over broader domain concepts and ubiquitous language, and serves as the **drafting workspace** a version snapshot is authored FROM prior to publication, cited in the artifact only via the `provenance` field — a drafting-history citation, **never** a runtime or interpretive dependency of the Published snapshot's own meaning. The Domain Contract is not itself a Referenced Authoritative Artifact for a specific historical Event Contract version, and it continues to be edited in place across its own document-version history (§8.1.1 rule 2 immutability does not apply to it). Publishing a version-artifact's `event_class`/`allowed_streams`/`merge_constraints`/`payload_shape`/`payload_semantics_and_invariants` for the first time is **governed authoring of new content**, not a mechanical transcription — `event_class`/`allowed_streams`/`merge_constraints` do not currently exist for `candle`/`swing`/`structure`/`regime`/`feature` at all, and even where payload shape/invariants prose already exists in a Domain Contract today, inlining it into a Published version-artifact is itself a governed authoring/review act, not a copy-paste, since the artifact's own copy becomes the immutable authority from that point forward.

**Resolution — deterministic path function, no new registry service:** `{contract_id, contract_version}` resolves to `docs/architecture/event-contracts/<contract_id>/<contract_version>.yaml` **directly, by path** — exactly as `{ADR-id}` already resolves to `docs/adr/ADR-<NNN>.md` today, with no separate lookup table or runtime resolver component required. This is deliberately the *minimum* new authority: no new service, no new evaluator/grant/policy-registry mechanism (Chapter 10 §10.4's own evaluator machinery is untouched and unreferenced by this decision), no new runtime dependency beyond what §8.2.5 already mandated every event carry.

**Canonical path/version grammar (fixes `P3-ADR039-A-MIN-01`; version-token shape fixed by `P3-ADR039-A-MAJ-03`):** `contract_id` reuses the owning Domain Contract's existing `id:` convention verbatim (lowercase, hyphen-separated; no new rule introduced). `contract_version` is restricted to the literal pattern `v<major>.<minor>` — `v` followed by two positive-integer-or-zero components separated by a single `.`, each with no leading zero (`v1.0`, `v1.1`, `v2.0`, ...; a bare integer form like `v1` is **no longer valid** under this grammar, superseding round 1's `v<integer>` form). This is the **minimum canonical form** able to carry Chapter 10 §10.3's own major-vs-non-breaking distinction, which a bare integer cannot express: a `contract_id`'s first ever `Published` version is always `v1.0`; a subsequent **breaking** change (per Chapter 10 §10.3/§10.3.1's own already-Locked classification, evaluated against whatever `compatibility_commitment` the owning Domain Contract has declared) is published as a new version-artifact whose major component is incremented by exactly `1` and whose minor component resets to `0`; a subsequent **non-breaking**, contract-surface-evolving change is published as a new version-artifact whose minor component is incremented by exactly `1`, major unchanged. No other transition is valid — major and minor never both change in one step, and neither ever decreases. Resolution is **pure literal string substitution** into the path template: no case-folding, no normalization, no alias table, and no ambiguity in how `major`/`minor` map to path segments (the full `v<major>.<minor>` token is one path segment, never split across two). An input that does not already match this exact grammar (wrong case, a bare integer, three-plus components, a leading zero on either component, `.`/`/`/traversal characters beyond the single required `.` separator) fails closed — it is not "helpfully" resolved to the nearest valid file, since doing so would itself create alias ambiguity the direct-path mechanism is chosen specifically to avoid. `contract_version` remains an **ordering/legibility identifier only**; it is categorically distinct from, and not a substitute for, `schema_version` (its own separately-tracked axis, unchanged — see below) or the version-artifact file's own git blob/content-hash identity (§8.1.1 rule 5, satisfied separately — see below).

**Immutability and identifier non-reuse:** governed by the identical discipline this repository already applies to ADRs ([Chapter 11](../constitution/11-adr-process.md) §11.3): a version-artifact file transitions `Draft` → `Published`; from the `Published` boundary forward it is immutable byte-for-byte — no in-place edits, no silent content changes under the same `contract_version` identifier. A `contract_version` identifier, once used for a `Published` snapshot, is **never** reassigned to different content — evolving the contract always means authoring a **new** file under a **new** `contract_version`, never editing the old one (§8.1.1 rules 2/3, satisfied directly by construction).

**Verifiable content identity:** the git blob hash of the exact version-artifact file — the same mechanism already used, throughout this repository's own governance history, for every other Referenced Authoritative Artifact (ADRs, Constitution chapters, design candidates). No new hashing/serialization scheme is introduced.

**Replay/audit retention and resolvability (fixes `P3-ADR039-A-MAJ-02`):** §8.1.1 rule 4 requires persistent resolvability through the committed replay/audit horizon, **with an explicit retention/archive policy past that horizon**. No such platform-wide retention/archive policy currently exists for ADRs, Domain Contracts, or any other artifact class — Chapter 10 §10.9 explicitly lists "retention/archive protocol cụ thể cho compatibility result và artifact" as deferred, out of Constitution scope, for Phase 1. This ADR does **not** invent that policy, and does **not** claim Option A already inherits a working one from elsewhere in the platform, since none exists to inherit. Consequently: version-artifact files may be authored, reviewed, and `Published` under this mechanism today (the git-repository-resident, commit-addressable part of rule 4 is satisfied now, identically to every other artifact this repository already tracks this way), but a version-artifact **must not be treated as satisfying §8.1.1 in full, and must not become a usable `event_contract_ref` target for a real, persisted authoritative event, until an authoritative retention/archive policy is separately established** through its own governed decision. This is a fail-closed gap, not a silently-inherited guarantee.

**Ownership boundary vs. `schema_version` — axes remain independent, per §8.2.5 (unchanged, not redefined):** this ADR supplies the missing resolution mechanism for `event_contract_ref.contract_version` only. It does not touch, redefine, or provide an equivalent mechanism for `schema_version` — that remains its own, separately-tracked axis, exactly as §8.2.5 already fixes (*"schema_version có thể giữ nguyên qua nhiều Event Contract version"*). Conflating the two, or treating this ADR as having resolved `schema_version`'s own resolution question, would repeat the exact category error §8.2.5 already warns against one level down.

**First authoritative version, when no prior published snapshot exists for a `contract_id`:** the first `Published` version-artifact file for a given `contract_id` is authored, reviewed, and Product-Owner-decided through the **same governance process already used for the owning Domain Contract itself** (Draft → Review A/Independent Review B → Product Owner decision) — no new evaluator, grant, or self-certification path is introduced. Because `event_class`/`allowed_streams`/`merge_constraints` do not yet exist in any current Domain Contract's own text, this first-publication step is **governed authoring of genuinely new content**, not a mechanical extraction — the review must evaluate that content on its own merits, not merely check it against a pre-existing Domain Contract source (there isn't one yet). Its `contract_version` identifier is fixed at `v1.0` for the first entry in that `contract_id`'s own version lineage, per the grammar fixed above — no other value is valid for a first publication. This ADR does not itself author or Publish any concrete Event Contract snapshot (see Boundaries) — it fixes the *mechanism*, not any specific `feature-computed`/`feature-fact-invalidated` version identity.

**Later breaking/non-breaking evolution — governed entirely by already-Locked Chapter 10, not redefined here:** every subsequent change to a `contract_id`'s `event_class`/`allowed_streams`/`merge_constraints`/payload shape is published as a **new**, immutable version-artifact file, never an edit to a prior one. Whether that change is breaking or non-breaking is determined at publication time by Chapter 10 §10.3/§10.3.1's own already-Locked classification rules, applied against whatever `compatibility_commitment` the owning Domain Contract has declared for that `contract_id` (e.g. `feature.md` v0.6's own `compatibility_commitment: backward_only` for `feature-computed`/`feature-fact-invalidated`) — this ADR invents no parallel breaking/non-breaking classification scheme, only the mechanical consequence for `contract_version`: a **breaking** result increments the major component by `1` and resets minor to `0` (e.g. `v1.3` → `v2.0`); a **non-breaking** result increments the minor component by `1`, major unchanged (e.g. `v1.3` → `v1.4`). This ADR only fixes where the resulting snapshot is durably recorded and how it resolves.

**Alternatives considered:**

1. **(A) Dedicated immutable/versioned Event Contract artifacts, canonical lookup by `{contract_id, contract_version}` (chosen).** Satisfies §8.1.1 rules 1/2/3/5 directly and by construction; rule 4 (persistent resolvability **with an explicit retention/archive policy**) is satisfied only in part today — the artifact is git-repository-resident and commit-addressable now, but the explicit retention/archive policy itself does not yet exist platform-wide (see the Replay/audit retention paragraph above) and remains an open prerequisite before this mechanism is fully §8.1.1-compliant. Reuses an already-established repository pattern (`docs/architecture/input-contracts/*.yaml`) rather than inventing a new one; introduces no new runtime service, evaluator, or grant mechanism; makes the version-artifact the one complete, self-contained authoritative snapshot rather than splitting authority across two documents.
2. **(B) Versioned immutable Event Contract snapshots retained inside/alongside the owning Domain Contract, with an exact resolver rule.** Rejected — this repository's own Domain Contracts are edited **in place** across their own version history (a single `feature.md` file has already carried v0.1 through v0.6, each new version rewriting/extending prior sections rather than freezing a separate, independently-resolvable snapshot per version); resolving a specific historical `contract_version` would require git-archaeology against commit history rather than a direct, deterministic path function, and — more fundamentally — a Domain Contract's own document version is a **single axis covering the whole document** (every event type and algorithm section it owns), while §8.2.5 requires **independent** version axes **per `contract_id`**; using the Domain Contract's own version as a stand-in would repeat, one level up, the exact "wrong field used as a version proxy" mistake §8.2.5 already forbids for `schema_version`.
3. **(C) Git commit/blob/content identity directly as `contract_version`.** Rejected as the sole mechanism — a bare content hash satisfies §8.1.1 rule 5 (verifiable content identity) automatically, but carries no human-legible ordering signal two hashes can be compared to determine "which came first" or "was this a major/minor step" — information Chapter 10 §10.3's own SemVer-equivalent breaking/major-bump signaling directly depends on. It also does not, by itself, resolve *which exact byte range* of a living, in-place-edited Domain Contract the hash should be computed over (the same conflation Option B fails on). The chosen mechanism (A) already incorporates this option's genuinely useful part — a git blob hash still serves as the version-artifact file's own content-identity proof — without inheriting its ordering/scoping weaknesses.
4. **(D) Governance `docs/MANIFEST.md` as runtime Event Contract resolution authority.** Rejected on the same grounds already established for the structurally identical question in [ADR-038](./ADR-038.md)'s own corrected reasoning: `MANIFEST.md`'s current Chapter 0 §5b/§7 scope (Decision Log; document version/status; ADR lifecycle/supersession; OQ status) has no natural extension to serving as a required, at-every-event runtime dependency — an even larger, higher-frequency responsibility here than the content-identity case, since §8.2.5 mandates `event_contract_ref` on literally every authoritative event platform-wide. [ADR-022](./ADR-022.md)'s own precedent (cited there, reused here) explicitly declined to carry MANIFEST-as-canonical-authority forward into runtime-activation territory beyond its own bounded Phase-1-architecture-only scope, reserving any such extension for a dedicated, separate governed decision — this is not that decision, and nothing here makes it one.

No materially better existing-authority option was identified beyond these four; the chosen mechanism (A) was preferred specifically because it introduces the least new authority/infrastructure of the four while coming closest to satisfying all five §8.1.1 conditions — fully on rules 1/2/3/5, and on rule 4 up to the still-open, platform-wide retention/archive-policy prerequisite common to every alternative considered (none of B/C/D resolve that prerequisite either).
