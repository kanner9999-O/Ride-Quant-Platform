## Decision question

Approved `ADR-038`'s `backward_only` commitment applies, in full, to the Feature Output Event
Contracts — `causal_state_dependency_declaration` included; this is not in question and this ADR
creates no exemption from it. The actual question: which Chapter 10 mechanism correctly tests a
concrete `causal_state_dependency_declaration` delta against that commitment — §10.3.1's own
minimal, data-presence-calibrated schema-element classification rules, or §10.3's own general
contract-surface/current-consumer breaking-change test, read together with §10.7's
downstream-impact-assessment requirement?

## Smallest coherent decision surface

This ADR decides only **which Chapter 10 classification mechanism applies** when testing a
`causal_state_dependency_declaration` delta against Approved `ADR-038`'s fully-applicable
`backward_only` commitment, and, by the identical, closed test stated in the Decision below, any
future field introduced under `ADR-048`'s own `declared-state-dependencies`/`per_effect_event_contract`
governance mechanism specifically. It does **not** decide, and leaves entirely to `ADR-039`'s own
existing, unchanged authority or to later, separately-governed work:

- **`ADR-038`'s `backward_only` commitment itself** — unchanged, unexempted, unreopened; it applies
  to the whole Feature Output Event Contract artifact exactly as `ADR-038` already fixed it. This
  ADR decides a classification-mechanism question entirely inside that commitment's own scope, not
  a question about the commitment's existence or reach.
- **`event_class`, `allowed_streams`, `merge_constraints`** — remain governed exactly as `ADR-039`
  already fixed. Not reopened, not narrowed, not redefined.
- **Question (a)** — the platform-wide format-specific reader/schema policy `ADR-037`/`ADR-038`
  already named as missing. This ADR neither selects, sketches, nor requires one.
- `ADR-048`'s own grammar for `causal_state_dependency_declaration` (unchanged).
- Whether `causal_state_dependency_declaration` specifically is ultimately classified
  breaking/non-breaking for Feature's own `v1.0 → v1.1` delta — this ADR fixes the **mechanism** used
  to reach that classification; actually applying it to produce a concrete, certified conclusion for
  Feature's own candidates remains separate, later work (see Consequences).
- Any Candle/Structure/Regime Event Contract's own content.

## Why (a) is not required to resolve (b)

(a) answers a question about DATA: given a declared compatibility direction, how permissively or
strictly does an old/new reader parse event-instance payload bytes it does not fully recognize. (b)
answers a logically prior, orthogonal question for this one field: which Chapter 10 mechanism
correctly tests a delta against the (already-fully-applicable) commitment, given that
`causal_state_dependency_declaration` is never "data" (something any payload-reading consumer ever
encounters) in the first place — confirmed true by direct inspection (Context, above). §10.3.1's own
schema-element rules presuppose a reader parsing payload bytes; they have no defined meaning for a
field no such reader ever sees, so mechanically applying them would answer a question about data
tolerance for a field that raises no data-tolerance question at all. §10.3's own general test asks
instead whether any actual, currently-valid consumer — of event data OR of the artifact document
itself — becomes invalid; that test has a well-defined answer for any field regardless of whether it
is payload, and is therefore the mechanism this field's own nature calls for. Resolving (b) for this
field requires only Chapter 8/Chapter 10's own already-locked structural vocabulary plus direct
inspection of this repository's own real consumers/tooling (Context, above) — never a format-specific
parsing-tolerance policy.

This reasoning is deliberately **not** extended to `event_class`/`allowed_streams`/
`merge_constraints`: `ADR-039` already, explicitly, fixes their own classification treatment — a
rule this ADR does not revisit, weaken, or treat as analogous to this field's own case.

## Alternatives considered

1. **Categorical exemption, generalized to every top-level sibling field of `payload_shape`
   (`event_class`, `allowed_streams`, `merge_constraints`, `causal_state_dependency_declaration`
   alike).** Rejected (this was v0.1's own Decision, corrected here per `ADR050-A-MAJ-01`) —
   directly contradicts `ADR-039`'s own explicit, unqualified text tying `event_class`/
   `allowed_streams`/`merge_constraints` changes to Chapter 10 §10.3/§10.3.1 compatibility-commitment
   classification. A decision cannot simultaneously claim `ADR-039` is unchanged and assert a rule
   that produces the opposite classification outcome for three of the four fields `ADR-039` itself
   already classifies.
2. **Field-level exemption — `causal_state_dependency_declaration` categorically outside
   `compatibility_commitment`'s scope entirely.** Rejected (this was v0.2's own Decision, corrected
   here per `ADR050-A-MAJ-02`) — read against `ADR-038`'s own Decision text ("The Feature Output
   Event Contracts... commit to backward compatibility only," applied to the whole artifact, Ground
   truth above), framing any field as outside that commitment's scope amounts to narrowing an
   Approved ADR's commitment from this Draft candidate, without `ADR-038` ever being touched or
   superseded. It also removes any real test for the field: a field permanently outside the
   commitment's scope could never be found breaking under `ADR-038`, regardless of what a future
   instance of it actually did to real consumers — the opposite of rigor, not merely imprecise
   wording.
3. **(CHOSEN) No exemption — `ADR-038`'s commitment applies in full; the classification mechanism
   used to test compliance is selected by the delta's own nature.** For `causal_state_dependency_declaration`
   (and, by the same closed test, any future field `ADR-048`'s own `declared-state-dependencies`/
   `per_effect_event_contract` governance mechanism introduces): because the field is never
   serialized into any event instance's own payload bytes, §10.3.1's data-presence-calibrated
   schema-element rules do not fit it and are not used; Chapter 10 §10.3's own general
   contract-surface/current-consumer test, read with §10.7's downstream-impact-assessment
   requirement, is used instead — still entirely within, and in service of, `ADR-038`'s own
   fully-applicable commitment. `event_class`/`allowed_streams`/`merge_constraints` remain exactly as
   `ADR-039` already classifies them (unchanged). This resolves (b) for the one field actually in
   question using only already-locked structural vocabulary, real downstream-impact evidence
   (Context above), and no reader/format-tolerance assumption of any kind — and leaves a genuine,
   non-vacuous test in place for every future instance of this same field category.
4. **Mechanically apply §10.3.1's data-presence rules to `causal_state_dependency_declaration`
   anyway, on the theory that `ADR-038`'s commitment must use one single mechanism for every field.**
   Rejected. Would import §10.3.1's "forward compatibility structurally unavailable because the data
   is absent" reasoning onto a field that is never present in any event's own data in the first
   place — a category error, not a stricter or more faithful application of `ADR-038`'s commitment.
   Would also make Chapter 8 §8.2.3's `declared-state-dependencies` mechanism permanently unusable
   for any already-Published Event Contract platform-wide until the large, currently-unscoped
   reader/format-policy work (a) completes — a disproportionate, cascading consequence for a
   mechanism that touches no payload data at all, and not something `ADR-038`'s own text requires.
5. **Merge (b) into (a) — resolve both together via one platform-wide reader/format policy now.**
   Rejected: (a) and (b) are orthogonal axes — (a) concerns reader tolerance for payload bytes; (b)
   concerns which Chapter 10 mechanism tests a non-payload field's compliance with an
   already-fully-applicable commitment. Resolving (a) first would not even answer (b), since (a)'s
   own machinery (JSON Schema/Avro/Protobuf-style unknown-field tolerance rules) has no defined
   meaning for a field that is never serialized. Attempting it now would also be a far larger
   decision than this bounded question requires, contrary to `G-ADR-002`'s "khó đảo ngược, không
   phải chi phí thấp" scoping discipline.

## Decision

**Approved `ADR-038`'s `backward_only` commitment applies, in full, to the entire Feature Output
Event Contract artifact — `causal_state_dependency_declaration` included. No field of any Feature
Output Event Contract is exempt from that commitment.** This ADR creates no exemption and narrows
no Approved ADR's scope.

**What this ADR actually decides: which Chapter 10 mechanism tests a `causal_state_dependency_declaration`
delta against that fully-applicable commitment.** §10.3.1's own minimal-classification sub-rules are
calibrated to elements of **payload data** a consumer's reader actually parses (`thêm element
required không có fallback → breaking`, and its symmetric data-presence reasoning throughout). A
field defined by Approved `ADR-048` as a top-level sibling of `payload_shape`, never nested inside
`payload_shape`/`payload_semantics_and_invariants`, and never serialized into any event instance's
own payload bytes (Ground truth, above) is never encountered by any such reader — applying
§10.3.1's data-presence rules to it would answer a data-tolerance question for a field that raises
no data-tolerance question at all, a mechanical misapplication, not a stricter reading of `ADR-038`.

**The classification mechanism for `causal_state_dependency_declaration` is instead Chapter 10
§10.3's own general breaking-change test, read together with §10.7's downstream-impact-assessment
requirement — both applied entirely within, and in service of, `ADR-038`'s own fully-applicable
commitment:** a change is breaking if it makes a currently-valid consumer invalid. Applied here,
covering both categories of real consumer this field can have (§10.7's own "dependency graph —
consumer nào đang pin cái gì" requirement, extended deliberately to tooling, not only event-data
readers):

- **Event-instance-data consumers.** None exist for this field by construction — it is never
  present in any event instance's own payload, so no data-reading consumer's behavior changes in any
  way (Ground truth, above). Not an assumption of tolerant-reader behavior: a reader cannot fail to
  tolerate bytes that are never there to encounter.
- **The one validator this field has a defined role for** — `context-aggregator`'s own Draft Input
  Contract, already declaring `causal_closure_policy.mode: declared-state-dependencies` for the
  `feature-engine-feature` stream (Ground truth, above). This consumer is not merely unaffected — it
  currently **cannot** satisfy its own already-declared mode for this stream at all, and this
  field's addition is what first makes that satisfiable. Enabling, not breaking.
- **Tooling/validator consumers of the Event-Contract-artifact document itself.** Checked by direct
  code inspection, not assumed tolerant (Ground truth, above):
  `output_contract_resolver.py`/`authority_resolver.py` extract only specific named
  scalars/blocks via targeted prefix-matching and enforce no closed top-level key set; adding this
  field alters none of their extraction targets. No other such tooling exists in this repository.

**Conclusion of applying this mechanism (non-normative preview — see Consequences for why this ADR
does not itself certify it):** no currently-valid consumer, of either category, becomes invalid.
