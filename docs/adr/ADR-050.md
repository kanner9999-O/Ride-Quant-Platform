## Decision question

Does Chapter 10 §10.3.1's `compatibility_commitment` declaration — and the backward/forward
compatibility-classification rules that attach to it — apply to a top-level Event-Contract-artifact
field that is never part of `payload_shape` and never serialized into any event instance's own
payload bytes? Or is such a field categorically outside that commitment's scope, with its own
compatibility classified instead under Chapter 10 §10.3's general consumer-invalidation test?

## Smallest coherent decision surface

This ADR decides only the **categorical scope boundary** of `compatibility_commitment`/§10.3.1 —
which class of Event-Contract-artifact fields it governs. It does **not** decide, and leaves
entirely to later, separately-governed work:

- **Question (a)** — the platform-wide format-specific (JSON Schema/Avro/Protobuf-or-equivalent)
  reader/schema policy `ADR-037`/`ADR-038` already named as missing. This ADR neither selects,
  sketches, nor requires one — see "Why (a) is not required to resolve (b)" below.
- Any specific contract's own `compatibility_commitment` **value** (`ADR-038`'s `backward_only` for
  `feature-computed`/`feature-fact-invalidated` is unchanged, unreopened, unamended).
- `ADR-048`'s own grammar for `causal_state_dependency_declaration` (unchanged).
- Whether `causal_state_dependency_declaration` specifically is ultimately classified
  breaking/non-breaking for Feature's own `v1.0 → v1.1` delta — this ADR fixes the **rule** that
  governs that classification; applying it to produce a concrete conclusion for Feature's own
  candidates remains separate, later work (see Consequences).
- Any Candle/Structure/Regime Event Contract's own content.

## Why (a) is not required to resolve (b)

(a) answers a question about DATA: given a declared compatibility direction, how permissively or
strictly does an old/new reader parse event-instance payload bytes it does not fully recognize. (b)
answers a logically prior, orthogonal question: whether a given field is "data" (something any
reader of event instances ever encounters) **at all**. A field that is never present in any event
instance's own bytes — confirmed true of `causal_state_dependency_declaration` by direct inspection
(Context, above) — cannot be "tolerantly" or "strictly" read by any payload-parsing consumer, because
no such consumer's parsing logic ever encounters it in the first place. Resolving (b) therefore
requires only Chapter 8/Chapter 10's own already-locked structural vocabulary (envelope vs. payload,
`ADR-039`'s own artifact field taxonomy) — never a format-specific parsing-tolerance policy. This is
independently confirmed, not merely asserted: `event_class`/`allowed_streams`/`merge_constraints`
have existed on every current Event Contract version-artifact since `ADR-039`'s own approval, and no
governing text anywhere in this repository has ever treated a prospective change to any of them as
gated on the still-missing reader/format policy (a) — the same category of field this ADR's Decision
places `causal_state_dependency_declaration` alongside.

## Alternatives considered

1. **(CHOSEN) Categorical exemption, generalized.** `compatibility_commitment`/§10.3.1 governs
   exclusively `payload_shape`/`payload_semantics_and_invariants` content — the shape and semantics
   of data actually serialized into event-instance payload bytes. Fields declared as top-level
   siblings of `payload_shape` on the Event Contract version-artifact (per `ADR-039`'s own fixed
   shape) — `event_class`, `allowed_streams`, `merge_constraints`, and (per Approved `ADR-048`)
   `causal_state_dependency_declaration`, and any future field of the same structural kind — are
   categorically outside §10.3.1's scope. Their compatibility is evaluated instead under Chapter 10
   §10.3's own general breaking-change test (does the change make a currently-valid consumer
   invalid), never under §10.3.1's data-presence-calibrated minimal-classification rules. A new
   `contract_version` is still always required for any such addition (`ADR-039`'s immutability
   model, unaffected, not reopened). This is the narrowest rule that resolves (b) using only
   already-locked structural distinctions, generalizes cleanly to every future producer's identical
   first encounter with an `ADR-048`-style field, and requires no reader/format-policy content
   whatsoever.
2. **No exemption — every artifact-level field is subject to the same §10.3.1 data-presence rules as
   payload.** Rejected. This would import §10.3.1's "forward compatibility structurally unavailable
   because the data is absent" reasoning onto a field that is never present in any event's own data
   in the first place — a category error, not a stricter reading. It would also make Chapter 8
   §8.2.3's `declared-state-dependencies` mechanism — which `ADR-048` was approved specifically to
   serve — permanently unusable for any already-Published Event Contract platform-wide until the
   large, currently-unscoped reader/format-policy work (a) completes, a disproportionate, cascading
   blocker for a mechanism that touches no payload data at all. Nothing in this repository's own
   history has ever applied this reading to `event_class`/`allowed_streams`/`merge_constraints`
   either.
3. **Merge (b) into (a) — resolve both together via one platform-wide reader/format policy now.**
   Rejected, per the governing task's own explicit boundary and independently confirmed unnecessary
   above ("Why (a) is not required to resolve (b)"): (a) and (b) are orthogonal axes — (a) concerns
   reader tolerance for payload bytes; (b) concerns whether a field is payload at all. Resolving (a)
   first would not even answer (b), since (a)'s own machinery (JSON Schema/Avro/Protobuf-style
   unknown-field tolerance rules) has no defined meaning for a field that is never serialized.
   Attempting it now would also be a far larger decision than this bounded question requires,
   contrary to `G-ADR-002`'s "khó đảo ngược, không phải chi phí thấp" scoping discipline.
4. **Resolve narrowly for `causal_state_dependency_declaration` only, not as a general category
   rule.** Rejected. Does not generalize — the identical question recurs, unresolved, the first time
   any Candle/Structure/Regime Event Contract needs its own first `ADR-048`-style post-publication
   delta (already flagged as inevitable by the triage, §6). The categorical test (top-level sibling
   of `payload_shape`, per `ADR-039`'s own already-fixed shape; never serialized into any instance)
   is already objectively defined by existing structural vocabulary and costs nothing extra to state
   once, generally, rather than once per field per `contract_id`.

## Decision

**Chapter 10 §10.3.1's `compatibility_commitment` declaration, and the backward/forward
compatibility-classification rules that attach to it, govern exclusively an Event Contract
version-artifact's `payload_shape`/`payload_semantics_and_invariants` content.** A top-level field
declared as a sibling of `payload_shape` on the version-artifact (per `ADR-039`'s own fixed shape) —
never nested inside `payload_shape` or `payload_semantics_and_invariants`, and never serialized into
any event instance's own payload bytes — is categorically **outside** `compatibility_commitment`'s
scope. This currently includes `event_class`, `allowed_streams`, `merge_constraints`, and (per
Approved `ADR-048`) `causal_state_dependency_declaration`.

**Compatibility classification for such a field instead uses Chapter 10 §10.3's own general
breaking-change test** — a currently-valid consumer becomes invalid, or does not — evaluated against
the contract's real, registered consumer topology (`context-map.yaml`/`module-registry.yaml`,
same evidentiary standard `ADR-038`/`ADR-047` already use), never against §10.3.1's data-presence
rules.

**Unaffected, not reopened:**

- A new `contract_version` is still always required for any such field's first addition to an
  already-`Published` artifact (`ADR-039`'s immutability model).
- `payload_shape`/`payload_semantics_and_invariants` deltas remain governed by §10.3.1 exactly as
  before — `feature.md`'s own already-closed `BREAKING` classification of `ADR-037`'s
  `computation_dependency_content_evidence` (a true `payload_shape` field) is not reopened,
  reclassified, or affected by this Decision in any way.
- Any contract's own declared `compatibility_commitment` value (`backward_only`, etc.) is unchanged;
  this Decision only fixes which fields that declared direction's rules apply to.
- Question (a) — the platform-wide reader/format policy — remains exactly as open, and exactly as
  separately governed, as `ADR-037`/`ADR-038` already state.

## Consequences

This ADR resolves question (b) only. It does not itself classify Feature's own
`causal_state_dependency_declaration` delta as breaking or non-breaking — that classification is a
separate, later, bounded application of this Decision's rule, requiring its own transaction (not
performed here, consistent with the forbidden scope governing this one: no Feature `v1.1` file is
touched, and the version-impact artifact's own stale reasoning is not rewritten here). Applying this
Decision's rule to that concrete case (non-normative preview, not asserted as this ADR's own
conclusion): `causal_state_dependency_declaration` is a top-level sibling of `payload_shape` on both
Feature `v1.1` candidates (confirmed, Context above), never serialized into any event instance's own
payload; under this Decision's rule, its compatibility classification would therefore use Chapter 10
§10.3's general test rather than §10.3.1, and — because `context-aggregator` is not currently relying
on anything this field would remove, narrow, or reinterpret, and in fact cannot satisfy its own
already-declared `declared-state-dependencies` mode for `feature-engine-feature` until a version
carrying this field exists — no currently-valid consumer would become invalid. A follow-on,
separately-governed bounded transaction should: (1) apply this rule concretely to close that
classification for Feature's own delta, citing this ADR as authority; (2) correct
`docs/project/feature-causal-state-dependency-version-impact-001.md`'s own stale §3.3 claim (that no
registered consumer uses `declared-state-dependencies` mode for Feature's stream) against
`context-market-input.yaml`'s actual content; (3) when any Candle/Structure/Regime Event Contract
first needs a post-publication artifact-level-field delta, cite this ADR directly rather than
re-litigating the scope question. This ADR does not change `ADR-037`/`ADR-038`/`ADR-039`/`ADR-048`'s
own decisions, does not modify any Constitution chapter, does not modify `context-market-input.yaml`
or any other Input Contract, and does not authorize publication of any Event Contract.
