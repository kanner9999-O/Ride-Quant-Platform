**Scope classification — `ADR Required`.** Chapter 10 §10.3.1 (fresh-read) mandates every published
contract declare a compatibility direction but does not itself select a value for any specific
contract: *"published contract nằm trong phạm vi compatibility evaluation mà không khai báo chiều
compatibility bắt buộc là invalid declaration → không được chứng nhận compatible → eligible =
false"* — an undeclared direction fails closed, it is never inferred. That selection is a genuine
semantic decision this repository has not yet made for any of these eight `contract_id`s (confirmed
above). Chapter 0 §4b's `>1`-module trigger (*"quyết định ảnh hưởng >1 module... → Bắt buộc"*) is
independently sufficient and applies to all eight: even the narrowest case (each of the four
Structure `contract_id`s) is producer `structure-engine` + consumer `context-aggregator` = 2
modules — the identical minimum cardinality `ADR-038` itself already found sufficient for Feature's
own two `contract_id`s. `ADR-038` is direct process/semantic precedent for *how* to select an Event
Contract compatibility commitment (backward-only, reasoned from real consumer topology and the
§10.5 immutable-binding principle) — it is cited throughout this ADR as precedent, never as
authority that automatically decides this ADR's own outcome.

**Decision:** Each of the following eight Event Contracts commits, as a **proposed Draft
candidate**, to **`backward_only`** compatibility — Chapter 10 §10.3.1's exact semantic:
*"consumer CŨ vẫn đọc/validate đúng dữ liệu MỚI"* (an existing consumer remains able to correctly
read/validate new data under a later contract version claimed compatible). This is a proposed
policy commitment for Review A and eventual Product Owner decision — **it is not yet a Product
Owner decision, not "selected," not "approved," and not "accepted."** Every row below is an
independent, per-`contract_id` decision; no row's value is inferred from, or constrains, another
row's value — packaging into one file is a governance-transaction choice (`MODEL C`), not a
semantic-coupling one.

**Distinguishing three separate Chapter-10 concepts (required by this decision, only the first is
decided here):**

1. **Compatibility commitment (§10.3.1) — proposed by this ADR, decided only at Product Owner
   approval.** A contract-level declaration of which direction(s), if any, each published contract
   requires. This is the sole subject of this ADR's Decision table above.
2. **Compatibility classification of a concrete schema delta — NOT decided here.** Whether a
   specific future field addition/removal/retyping for any of these eight `contract_id`s actually
   satisfies `backward_only` is a separate, per-change determination made once that concrete delta
   exists, against whatever format/reader policy applies at that time (see below). This ADR
   classifies no delta, because none of these eight Event Contracts exist yet.
3. **Compatibility Result (§10.4) — NOT created by this ADR, out of scope entirely.** A
   Compatibility Result is a heavy, immutable, provenance-pinned artifact requiring a registered,
   granted evaluator (Chapter 9 §9.6 Declaration → Grant → Enforcement → Verification) and full
   subject/input/policy-version/grant/evaluation-boundary evidence (§10.4.1). This ADR creates no
   evaluator, grant, or policy-registry mechanism, and issues no Compatibility Result for any
   subject.

**Format/reader-policy gap — stated explicitly, not assumed away.** This ADR selects a
compatibility **direction** as policy for each of the eight `contract_id`s. It does **not** prove
any concrete schema delta compatible, and does **not** assume:

- tolerant/unknown-field-accepting reader behavior for any consumer;
- a particular JSON/Avro/Protobuf (or equivalent) serialization behavior;
- an existing schema-validator implementation.

Chapter 10 §10.3.1 (fresh-read): *"Quy tắc theo từng format cụ thể (JSON Schema, Avro, Protobuf...)
thuộc Domain Contract/Phase 1 — Constitution chỉ khóa semantic trên."* No such format-specific
reader/schema policy currently exists for any of these eight `contract_id`s (same gap `ADR-038`
already named for Feature's own two events, confirmed here to be platform-wide, not
Feature-specific). Actual compatibility of a concrete future delta remains a separate determination
against that policy once it exists — never assumed while it is absent.

**What `backward_only` protects — and what it does not, per §10.5.** *"Việc provider publish một
version mới KHÔNG phải trigger"* — a consumer that keeps an immutable, pinned old binding is
already unaffected merely because a newer producer contract version is published, with or without
this ADR (§10.5's own worked example: *"Consumer pin Contract v2 · Provider publish Contract v3 →
binding vẫn là v2 → KHÔNG revalidate activation cũ"*). `backward_only`, for each of these eight
`contract_id`s, exists to protect the different, real scenario each row's table entry is actually
for: a consumer that **intentionally** advances or upgrades its pinned binding to a later contract
version claimed compatible — for that consumer, this commitment (once approved) would obligate the
platform not to have broken it. Forward compatibility (a new consumer correctly reading old data)
remains, for every row, explicitly **not** committed by this candidate — left undeclared-as-a-
commitment, not asserted to hold or fail.

**Alternatives considered (assessed per Chapter 10 §10.3.1's declared choice space; rejection is
policy/risk-based, not a fabricated format-behavior claim — none of these eight contracts exist yet,
so no concrete reader/schema fact can be cited either way):**

1. **`backward_only` (proposed).** Adopted as the explicit policy commitment for all eight rows,
   protecting each `contract_id`'s real, already-verified downstream consumer(s) that intentionally
   advance their binding to a later, claimed-compatible version — without promising a direction
   (forward) this repository has no current reader/format policy to support for any of the eight,
   consistent with `ADR-038`'s own precedent reasoning for the structurally identical Feature case.
2. **`forward_only`.** Rejected on current-topology, policy-based grounds: `forward_only` protects a
   *new* consumer reading *old* data — none of these eight `contract_id`s exists yet, so there is no
   old data to protect reading of, and the topology this ADR must actually protect is the
   *intentionally-advancing existing consumer* scenario each row's rationale names, which
   `forward_only` does not address. Not claimed impossible for every future architecture — only that
   it does not serve the protection need this topology currently and most directly presents.
3. **`bidirectional`.** Rejected as a strictly larger commitment surface than currently justified:
   it requires sustaining both directions, and the concrete reader/migration mechanics needed to
   support the forward leg for any of these eight `contract_id`s are not established (same gap
   `forward_only` above is rejected on). Not claimed impossible in principle for a future,
   differently-justified decision — only unjustified by current evidence for this first-publication
   commitment.
4. **Explicit no-compatibility commitment.** Constitutionally permitted — §10.3.1 explicitly allows
   a contract to commit to no direction, provided the choice is itself an explicit, auditable
   declaration, never an absent field. Rejected here not because a currently-pinned binding
   otherwise lacks protection (per §10.5, an existing pinned binding is already unaffected by later
   publication regardless of this ADR's decision), but because no-commitment provides **no** governed
   cross-version guarantee for a consumer that intentionally advances its binding — and every one of
   these eight `contract_id`s has at least one real, already-registered consumer in governed
   topology (§B of the scope-derivation artifact, re-confirmed above), so leaving that
   advancing-consumer scenario entirely unprotected across all eight would not reflect the
   platform's actual dependency topology or Chapter 10 §10.7's downstream-impact-assessment purpose.

**Consequences:**

Benefits:
- Explicit first-publication compatibility direction proposed for all eight Context-upstream Event
  Contracts, closing the currently-fail-closed gap Chapter 10 §10.3.1 imposes on any undeclared
  contract.
- Every currently-verified downstream consumer (`structure-engine`, `raw-regime-engine`,
  `feature-engine`, `context-aggregator`) gains a governed upgrade expectation for whichever
  contract(s) it depends on, once approved.
- No absent/implicit compatibility declaration for any of the eight — each row is independently,
  explicitly stated.

Costs:
- Future schema evolution for any of the eight `contract_id`s is constrained by whichever
  commitment is ultimately approved.
- A concrete future schema delta for any of these contracts still requires its own compatibility
  classification against the approved commitment and against the format/reader policy that must be
  separately established — this ADR does not remove that later obligation.
- Adopting `backward_only` implies stronger migration/versioning discipline going forward for
  producers of these eight contracts than an unconstrained/no-commitment baseline would.
- Absent a format/reader policy, a concrete future compatibility claim for any of the eight fails
  closed under Chapter 10 §10.3.1/I-6 rather than being assumed compatible — a real, current cost of
  not yet having that policy, not introduced by this ADR but not resolved by it either.

Model-C packaging consequence (Chapter 11 §11.8, whole-ADR-file `supersedes` relation — fresh-read:
*"ADR mới Approved với `supersedes: [ADR-cũ]`"*, no partial/per-decision-item supersession mechanism
exists):
- One Product Owner approval decision, once made, can govern all eight rows' proposed commitments
  at once.
- A future change affecting only one row (e.g. Structure's own commitment needing revision) would
  require a new ADR superseding ADR-047 **as a whole**, because Chapter 11 supersession is
  ADR-file-grained, not per-decision-item-grained.
- That future superseding ADR can explicitly carry forward the seven unaffected rows' decisions
  unchanged while revising only the targeted row(s) — Chapter 11 does not prohibit a superseding ADR
  from re-stating unaffected prior content, only from editing the superseded file in place.
- This is a bounded-reviewability/future-supersession-grain consequence of the packaging format
  chosen by the Product Owner (`MODEL C`), not a claim of runtime or architectural coupling between
  Candle/Structure/Regime — those three families remain exactly as independent at the runtime/
  producer level as `ADR-003`/`ADR-014` already establish; this ADR does not touch that boundary.

**Risks:**

- Over-broad assumption that one compatibility direction (`backward_only`) fits all eight contracts
  equally well, when their concrete future evolution needs could differ — mitigated by the explicit
  per-`contract_id` decision table above (no value inferred across rows) and by fresh Review A
  independently assessing each row's own rationale, not the table as a single undifferentiated
  block.
- Future schema changes to any of the eight could expose a contract-specific need this proposal did
  not anticipate — mitigated by later supersession remaining available (Chapter 11 §11.8), and by
  concrete compatibility always being separately, independently evaluated per delta (§10.3.1),
  never assumed satisfied merely because this ADR is approved.
- No current format-specific reader/schema policy exists for any of the eight — mitigated by this
  ADR explicitly stating that gap (Format/reader-policy gap, above) rather than assuming tolerant-
  reader behavior; any concrete future compatibility claim fails closed under I-6 until that policy
  exists.
- One-file supersession grain (Model C) means a future single-row correction requires a
  whole-file-superseding ADR — mitigated by that superseding ADR being explicitly permitted to carry
  forward unaffected rows verbatim (Consequences, above); this is a bounded, known cost of the
  Product-Owner-selected packaging, not an unbounded one.
- The owning Domain Contracts for all eight `contract_id`s (`candle.md`, `structure.md`,
  `regime.md`) remain `Draft` at this boundary — mitigated by this ADR not depending on any of them
  reaching `Approved`/final status to propose a compatibility direction for their already-existing,
  already-stable event definitions; if a Domain Contract's own event definition changes materially
  before first publication, that is itself new evidence requiring fresh Review A of this candidate,
  not a reason to avoid proposing now.
- Event Contracts for all eight remain absent until later, separate authoring — mitigated by this
  ADR explicitly stating (First-publication Event Contract gap, above) that no Event Contract is
  authored or published here, and that each one independently requires its own governance cycle.

**Accepted risks:** None recorded. This ADR is `Draft`, unreviewed, and unapproved — no Product
