## Decision

Establish the minimum Event Contract architecture, and the one minimum Domain-Context/Capability
registration it requires, necessary for a genuine post-Genesis Stream Registry activation event to
exist — governed-authored new content (per `ADR-039`'s own "first publication is governed authoring,
not mechanical transcription" rule), not transcribed from any Domain Contract, because none exists
for this control-plane concern.

**1. Contract identity — narrow, registry-version-activation-specific (not a general lifecycle-event
abstraction):**

```text
contract_id:  stream-registry-version-activated
event_type:   STREAM_REGISTRY_VERSION_ACTIVATED
```

A broader "generic lifecycle boundary event" abstraction (covering stream activation/retirement/
writer-handoff too) is explicitly **not** adopted — Chapter 8 §8.3.1/§8.3.5 describes these as
related but textually and structurally distinct boundary kinds (different required identifying
fields: a registry-version activation identifies a `registry_version`; a stream retirement identifies
a `terminal_position`; a writer handoff identifies a `handoff_boundary`), and nothing in the current
task — closing the one boundary blocking Context's own registry transition — requires deciding the
other three now. A future registry-version transition that also needs stream retirement/writer
handoff would use its own, separately-derived Event Contract(s) for those boundary kinds, governed
exactly this same way, not a shared polymorphic contract invented here speculatively.

**2. `event_class: lifecycle_boundary` (governed-authored, new vocabulary term — justified, not
reflexive):** Chapter 8 §8.3.1's own illustrative `event_class` example is explicitly open-ended
(*"event_class: decision | observation | ..."*) — the same textual latitude `candle-closed/v1.0.yaml`
already exercised to adopt `observation`, and the Candle/Structure/Regime/Feature family already
exercised to adopt `derived_fact`. Neither existing term fits: this event is neither a raw venue
observation nor a derived analytical fact — it is a platform-governance fact about the event-sourcing
topology itself, exactly the category Chapter 8 §8.3.1/§8.3.5/§8.4.1 repeatedly names "lifecycle
boundary" (*"activation/retirement/stream-creation/writer-authority-transition boundary"*). No
existing term is stretched or overloaded to cover it.

**3. Subject semantics — new minimal Business Capability/Domain Context required (the one genuine
sub-gap found while deriving this contract):** Chapter 8 §8.2.2 requires `context_id` (a registered
Domain Context, Chapter 4 §4.2) on every `subject_ref`, with no carve-out for control-plane events.
`docs/domain/context-map.yaml` (fresh-read in full) registers eleven Domain Contexts today — every
one of them a business domain (market data/structure/regime/feature/context/account/strategy/
decision/risk/execution family); none covers platform-control-plane governance facts, and
`stream-registry-authority`'s own `module-registry.yaml` entry explicitly leaves
`implements_capabilities`/`serves_contexts` empty for exactly this reason (*"no existing
context-map.yaml capability/Domain Context registered for this responsibility, and this module is not
a candidate to invent one"* — correct for a **mechanical module-registration transcription**
transaction, which is not authorized to invent architecture, but not a permanent exemption from
Chapter 8 §8.2.2's own requirement once a real event needs to name one). This ADR mints the minimum
registration, bundled here because it is strictly required to make this same Decision's own
`subject_ref` resolvable — the same "one coherent decision, one ADR" bundling `ADR-036` already used
for its own `stream-registry-authority` module identity:

```yaml
# docs/domain/context-map.yaml — addition, NOT performed by this ADR (Consequences item 2)
capabilities:
  - id: platform-control-plane
    title: Platform Control Plane
    responsibility: >
      Owns platform-governance facts about the event-sourcing topology itself (Stream Registry
      lifecycle/activation, canonical Audit preservation boundary) that no business-domain
      capability owns (Chapter 8 §8.3.1/§8.3.5/§8.4.1) — never business/domain decision semantics.
    status: active

contexts:
  - id: platform-control-plane
    title: Platform Control Plane
    capability_id: platform-control-plane
    responsibility: >
      Platform-lifecycle/audit boundary facts (registry-version activation; future stream
      activation/retirement/writer-handoff; audit-preservation) — Chapter 8 itself, not a Domain
      Contract, owns these semantics.
    owned_contracts: []   # no Domain Contract exists or is needed — Chapter 8 is the controlling
                          # authority, the same empty-field convention module-registry.yaml already
                          # uses for contract-compatibility-authority/stream-registry-authority
    status: active
```

`subject_ref` for this event type:

```yaml
subject_ref:
  context_id: platform-control-plane
  subject_kind: policy
  subject_type: StreamRegistryVersion
  subject_id: <the exact registry_version literal being activated, e.g. "v1.1">
  scope: {}
```

`subject_kind: policy` matches Chapter 8 §8.2.2's own worked example verbatim (*"RISK_POLICY_VERSION_ACTIVATED
(subject = policy version)"*) — a registry-version activation is structurally identical: a
versioned control/policy artifact becoming active. No `scope` fields are needed — Chapter 8 §8.3.1
already fixes Stream Registry as a single, unnamed, platform-wide lineage (*"Authoritative source duy
nhất"*), not multi-tenant/scoped.

**4. Required payload — exactly one field, nothing speculative:**

```yaml
payload_shape:
  activated_registry_version: {type: string, required: true, description: >
    The exact registry_version literal (ADR-039's v<major>.<minor> grammar, reused by ADR-041's own
    citation for Stream Registry) that becomes active, per Chapter 8 §8.3.1, from this event's own
    committed sequence position forward on platform-lifecycle.}
```

No predecessor/old-registry-version field, no stream-diff/added-streams field, and no content-hash
field are added. Chapter 8 §8.3.1's `active_registry_at()` function is computed purely from
`effective_from` ordering across registry files that already exist at evaluation time — it needs no
self-declared predecessor from the activation event. Exact content identity of the activated registry
version is resolved separately, by `ADR-041`'s own `docs/architecture/stream-registry-versions/
<registry_version>.yaml` snapshot path — duplicating a content hash here would create a second,
competing source for a fact `ADR-041` already owns (I-12). This is the complete payload — adding
`activated_by`/`reason`/`previous_version` or similar fields now would be exactly the "generic
lifecycle field added because it might be useful later" this task's own instruction forbids; nothing
in Chapter 8's required activation semantics (enumerated above) needs them.

**5. `allowed_streams: [{stream_id: platform-lifecycle}]`** — Chapter 8 §8.3.5: *"Mọi activation...
boundary phải được ghi trên stream này"* (the canonical Lifecycle Stream, exclusively). Not
`platform-audit` — that protected stream serves a textually distinct purpose (§8.4.1 audit-
preservation facts when a target stream loses append-eligibility), unrelated to registry-version
activation.

**6. `merge_constraints: {}`** — this event is, and must be, a **root event**: nothing in Chapter 6

decision to activate a new topology is a governed, Product-Owner/architecture-level act (an ADR
approval plus a later governed registry-authoring transaction), never itself caused by a prior
*authoritative domain event* in the sense Chapter 6 §6.7 defines causation. `causation_refs` is
therefore canonically `[]` for every instance of this event type — the identical root-event pattern
`candle-closed/v1.0.yaml` already establishes for `CandleClosed`, reused here, not invented. No
`merge_constraints.prerequisite_policy` is declared, for the same reason `candle-closed` declares
none: there is no causal prerequisite to express.

**7. `causal_state_dependency_declaration: {mode: vacuous}`** — Approved `ADR-048`'s own canonical
mechanism; valid precisely because `causation_refs` is canonically `[]` (item 6). No `roles` field
is present (`ADR-048`'s own fail-closed rule: its presence under `mode: vacuous` would itself be a
malformed declaration).

**8. Producer authority — already decided, applied not redecided:** `envelope.producer_ref.module_id:
stream-registry-authority` — the sole registered writer authority over `platform-lifecycle`
(`ADR-036`; `module-registry.yaml`, fresh-confirmed this transaction). This Event Contract does not
redeclare writer authority — Chapter 8 §8.2.4/§8.3.1 already own it; declaring it again here would
create a second, competing source for the same fact (I-12). A future Review A for the concrete
artifact must confirm the eventual implementation never allows any other `module_id` to author this
event type.

**9. `compatibility_commitment: backward_only`** — decided here, as part of this same bundled
Decision (not deferred, and not reflexively copied from `ADR-038`/`ADR-047`'s *values* — their
reasoning *pattern* is independently re-applied against this contract's own, genuinely different
topology). **Corrected consumer-topology framing (v0.2, `ADR052-A-MIN-01` — the protection rationale
below no longer claims every cursor-bearing module directly binds to this Event Contract's own
schema):** the scenario `backward_only` protects — a consumer that intentionally advances its own
pinned binding for this `contract_id` and must keep correctly reading it — is not speculative here,
but the accurate consumer is narrower and more precise than "every cursor-bearing module directly":
Chapter 8 §8.5.2's own Registry → Lifecycle relational invariant means every current and future
cursor-bearing module ultimately *depends on* `active_registry_at()`/lifecycle-resolution authority
being correct, but that resolution is naturally delegated to one shared canonical
resolution mechanism (the same pattern `authority_resolver.py` already establishes for other
Referenced Authoritative Artifact resolution) rather than each module separately parsing
`STREAM_REGISTRY_VERSION_ACTIVATED` events itself. The genuinely direct consumer this commitment
protects is that shared resolution mechanism (and `stream-registry-authority`'s own eventual
historical-replay/audit tooling) — which must keep correctly reading this event type across an
advancing binding for *every* dependent module's resolution to remain correct, platform-wide,
forever. This indirect-but-universal dependency is still a materially broader, more durable
protection need than `ADR-047`'s own narrowest row (`break-of-structure-detected`, one verified
direct consumer) — just stated accurately as "depends on," not "directly consumes."
`forward_only`/`bidirectional`/no-commitment are rejected for the identical reasons `ADR-047`
rejected them for its own eight rows (Alternatives, below) — no concrete reader/schema fact is
asserted either way beyond the direction commitment itself (same format/reader-policy gap
`ADR-038`/`ADR-047` already named and left open, not resolved here).

**10. Relationship to old/new registry at append — envelope-level, not payload, not redefined:**
`envelope.stream_ref.registry_version` on the activation event itself equals the **old** active
registry (Chapter 8 §8.3.1's own `active_registry_at(pre_append_frontier)` rule) — never the one
being activated. The new registry file's own `effective_from.event_ref` is populated, after the
activation event commits, with that event's now-known `(stream_id, sequence, event_id)`. This Event
Contract does not restate either relationship in its payload — both are Chapter 8 §8.3.1's own
envelope/registry-file mechanics, applied here, not redefined (see Circularity analysis, below).

**11. Governed transition ordering — new, explicit protocol content this ADR itself owns (v0.2
correction, `ADR052-A-MAJ-01`):** the full candidate content of a new registry version (every
stream entry, including every existing one carried forward byte-identical, and the exact
`registry_version` literal it will carry) **must be authored, Review-A'd, and Product-Owner-approved
as a Draft before the corresponding activation event may be appended** to `platform-lifecycle` — the
one field that cannot yet be filled at that point, `effective_from.event_ref`, is the only thing left
open; it is populated mechanically, with no further governance step, once the activation event's own
real identity is known. This ordering is not decided anywhere in Chapter 8/`ADR-041` today (both fix
*what* must be true of the eventual artifacts, neither fixes *when*, relative to each other's own
review cycles, the activation event may be appended) — it is new, narrow, transition-sequencing
architecture this ADR supplies because its own stated purpose, the activation event's Event Contract
architecture, is not actually usable without it (see Circularity analysis, below, for the full
derivation and the proof that this ordering is what keeps `E`'s own payload from tripping `ADR-041`'s
authoritative-use gate). This item governs every future post-Genesis registry transition that uses
this Event Contract, not only Context's own — the same way items 1-10 do.

## Circularity / recording-sequence analysis (required by the governing task)

**v0.2 correction (`ADR052-A-MAJ-01`):** v0.1 asserted this sequence was "not a genuine
circularity" and "already mechanically closed" by Chapter 8 + `ADR-041` alone. Fresh
Review A correctly found that assertion collided, unaddressed, with `ADR-041`'s own
authoritative-use gate. The collision is stated explicitly below, then resolved by adding
the one piece of protocol-ordering content this ADR itself must supply (Decision item 11,
new), after which the (now-strengthened) interpretation that the activation event's
payload does not trip `ADR-041`'s gate is proven, not assumed.

### The collision, stated explicitly

`ADR-041`'s Authoritative-use gate (`docs/adr/ADR-041.md`, "Decision," bullet 1): *"Before
any `contract_version`/`registry_version` may be named by an authoritative event's/
cursor's own reference, its immutable version snapshot MUST already exist at its
canonical path — an identifier with no corresponding snapshot is never a valid
authoritative reference target."* The activation event `E` is itself an authoritative
event, and its own payload (`activated_registry_version: "v1.1"`) names the literal
string `"v1.1"` — and, under v0.1's own Step 2→3 ordering, `E` would commit **before**
any `v1.1` file (let alone its immutable snapshot) exists. Read literally and without
further argument, this is exactly the pattern `ADR-041`'s gate forbids. v0.1's claim that
`E`'s payload is merely "a plain string literal" needing "no referent to be chosen" was
asserted, not proven, against this gate — the fresh Review A finding is correct that this
is not yet mechanically closed.

### Resolution — new protocol-ordering content this ADR itself must supply (see Decision item 11)

The gate's own concern (per its text and per `ADR-041`'s own Context section) is
**exact-historical-content resolution**: a cursor or event that names a version
identifier must be able to have that identifier resolve, now or on replay, to byte-exact
content — the entire reason `ADR-041` exists. `ADR-041` itself explicitly disclaims
touching Chapter 8 §8.3.5's own activation-boundary mechanics (`ADR-041` Decision, final
bullet: *"Stream Registry activation/version transitions remain governed entirely by
Chapter 8 §8.3.5's own lifecycle-boundary model... this Decision adds an exact-version-
snapshot resolution layer underneath that model, it does not redefine, bypass, or gate
any part of §8.3.5's own activation-boundary semantics"*). The operative resolution
mechanism Chapter 8 §8.3.1 actually uses, `active_registry_at(frontier)`, is a pure
function over **which registry files exist and their own `effective_from` values at
evaluation time** — it never reads `E`'s own payload at all; it only ever reads the
**registry file's** `effective_from.event_ref`, which points *at* `E`'s identity
`(stream_id, sequence, event_id)`, never the reverse. `E`'s own payload field is
therefore not consulted by the one mechanism that actually resolves "what is active" —
on its own, this already suggests `E`'s payload is a descriptive/audit label, not a
resolution-bearing reference.

But a label can still be a "reference" in `ADR-041`'s sense if something could ever rely
on it naming "v1.1" before "v1.1" is real — e.g., if the eventual registry file's content
could still change (a different version identifier, or different stream content) between
`E`'s commit and the file's own authoring, `E`'s label would become a stale/orphaned
promise with nothing to answer it. **This is the genuine gap v0.1 did not close**, and
closing it requires a protocol-ordering commitment, not merely a definitional argument:

**New Decision item 11 (the protocol-ordering content this ADR itself supplies):** the
full candidate content of the new registry version — the entire `stream-registry.yaml`
file, including the new stream's identity/writer authority and every existing entry
carried forward byte-identical — must be authored as a reviewed, Product-Owner-approved
Draft **before** `stream-registry-authority` ever appends the activation event. Only the
one field that cannot yet be known (`effective_from.event_ref`, since `E` does not yet
exist) remains open at that point; everything else, including the exact literal version
identifier `E`'s own payload will name, is already governed-fixed. Under this ordering:

```text
Step 1 (architecture, this ADR): the activation event's Event Contract -- identity,
  payload, allowed_streams, class, causation, producer authority, compatibility -- is
  decided and governed-authored ONCE, ahead of any concrete transition. Already done once
  this ADR is Approved.

Step 2 (at the actual transition, NOT performed by this ADR): the FULL v1.1
  stream-registry.yaml candidate content (all eight streams -- seven carried forward
  byte-identical, plus context-aggregator-context) is authored, reviewed (Review A), and
  Product-Owner-approved as a Draft -- EXCEPT effective_from.event_ref, which cannot yet
  be populated. This is the governed act that fixes "v1.1" and every other byte of the
  eventual file BEFORE E exists -- not merely a verbal plan, a reviewed artifact.

Step 3 (at the actual transition, NOT performed by this ADR): stream-registry-authority
  appends the activation event E to platform-lifecycle. E.payload.activated_registry_version
  = "v1.1" -- naming exactly, and only, the identifier Step 2 already fixed by governed
  review; E.envelope.stream_ref.registry_version = v1.0 (the OLD, already-Approved,
  already-existing registry -- Chapter 8 §8.3.1's own active_registry_at(pre_append_frontier)
  rule). E is validated entirely against authority that already exists (v1.0); nothing
  about validating E requires v1.1's file to exist yet.

Step 4 (at the actual transition, NOT performed by this ADR): once E has committed, E now
  has a real, stable, resolvable event_ref: {stream_id: platform-lifecycle, sequence: <E's
  allocated sequence>, event_id: <E's id>}. The ALREADY-approved v1.1 Draft from Step 2 is
  now completed with effective_from.event_ref = E's own, now-known, real identity -- the
  one field Step 2 could not yet fill -- and ONLY this mechanical backfill is performed;
  no other byte of the already-approved content changes.

Step 5 (at the actual transition, NOT performed by this ADR): v1.1 is Published under
  ADR-041's own existing Option 2 lifecycle (the immutable docs/architecture/
  stream-registry-versions/v1.1.yaml snapshot is captured, byte-identical to the now-
  complete current/active file) -- ADR-041's existing Draft -> Published distinction,
  applied here without modification, is itself the "prepared-vs-authoritative" distinction
  the governing task asked whether a new one is needed. It is not; this is that
  distinction, reused.

Step 6: from E's own sequence position forward, active_registry_at(frontier >= E.sequence)
  = v1.1 -- a pure function of which registry files exist and their own effective_from
  values AT THE TIME OF EVALUATION, never a separately-tracked runtime "activation" flag,
  and never reading E's own payload. Nothing can treat v1.1 as active before its own file,
  with the real effective_from, is actually Published (Step 5) -- there is no race window
  where v1.1 could be prematurely "active" merely because E has committed.
```

### Proof that `E`'s payload does not trip `ADR-041`'s gate, under this ordering

1. **`E`'s payload is never read by the resolution mechanism.** `active_registry_at()`
   resolves purely from registry files' own `effective_from` fields (Chapter 8 §8.3.1);
   it never inspects `E.payload.activated_registry_version`. No cursor, validator, or
   replay path is ever specified (Chapter 8, anywhere) to read that field for resolution
   purposes — it exists for human/audit legibility of the lifecycle log, not as a
   resolution input.
2. **Under Decision item 11's ordering, the field can never mismatch.** The literal
   `"v1.1"` `E`'s payload will name is fixed by the SAME governed review (Step 2) that
   fixes the eventual file's own `registry_version` field — they are not two independent
   assertions that could drift apart; they are one approved decision, recorded twice (once
   provisionally in the pre-approved Draft, once immutably in `E`'s own payload at append
   time). There is no window in which `E` could name an identifier that the eventual file
   does not also carry, because the file's content (including its own `registry_version`
   literal) was already fixed, reviewed, and approved before `E` ever committed.
3. **Crash/interruption fails safe at every stage.** If the process crashes after Step 2
   (content approved) but before Step 3 (`E` appended): nothing irreversible has happened;
   the approved Draft simply waits, unresolvable, until append is retried — no orphaned
   event, no stale reference. If it crashes after Step 3 (`E` committed) but before Step 4
   (backfill) or Step 5 (publish): `E` is now a permanent, immutable fact, but it names
   exactly the identifier the already-approved Draft also carries — recovery is simply
   "resume at Step 4," never "re-decide what v1.1 should contain," because that decision
   already survived Step 2's own governance boundary before `E` ever existed. At no stage
   does a partial failure leave two different, competing claims about what `"v1.1"` means.
4. **Chapter 8 §8.3.5's own activation-boundary semantics are not redefined.** Steps 1-6
   are a direct application of Chapter 8 §8.3.1/§8.3.5's already-Locked text (quoted in
   full, "What Chapter 8 already decides," above) plus `ADR-041`'s own already-Approved
   Draft/Published distinction for the registry file itself, composed with exactly one
   addition — the governed-review-before-append ordering (item 11) — which Chapter 8 does
   not itself specify (it fixes *what* an activation event must prove, not *when*, relative
   to the new registry's own review cycle, it may be appended) and which `ADR-041`
   explicitly leaves to "Chapter 8 §8.3.5's own lifecycle-boundary model," i.e., to this
   ADR, the one that owns the activation event's own architecture.

**No amendment to `ADR-041` or Chapter 8 is required, and neither is proposed.** The
missing piece was ordering discipline for *this* ADR's own subject matter (when, relative
to content review, the activation event may be appended) — squarely ADR-052's own job,
not a narrowing of either existing Approved authority's own text. `docs/adr/ADR-041.md`
and Chapter 8 remain byte-identical, unedited, and uncontradicted by this correction.

## Registry-version identity treatment

**v0.2 correction (`ADR052-A-MAJ-02`):** v0.1 claimed `v1.1` was "uniquely, mechanically
determined by already-existing authority" via `ADR-039`+`ADR-041`+Chapter 10 §10.3.1
jointly. That overstated what those three authorities actually establish, fresh-checked:

- `ADR-039`'s breaking/non-breaking major/minor mapping is defined against Chapter 10
  §10.3's **published-contract-surface** compatibility test — it classifies changes to an
  **Event Contract's** own schema/semantic surface as seen by a consumer binding to a
  `{contract_id, contract_version}`. It says nothing about Stream Registry topology.
- `ADR-041` reuses `ADR-039`'s `v<major>.<minor>` **grammar** (the literal token
  format/path-substitution/fail-closed rules) "by direct citation, not redefined," for
  both Input Contracts and Stream Registry — `ADR-041`'s own text never states it also
  reuses `ADR-039`'s breaking/non-breaking **classification test** for deciding which
  component increments when Stream Registry's own topology changes. Format and
  classification-semantics are two different things `ADR-041` keeps separate; it adopts
  only the former.
- Chapter 10 §10.3.1 fixes general classification *principles* ("thêm element optional ...
  có thể non-breaking") for evaluating **a published contract surface**. It does not, on
  its own, state that these principles extend to Stream Registry topology additions, or
  that doing so yields a *minor* bump specifically — applying it here is a **choice to
  extend** an Event-Contract-scoped test to a different artifact family, not something
  Chapter 10 itself already decided for that family.

No existing authority, individually or jointly, already forces `v1.1`. **Corrected
treatment (bounded Option A, per the governing task — this ADR decides the one, narrow,
non-generalizing choice its own pending transition needs, without inventing a platform-
wide Stream Registry SemVer policy):**

```text
This ADR DECIDES, for this specific, currently-pending post-Genesis transition only (the
one ADR-051 requires -- adding context-aggregator-context to the Genesis Registry), that
the resulting registry_version shall be v1.1. Reasoning, stated as this ADR's own choice,
not as a pre-existing rule: the transition is purely additive -- every one of the seven
existing streams' identity/writer_authority/status/sequence_policy/genesis_position
carries forward byte-identical, and no existing reader of v1.0 is made invalid by an
eighth, independent entry appearing alongside them. Treating this as the kind of change
ADR-039/Chapter 10 §10.3.1 would call "non-breaking" if it were evaluating a published
contract surface -- and therefore choosing the minor-increment literal "v1.1" rather than
a major bump to "v2.0" -- is a REASONED EXTENSION of that existing vocabulary to this one
transition, not a mechanically pre-existing Stream Registry rule.

This determination is scoped to THIS transition only. It does NOT establish that every
future Stream Registry transition is "minor" by default, does NOT define what makes a
FUTURE Stream Registry change "breaking" (e.g., a stream retirement or a writer-authority
handoff may or may not warrant a major bump -- this ADR takes no position), and does NOT
create a general Stream Registry versioning policy. A future transition needs its own
reasoned decision about major vs. minor, made by whatever ADR or governed transaction
authors it -- this ADR's own choice here does not bind that future decision, is not cited
as a controlling precedent requiring the same answer, and this ADR does not depends_on or
supersede anything to make it one.
```

This determination is recorded here for the benefit of the later, separate, mechanical registry-
authoring transaction (`ADR-051`'s own Track A) — this ADR does not itself create any `v1.1` file or
snapshot.

## Alternatives considered

1. **Narrow, registry-version-activation-specific Event Contract (chosen).** Minimum architecture
   sufficient to prove Chapter 8's required activation semantics for exactly the one boundary blocking
   Context's registry transition; no broader abstraction invented speculatively.
2. **A single, general-purpose "lifecycle boundary event" contract covering activation, retirement,
   and writer-handoff together.** Rejected — Chapter 8 §8.3.1/§8.3.5 describes three structurally
   distinct identifying shapes for these boundary kinds (`registry_version` vs. `terminal_position`
   vs. `handoff_boundary`); forcing one payload shape to cover all three now, before any of the other
   two is actually needed, would either invent unused optional fields or a discriminated-union shape
   neither Chapter 8 nor the governing task's own instruction asks for — directly the "do not add
   generic fields merely because they might be useful later" the governing task forbids.
3. **Defer the Domain-Context/Capability registration to a future, separate ADR.** Rejected — it is
   strictly required to make THIS Decision's own `subject_ref` resolvable (Chapter 8 §8.2.2's `context_id`
   cardinality is unconditional); deferring it would leave this ADR's own Decision incomplete and
   unimplementable, the same reasoning `ADR-036` already applied when it bundled the
   `stream-registry-authority` module identity into its own Decision rather than deferring it.
4. **Treat registry-version identity as an open decision requiring its own future, separate ADR
   (rejected, v0.2 correction supersedes the prior rationale, `ADR052-A-MAJ-02`).** v0.1 rejected
   this alternative on the premise that `ADR-039`/`ADR-041`/Chapter 10 §10.3.1 already jointly and
   mechanically determine `v1.1` — fresh-checked, they do not (see "Registry-version identity
   treatment," above: `ADR-041` reuses only `ADR-039`'s token grammar, not its breaking/non-breaking
   classification test, for Stream Registry). The alternative is still rejected, but for the correct
   reason: deferring this one, narrow, currently-pending transition's own version identifier to a
   separate future ADR would be needless process overhead for a decision this same ADR can, and
   should, make directly and transparently as its own reasoned, scoped choice (above) — not because
   the question was already mechanically closed. A future, DIFFERENT transition's own version
   identifier remains genuinely open and is not decided here (see "Registry-version identity
   treatment" 's own explicit non-generalization clause).
5. **No ADR — treat the activation Event Contract as a mechanical transcription.** Rejected — there is
   nothing to transcribe FROM (no Domain Contract declares any of `event_type`/`event_class`/
   `payload_shape`/`compatibility_commitment` for this concern); `ADR-039`'s own text is explicit that
   a first-publication `event_class`/payload authoring act is governed authoring, and Chapter 0 §4b's
   Event-Schema-change trigger fires independently of whether a Domain Contract exists to transcribe
   from.
