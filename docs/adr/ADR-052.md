# ADR-052: Post-Genesis Stream Registry Activation — Lifecycle Activation Event Architecture

**Context:** Approved [ADR-051](./ADR-051.md) v0.3 decides that Context's own output requires exactly
one new post-Genesis logical stream, `context-aggregator-context`, sole writer `context-aggregator`
— but a post-Genesis stream cannot become active by registry-file edit alone. [Chapter 8](../constitution/08-event-model.md)
§8.3.1 is unconditional: *"mọi registry version sau Genesis phải khai báo `effective_from.event_ref`
trỏ tới lifecycle activation event của chính nó, trên canonical lifecycle stream"* — a **genuine,
committed** activation event on `platform-lifecycle`, not a file-level assertion. Fresh-verified this
transaction (direct repository search, not inherited from any prior finding):

- No lifecycle/governance Domain Contract exists anywhere (`docs/domain/` has no `lifecycle.md`/
  `audit.md`; confirmed by direct `find`).
- No Event Contract exists under `docs/architecture/event-contracts/**` for any event type targeting
  `platform-lifecycle` or `platform-audit` (confirmed — the ten existing Event Contracts are all
  analytical-chain events; none references either protected stream).
- No concrete registry-version-activation event instance exists anywhere (no runtime, no log —
  confirmed: `stream-registry-authority` has zero implementation in `python/`/`go/`, grep-confirmed).
- `docs/architecture/stream-registry.yaml` (fresh-read, `status: Approved`, `registry_version: v1.0`)
  carries no `effective_from` on any entry — correctly absent, since `v1.0` is the Genesis Registry,
  Chapter 8 §8.3.5's own root exception (no activation boundary required before it). It contains
  exactly the seven streams Approved `ADR-036` fixed; `context-aggregator-context` is not among them.
- `module-registry.yaml`'s `stream-registry-authority` entry (fresh-read) already registers:
  `module_type: runtime_service`, sole writer authority over `platform-lifecycle`/`platform-audit`,
  `implements_capabilities: []`, `serves_contexts: []` — **identity and writer authority are already
  decided** (`ADR-036`); **no capability/Domain Context is registered for this responsibility**, and
  no Event Contract exists for anything this module would ever emit.

**This ADR is not the registry transition itself.** It closes the one architecture boundary that sits
strictly between an Approved `ADR-051` and a genuine, appendable post-Genesis `stream-registry.yaml`
transition: **the lifecycle activation event's own Event Contract architecture** — without which no
implementation could ever produce a conforming activation event, and no new registry version could
ever satisfy Chapter 8 §8.3.1's `effective_from.event_ref` requirement with anything other than a
fabricated reference.

## What Chapter 8 / `ADR-036` / `ADR-051` already decide — not re-decided here

```text
- Exactly one canonical Lifecycle Stream, stream_id = platform-lifecycle (Chapter 8 §8.3.5, ADR-036).
- Sole writer authority = stream-registry-authority (ADR-036; module-registry.yaml, fresh-confirmed).
- The activation event is appended UNDER THE OLD active registry, never the one it activates
  (Chapter 8 §8.3.1: "Registry activation event KHÔNG được validate bằng chính registry mà nó kích
  hoạt" — E.stream_ref.registry_version = active_registry_at(pre_append_frontier) = old registry).
- The new registry becomes active only AFTER that event commits (Chapter 8 §8.3.1:
  active_registry_at(frontier ≥ n) = new_registry, n = E's own sequence).
- The activation event must identify EXACTLY the registry version being activated (Chapter 8 §8.3.1,
  "Lifecycle activation event phải định danh chính xác registry version được activate" — one of the
  conditions making active_registry_at() total + unique).
- The new registry's own effective_from points back to that exact event (Chapter 8 §8.3.1/§8.3.5).
- The activation event cannot be appended to the stream it is newly activating (Chapter 8 §8.3.5
  bootstrap-cycle prohibition) — not directly applicable to a registry-VERSION transition on an
  ALREADY-active protected stream (platform-lifecycle itself is not being newly activated), but
  stated here for completeness since Chapter 8 names it as a general lifecycle-boundary invariant.
- Context's own stream identity (context-aggregator-context) and writer authority
  (context-aggregator) are Approved and unchanged (ADR-051 v0.3).
```

## Decision

Establish the minimum Event Contract architecture, and the one minimum Domain-Context/Capability
registration it requires, necessary for a genuine post-Genesis Stream Registry activation event to
exist — governed-authored new content (per `ADR-039`'s own "first publication is governed authoring,
not mechanical transcription" rule), not transcribed from any Domain Contract, because none exists
for this control-plane concern.

**1. Contract identity — narrow, registry-version-activation-specific (not a general lifecycle-event
abstraction):**

```text
contract_id:  stream-registry-version-activated
event_type:   STREAM_REGISTRY_VERSION_ACTIVATED
```

A broader "generic lifecycle boundary event" abstraction (covering stream activation/retirement/
writer-handoff too) is explicitly **not** adopted — Chapter 8 §8.3.1/§8.3.5 describes these as
related but textually and structurally distinct boundary kinds (different required identifying
fields: a registry-version activation identifies a `registry_version`; a stream retirement identifies
a `terminal_position`; a writer handoff identifies a `handoff_boundary`), and nothing in the current
task — closing the one boundary blocking Context's own registry transition — requires deciding the
other three now. A future registry-version transition that also needs stream retirement/writer
handoff would use its own, separately-derived Event Contract(s) for those boundary kinds, governed
exactly this same way, not a shared polymorphic contract invented here speculatively.

**2. `event_class: lifecycle_boundary` (governed-authored, new vocabulary term — justified, not
reflexive):** Chapter 8 §8.3.1's own illustrative `event_class` example is explicitly open-ended
(*"event_class: decision | observation | ..."*) — the same textual latitude `candle-closed/v1.0.yaml`
already exercised to adopt `observation`, and the Candle/Structure/Regime/Feature family already
exercised to adopt `derived_fact`. Neither existing term fits: this event is neither a raw venue
observation nor a derived analytical fact — it is a platform-governance fact about the event-sourcing
topology itself, exactly the category Chapter 8 §8.3.1/§8.3.5/§8.4.1 repeatedly names "lifecycle
boundary" (*"activation/retirement/stream-creation/writer-authority-transition boundary"*). No
existing term is stretched or overloaded to cover it.

**3. Subject semantics — new minimal Business Capability/Domain Context required (the one genuine
sub-gap found while deriving this contract):** Chapter 8 §8.2.2 requires `context_id` (a registered
Domain Context, Chapter 4 §4.2) on every `subject_ref`, with no carve-out for control-plane events.
`docs/domain/context-map.yaml` (fresh-read in full) registers eleven Domain Contexts today — every
one of them a business domain (market data/structure/regime/feature/context/account/strategy/
decision/risk/execution family); none covers platform-control-plane governance facts, and
`stream-registry-authority`'s own `module-registry.yaml` entry explicitly leaves
`implements_capabilities`/`serves_contexts` empty for exactly this reason (*"no existing
context-map.yaml capability/Domain Context registered for this responsibility, and this module is not
a candidate to invent one"* — correct for a **mechanical module-registration transcription**
transaction, which is not authorized to invent architecture, but not a permanent exemption from
Chapter 8 §8.2.2's own requirement once a real event needs to name one). This ADR mints the minimum
registration, bundled here because it is strictly required to make this same Decision's own
`subject_ref` resolvable — the same "one coherent decision, one ADR" bundling `ADR-036` already used
for its own `stream-registry-authority` module identity:

```yaml
# docs/domain/context-map.yaml — addition, NOT performed by this ADR (Consequences item 2)
capabilities:
  - id: platform-control-plane
    title: Platform Control Plane
    responsibility: >
      Owns platform-governance facts about the event-sourcing topology itself (Stream Registry
      lifecycle/activation, canonical Audit preservation boundary) that no business-domain
      capability owns (Chapter 8 §8.3.1/§8.3.5/§8.4.1) — never business/domain decision semantics.
    status: active

contexts:
  - id: platform-control-plane
    title: Platform Control Plane
    capability_id: platform-control-plane
    responsibility: >
      Platform-lifecycle/audit boundary facts (registry-version activation; future stream
      activation/retirement/writer-handoff; audit-preservation) — Chapter 8 itself, not a Domain
      Contract, owns these semantics.
    owned_contracts: []   # no Domain Contract exists or is needed — Chapter 8 is the controlling
                          # authority, the same empty-field convention module-registry.yaml already
                          # uses for contract-compatibility-authority/stream-registry-authority
    status: active
```

`subject_ref` for this event type:

```yaml
subject_ref:
  context_id: platform-control-plane
  subject_kind: policy
  subject_type: StreamRegistryVersion
  subject_id: <the exact registry_version literal being activated, e.g. "v1.1">
  scope: {}
```

`subject_kind: policy` matches Chapter 8 §8.2.2's own worked example verbatim (*"RISK_POLICY_VERSION_ACTIVATED
(subject = policy version)"*) — a registry-version activation is structurally identical: a
versioned control/policy artifact becoming active. No `scope` fields are needed — Chapter 8 §8.3.1
already fixes Stream Registry as a single, unnamed, platform-wide lineage (*"Authoritative source duy
nhất"*), not multi-tenant/scoped.

**4. Required payload — exactly one field, nothing speculative:**

```yaml
payload_shape:
  activated_registry_version: {type: string, required: true, description: >
    The exact registry_version literal (ADR-039's v<major>.<minor> grammar, reused by ADR-041's own
    citation for Stream Registry) that becomes active, per Chapter 8 §8.3.1, from this event's own
    committed sequence position forward on platform-lifecycle.}
```

No predecessor/old-registry-version field, no stream-diff/added-streams field, and no content-hash
field are added. Chapter 8 §8.3.1's `active_registry_at()` function is computed purely from
`effective_from` ordering across registry files that already exist at evaluation time — it needs no
self-declared predecessor from the activation event. Exact content identity of the activated registry
version is resolved separately, by `ADR-041`'s own `docs/architecture/stream-registry-versions/
<registry_version>.yaml` snapshot path — duplicating a content hash here would create a second,
competing source for a fact `ADR-041` already owns (I-12). This is the complete payload — adding
`activated_by`/`reason`/`previous_version` or similar fields now would be exactly the "generic
lifecycle field added because it might be useful later" this task's own instruction forbids; nothing
in Chapter 8's required activation semantics (enumerated above) needs them.

**5. `allowed_streams: [{stream_id: platform-lifecycle}]`** — Chapter 8 §8.3.5: *"Mọi activation...
boundary phải được ghi trên stream này"* (the canonical Lifecycle Stream, exclusively). Not
`platform-audit` — that protected stream serves a textually distinct purpose (§8.4.1 audit-
preservation facts when a target stream loses append-eligibility), unrelated to registry-version
activation.

**6. `merge_constraints: {}`** — this event is, and must be, a **root event**: nothing in Chapter 6
§6.7's causal-predecessor semantic applies to a registry-version-activation decision, because the
decision to activate a new topology is a governed, Product-Owner/architecture-level act (an ADR
approval plus a later governed registry-authoring transaction), never itself caused by a prior
*authoritative domain event* in the sense Chapter 6 §6.7 defines causation. `causation_refs` is
therefore canonically `[]` for every instance of this event type — the identical root-event pattern
`candle-closed/v1.0.yaml` already establishes for `CandleClosed`, reused here, not invented. No
`merge_constraints.prerequisite_policy` is declared, for the same reason `candle-closed` declares
none: there is no causal prerequisite to express.

**7. `causal_state_dependency_declaration: {mode: vacuous}`** — Approved `ADR-048`'s own canonical
mechanism; valid precisely because `causation_refs` is canonically `[]` (item 6). No `roles` field
is present (`ADR-048`'s own fail-closed rule: its presence under `mode: vacuous` would itself be a
malformed declaration).

**8. Producer authority — already decided, applied not redecided:** `envelope.producer_ref.module_id:
stream-registry-authority` — the sole registered writer authority over `platform-lifecycle`
(`ADR-036`; `module-registry.yaml`, fresh-confirmed this transaction). This Event Contract does not
redeclare writer authority — Chapter 8 §8.2.4/§8.3.1 already own it; declaring it again here would
create a second, competing source for the same fact (I-12). A future Review A for the concrete
artifact must confirm the eventual implementation never allows any other `module_id` to author this
event type.

**9. `compatibility_commitment: backward_only`** — decided here, as part of this same bundled
Decision (not deferred, and not reflexively copied from `ADR-038`/`ADR-047`'s *values* — their
reasoning *pattern* is independently re-applied against this contract's own, genuinely different
topology). The scenario `backward_only` protects — an existing consumer that intentionally advances
its own pinned Event Contract binding for this `contract_id` and must keep correctly reading it — is,
for this specific contract, not speculative: Chapter 8 §8.5.2's own Registry → Lifecycle relational
invariant structurally requires **every** current and future cursor-bearing module (every module that
will ever validate any authoritative event or Decision, platform-wide, forever) to resolve
`active_registry_at()` against this exact contract's own events. This is the widest, most
structurally-guaranteed consumer base of any contract_id this repository has or will ever mint —
strictly stronger grounding than `ADR-047`'s own narrowest row (`break-of-structure-detected`, one
verified consumer). `forward_only`/`bidirectional`/no-commitment are rejected for the identical
reasons `ADR-047` rejected them for its own eight rows (Alternatives, below) — no concrete
reader/schema fact is asserted either way beyond the direction commitment itself (same
format/reader-policy gap `ADR-038`/`ADR-047` already named and left open, not resolved here).

**10. Relationship to old/new registry at append — envelope-level, not payload, not redefined:**
`envelope.stream_ref.registry_version` on the activation event itself equals the **old** active
registry (Chapter 8 §8.3.1's own `active_registry_at(pre_append_frontier)` rule) — never the one
being activated. The new registry file's own `effective_from.event_ref` is populated, after the
activation event commits, with that event's now-known `(stream_id, sequence, event_id)`. This Event
Contract does not restate either relationship in its payload — both are Chapter 8 §8.3.1's own
envelope/registry-file mechanics, applied here, not redefined (see Circularity analysis, below).

## Circularity / recording-sequence analysis (required by the governing task)

The apparent circularity — *"the new registry snapshot needs `effective_from.event_ref`, but the
event itself must identify the new `registry_version`, while being appended under the old active
registry"* — is **not a genuine circularity**. Chapter 8 §8.3.1 already fixes a non-circular,
strictly-ordered sequence; nothing new needs to be decided to make it coherent, and Git commit
ordering alone is not what resolves it (the resolution is evidentiary/sequencing, not a VCS property):

```text
Step 1 (architecture, this ADR): the activation event's Event Contract — identity, payload,
  allowed_streams, class, causation, producer authority, compatibility — is decided and governed-
  authored ONCE, ahead of any concrete transition. Already done once this ADR is Approved.

Step 2 (at the actual transition, NOT performed by this ADR): stream-registry-authority appends the
  activation event E to platform-lifecycle. E.payload.activated_registry_version = "v1.1" (a plain
  string literal, DECIDED IN ADVANCE as part of the transition's own governed plan — it requires no
  pre-existing v1.1 FILE to already exist; a string value needs no referent to be chosen). E's own
  envelope.stream_ref.registry_version = v1.0 (the OLD, already-Approved, already-existing registry)
  — E is validated entirely against authority that already exists; nothing about validating E
  requires v1.1 to exist yet.

Step 3 (at the actual transition, NOT performed by this ADR): once E has committed, E now has a real,
  stable, resolvable event_ref: {stream_id: platform-lifecycle, sequence: <E's allocated sequence>,
  event_id: <E's id>}. ONLY NOW is the new stream-registry.yaml v1.1 FILE authored, with
  effective_from.event_ref = E's own, now-known, real identity — never a placeholder, never fabricated
  ahead of E's own commit.

Step 4 (at the actual transition, NOT performed by this ADR): v1.1 is reviewed and Published under
  ADR-041's own existing Option 2 lifecycle (Draft -> reviewed -> Published immutable snapshot) —
  the SAME Draft/Published distinction ADR-041 already provides is itself the "prepared-vs-
  authoritative" distinction the governing task asked whether a new one is needed: it is not. v1.1 as
  a Draft file, even one already citing E's real event_ref, is not yet authoritative until Published
  — exactly ADR-041's existing model, applied here without modification.

Step 5: from E's own sequence position forward, active_registry_at(frontier >= E.sequence) = v1.1 —
  a pure function of which registry files exist and their own effective_from values AT THE TIME OF
  EVALUATION, never a separately-tracked runtime "activation" flag. Nothing can treat v1.1 as active
  before its own file, with the real effective_from, is actually Published — there is no race window
  where v1.1 could be prematurely "active" merely because E has committed, because "active" is
  resolved by consulting the registry FILES, not E itself.
```

**No new platform-wide activation protocol decision is genuinely required.** The sequencing above is
a direct, mechanical application of Chapter 8 §8.3.1's own already-Locked text (quoted in full,
"What Chapter 8 already decides," above) plus `ADR-041`'s own already-Approved Draft/Published
distinction for the registry file itself — composed, not extended or amended. The one piece that
did **not** already exist, and that blocked this sequence from being executable at all, was Step 1 —
the activation event's own Event Contract — which this ADR now supplies.

## Registry-version identity treatment

**`v1.1` is uniquely, mechanically determined by already-existing authority** — not a new decision:

```text
1. ADR-039 fixes the v<major>.<minor> grammar and its breaking/non-breaking mapping (major+0.minor
   reset on breaking; minor+1 on non-breaking), reused by ADR-041's own citation for Stream Registry.
2. Chapter 10 §10.3.1's own minimal classification principles: adding a new, independent streams[]
   entry (context-aggregator-context) changes nothing about any of the seven existing entries'
   identity/writer_authority/status/sequence_policy/genesis_position — they remain byte-identical.
   This is squarely "thêm element KHÔNG ảnh hưởng consumer hiện tại" — the additive, non-breaking
   case §10.3.1 itself describes ("thêm element optional có semantic/default an toàn cho reader chưa
   biết nó -> có thể non-breaking"); no existing reader of v1.0's seven streams is made invalid by an
   eighth, independent entry appearing in v1.1.
3. Therefore: non-breaking -> minor increments only, major unchanged -> v1.0 -> v1.1, by direct,
   mechanical application of (1)+(2) — no new semantic-versioning policy is invented or needed; the
   platform does not need, and this ADR does not create, a general SemVer policy beyond what
   ADR-039/ADR-041/Chapter 10 §10.3.1 already jointly fix.
```

This determination is recorded here for the benefit of the later, separate, mechanical registry-
authoring transaction (`ADR-051`'s own Track A) — this ADR does not itself create any `v1.1` file or
snapshot.

## Alternatives considered

1. **Narrow, registry-version-activation-specific Event Contract (chosen).** Minimum architecture
   sufficient to prove Chapter 8's required activation semantics for exactly the one boundary blocking
   Context's registry transition; no broader abstraction invented speculatively.
2. **A single, general-purpose "lifecycle boundary event" contract covering activation, retirement,
   and writer-handoff together.** Rejected — Chapter 8 §8.3.1/§8.3.5 describes three structurally
   distinct identifying shapes for these boundary kinds (`registry_version` vs. `terminal_position`
   vs. `handoff_boundary`); forcing one payload shape to cover all three now, before any of the other
   two is actually needed, would either invent unused optional fields or a discriminated-union shape
   neither Chapter 8 nor the governing task's own instruction asks for — directly the "do not add
   generic fields merely because they might be useful later" the governing task forbids.
3. **Defer the Domain-Context/Capability registration to a future, separate ADR.** Rejected — it is
   strictly required to make THIS Decision's own `subject_ref` resolvable (Chapter 8 §8.2.2's `context_id`
   cardinality is unconditional); deferring it would leave this ADR's own Decision incomplete and
   unimplementable, the same reasoning `ADR-036` already applied when it bundled the
   `stream-registry-authority` module identity into its own Decision rather than deferring it.
4. **Treat registry-version identity as an open decision requiring its own future ADR.** Rejected —
   `ADR-039`/`ADR-041`/Chapter 10 §10.3.1 already jointly and mechanically determine `v1.1` for this
   specific, purely-additive change; inventing a reason to re-decide an already-mechanically-resolved
   question would itself violate `G-ADR-003`.
5. **No ADR — treat the activation Event Contract as a mechanical transcription.** Rejected — there is
   nothing to transcribe FROM (no Domain Contract declares any of `event_type`/`event_class`/
   `payload_shape`/`compatibility_commitment` for this concern); `ADR-039`'s own text is explicit that
   a first-publication `event_class`/payload authoring act is governed authoring, and Chapter 0 §4b's
   Event-Schema-change trigger fires independently of whether a Domain Contract exists to transcribe
   from.
