# ADR-032: Data Layer reference-resolution architecture

**v0.2 — bounded correction (2026-08-19), closes `ADR032-A-MAJ-01` (Major, Review A), vai trò:
`ADR-032 Bitemporal Contract Correction Executor`.** v0.1 §B.3 point 1 required a "point-in-time-bound"
reference query using a single, ambiguous temporal parameter. Chapter 5 (Locked) requires TWO
independent axes — effective applicability (§5.1 `effective_time`) and recorded-time/knowledge
visibility, disambiguated where needed by an opaque ordering position (§5.3 Replay Cursor) — not
one. A single parameter conflates the two and can permit exactly the look-ahead Chapter 5/I-3 exist
to prevent (a fact's own effective_time does not bound what Ride had recorded about it). §B.3 below
is rewritten so the contract requires both axes as separate, mandatory, independent inputs, with
deterministic resolution from their intersection. Nothing else in this ADR changes: language
decision (Go, §B.1), `market-reference-service` sole-authority / `market-data-ingestion`
query-consumer-only boundary (§B.2), no dependency-graph change, no Domain Contract semantics
touched (§A/§C unchanged in substance), ADR stays Draft, no Structure/Regime, LIVE still
NOT_AUTHORIZED (this ADR never referenced LIVE). `ADR032-A-MAJ-01`: `CLOSED_BY_BOUNDED_CORRECTION /
PENDING_REVIEW_A_REREVIEW` — NOT claimed `CLEAN`; a fresh Review A pass against this v0.2 boundary is
still required before Independent Review B / Product Owner approval.

## ADR Scope Rule check (Chapter 0 §4b) — ADR Required

This decision is **ADR Required**, not ADR Optional/Not Required: it fixes the implementation
language of `market-reference-service` (a `module-registry.yaml`-registered module) and it fixes a
**cross-module runtime contract** — the reference-resolution mechanism `market-data-ingestion`
depends on, and by extension any future consumer of `market-reference-service` (`risk-gateway`,
`execution-engine`, and any module needing Instrument/Venue/calendar/precision facts). Chapter 0
§4b's "ADR Required" row lists "quyết định ảnh hưởng >1 module" as sufficient on its own (disjunctive
with "khó đảo ngược" — the OR-not-AND lesson `monorepo.md` §6 and `naming.md`/`logging.md`/
`config.md`'s own ADR-scope history already established repeatedly in this repository). This
decision affects at least two modules directly (`market-reference-service`,
`market-data-ingestion`) and is a cross-module runtime contract by its own subject matter — it
satisfies the ">1 module" clause on its own, independent of reversibility.

## Context

Phase 3 Data Layer Batch 01 (`docs/CHANGELOG.md`, 2026-08-19) implemented `market-data-ingestion` in
Go and explicitly deferred `market-reference-service`, escalating two blockers rather than deciding
them silently:

1. `market-reference-service`'s implementation language does not resolve under existing authority —
   `ADR-008` pins Python/Go by **layer capability nature**, not by module name, and
   `market-reference-service`'s responsibility (owns authoritative Instrument/Venue identity,
   precision/tick/lot metadata, trading calendar/session) does not obviously match either named
   layer.
2. `market-data-ingestion` already depends on `market-reference-service`
   (`module-registry.yaml`, `depends_on: [market-reference-service]`) for exactly three things
   candle.md itself requires but does not own: canonical Instrument/Venue identity (candle.md §14
   venue neutrality), trading-calendar/session-derived window boundaries (candle.md §14, Chapter 5
   bitemporal model), and — for full I-9 compliance once quantization is wired up —
   precision/tick/lot metadata. No architecture-level document has yet fixed **how** that dependency
   is satisfied (query shape, temporal-applicability semantics), only **that** it exists.

This ADR resolves both blockers at architecture level only. It does not build
`market-reference-service`, does not touch Structure Engine/Raw Regime Engine, and does not change
`module-registry.yaml`'s existing dependency edge.

## B. Architecture/runtime mechanism this ADR decides

### B.1 Implementation language: **Go**

Evaluated against ADR-008's actual stated rationale (capability nature, not module-name match):

```text
Python rationale (I-2 Decision Parity + data-science ecosystem) — DOES NOT APPLY.
  market-reference-service is not part of the Decision Pipeline's Research/Production dual-execution
  surface (Structure/Regime/Feature/Strategy/Decision/Backtest) — I-2 does not require it to share a
  code path across execution modes the way Strategy/Decision logic does. It has no use for
  Polars/Pandas/TA-Lib/NumPy: identity/metadata/calendar lookups are not analytical/numerical
  research work.

Go rationale (concurrency, I/O, reliability) — PARTIALLY APPLIES, and applies MORE than Python's.
  market-reference-service does not have Market Data Ingestion's specific "many simultaneous WS
  connections" profile — it is queried, not connected-to. But its actual profile — a
  synchronously-queried, command/query-driven reference-data service that other runtime services
  depend on for correctness-critical lookups, with reliability and low-latency response as the
  primary non-functional requirement (I/O-bound request/response, not analytical computation) — is
  a materially closer match to Go's stated rationale than to Python's. Zero part of Python's
  rationale applies; part of Go's does.

Practical (non-ADR-008-textual) factor, stated separately so it is not conflated with the ADR-008
  analysis above: market-data-ingestion (Go, already built) is market-reference-service's only
  current consumer (module-registry.yaml depends_on), and Risk Gateway/Execution Engine — both
  already Go per ADR-008 — are the most likely future consumers of the same kind of reference
  lookup (instrument/venue identity, precision). Same-language same-process-or-adjacent-service
  calls avoid a cross-language RPC/serialization boundary for a foundational, correctness-critical,
  low-latency dependency. This factor is secondary to the ADR-008 rationale match above, not a
  substitute for it — it does not by itself justify a language choice ADR-008's actual rationale
  argued against.

Rust: NOT evaluated as a candidate and NOT introduced — ADR-008 reserves Rust for a future
  sub-millisecond critical-path change, explicitly requiring its own ADR (ADR-008 Decision, third
  bullet). Nothing about this ADR changes that.

Decision: Go, on ADR-008 capability-nature grounds (I/O + reliability rationale applies; Python's
  I-2/data-science rationale does not apply at all), reinforced by the practical same-language
  consumer factor stated above as a secondary consideration.
```

### B.2 Runtime responsibility/boundary between the two modules

```text
market-reference-service remains the SOLE authoritative owner of Instrument/Venue identity,
  precision/tick/lot metadata, and trading calendar/session (I-12) — unchanged from
  module-registry.yaml's existing owns_authoritative_state: true. It owns state transitions via
  command (registration/correction), and answers queries; it emits events for its own authoritative
  facts (module-registry.yaml: emits: [event, query], unchanged).

market-data-ingestion is a QUERY CONSUMER ONLY of this boundary. It:
  - MUST resolve venue-raw references, window boundaries, and (once wired) precision/tick/lot
    metadata exclusively through market-reference-service's query contract (§B.3) — never by
    independently inferring/hardcoding/caching-as-truth any of the three.
  - MUST NOT become a second authoritative source for identity/calendar/precision (I-12) — any local
    caching it performs (a performance optimization, not decided by this ADR) is non-authoritative,
    bounded, and re-resolvable; it is not a substitute source of truth if market-reference-service
    is unavailable or the cache is stale.
  - MUST NOT gain a command/mutation path into market-reference-service — the existing
    module-registry.yaml consumes: [query] for market-data-ingestion is preserved exactly; this ADR
    does not add a command edge.

No new dependency edge is created or proposed. module-registry.yaml already has
  market-data-ingestion.depends_on: [market-reference-service] — this ADR does not touch
  module-registry.yaml at all. Any future edge from risk-gateway/execution-engine to
  market-reference-service is explicitly OUT OF SCOPE — not decided, not implied, not precluded;
  that is each of those modules' own future build-time or ADR decision.
```

### B.3 Reference-resolution mechanism (contract shape, not implementation)

```text
For all three lookups market-data-ingestion needs — identity resolution, calendar/session window
  resolution, precision/tick/lot metadata — market-reference-service exposes a QUERY contract
  (module-registry.yaml: consumes: [command] for mutation, emits: [..., query] for answering reads;
  unchanged) with the following invariants, decided here at architecture level:

1. TWO-AXIS bitemporal query contract (v0.2 — see correction banner above; closes
   `ADR032-A-MAJ-01`). Chapter 5 (Locked) requires two independent axes for any bitemporal fact —
   effective applicability (§5.1 `effective_time`) and recorded-time/knowledge visibility (§5.2,
   disambiguated where multiple facts share a `recorded_time` by the opaque ordering position §5.3
   defines for Replay Cursor). Every query that can affect a decision-relevant output (which, for
   market-data-ingestion, includes window-boundary resolution — candle.md §14 — since a wrong window
   boundary corrupts the resulting Candle's identity) MUST supply BOTH of the following as separate,
   independent inputs; neither substitutes for the other:

   a. **Effective applicability input** — the effective market/reference time or interval (Chapter 5
      §5.1 `effective_time`) for which the Instrument/Venue/calendar/precision fact must apply (e.g.
      "what session boundary covers window_start 10:00?", "what precision applied to this instrument
      at this effective moment?").
   b. **Knowledge visibility boundary** — `recorded_time` / Replay Cursor (Chapter 5 §5.2/§5.3),
      including an opaque ordering position where §5.3 requires one to disambiguate facts sharing the
      same `recorded_time` — limiting the answer to reference facts Ride had ACTUALLY RECORDED by
      that historical execution point. This is the same Recorded Time boundary §5.3 defines for
      event-log replay visibility, applied here to `market-reference-service`'s own facts, not
      invented anew.

   The resolved answer MUST be the deterministic result of the **intersection** of these two
   constraints: facts effective for the requested applicability window/instant AND facts visible
   (`recorded_time` ≤ the supplied knowledge boundary, ordering-position-disambiguated per §5.3 where
   applicable) at the supplied knowledge/replay boundary. Neither axis alone determines the answer.

   Explicitly, to close the exact ambiguity `ADR032-A-MAJ-01` identified:
   - `effective_time` alone MUST NOT control visibility — a fact effective for a given moment is not
     thereby visible at that same moment; visibility is governed ONLY by axis (b), consistent with
     Chapter 5 §5.1/§5.3's own worked example (candle `effective_time` 10:00, correction
     `recorded_time` 10:07 — Replay at cursor 10:03 sees the original, never the correction, even
     though both share the same effective window).
   - Corrections to a reference fact recorded LATER than the supplied knowledge boundary MUST NOT
     appear in an earlier Replay/Backtest query against that boundary — the same look-ahead
     prohibition Chapter 5 §5.3/I-3 already establish for the event log, applied here to
     `market-reference-service`'s own corrections (database-architecture.md §5:
     `market-reference-service` correction is "via new event" — the same append-only/no-repaint
     discipline, not a new one).
   - Current wall clock or `market-reference-service`'s current live state MUST NOT be used to answer
     a bounded historical query — the caller-supplied knowledge boundary is authoritative for that
     query, not "whatever is true right now" (Chapter 5 §5.3: "Replay không dùng đồng hồ hệ thống
     hiện tại").
   - Exact transport/API serialization of these two inputs (parameter names, wire format, whether the
     ordering position is an offset/sequence/something else) remains explicitly DEFERRED to
     `market-reference-service`'s own build transaction (unchanged — see points 3/4 below). This
     correction fixes the CONTRACT SHAPE (two mandatory, independent axes; deterministic intersection
     semantics) — it does not invent the concrete calendar/session/precision algorithm (§C, unchanged)
     or any serialization detail.
2. Decision-relevant reference answers are Chapter 8 §8.1.1 Referenced Authoritative Artifacts once
   consumed by a decision-relevant path, and I-5-observable dependencies: a market-data-ingestion
   consumer that uses a reference answer to shape an authoritative Candle event MUST be able to
   capture that dependency (at minimum its immutable content identity) rather than silently
   re-resolving it live and unrecorded on every Replay. This ADR fixes the OBLIGATION; it does not
   fix candle.md's envelope schema to carry it (§C below — that is a Domain Contract change, out of
   this ADR's authority).
3. Transport/deployment topology (in-process library call vs. network RPC; synchronous request/
   response vs. some other shape) is explicitly NOT decided here — same language (§B.1) makes
   either viable, and Package 1.3-A already established the precedent that execution-topology
   choices are an Engineering/Phase-1(now: Phase-3-build-time) decision
   (`structure-regime-architecture.md` §3: "cơ chế thực thi cụ thể thuộc Engineering/Phase 1
   execution-topology decision... KHÔNG quyết định tại Package 1.3-A"). market-reference-service's
   own build transaction decides this, the same way market-data-ingestion's build transaction
   decided its own internal event-ID generation and stream-topology placeholders without that being
   an architecture decision.
4. Query API shape (exact method/endpoint signatures, error taxonomy, request/response schema) is
   NOT decided here — same reasoning as point 3; it is market-reference-service's own build-time
   elaboration, analogous to how market-data-ingestion's own envelope/precedence/gap package APIs
   were implementation-level decisions made at ITS build transaction (see
   go/market-data-ingestion/README.md, "Implementation-level decisions made at this build
   transaction"), not architecture-level ones.

Known implementation gap this ADR surfaces (v0.2 — restated for the two-axis contract; not fixed
  here — no code changes in this transaction, per explicit task instruction):
  market-data-ingestion's already-built internal/reference.Provider port (Batch 01) does not
  currently implement this two-axis contract at all: ResolveIdentity carries no temporal parameter
  whatsoever, and WindowFor takes only a single observation instant `t` — neither an explicit
  effective-applicability input (point 1.a above) nor a separate knowledge/replay-cursor boundary
  (point 1.b above). It was built against a Fake sufficient for Batch 01's scope, before this
  two-axis contract-shape decision existed. Bringing internal/reference.Provider in line with
  invariant 1 above is a REQUIRED future bounded code alignment — to be performed as its own
  transaction after ADR-032 reaches Product Owner approval, not performed by this correction.
```

## Decision (summary)

`market-reference-service` will be implemented in **Go**, on ADR-008 capability-nature grounds.
`market-reference-service` remains the sole authoritative owner of Instrument/Venue identity,
precision/tick/lot metadata, and trading calendar/session; `market-data-ingestion` (and any future
consumer) resolves those exclusively through `market-reference-service`'s query contract, which
architecture-level requires a two-axis bitemporal query — effective applicability AND knowledge/
Replay-Cursor visibility, resolved by deterministic intersection (§B.3, v0.2) — the exact API shape
and internal calendar/session/precision-computation mechanism are deferred to
`market-reference-service`'s own build transaction, consistent with how `market-data-ingestion`'s
own implementation-level details were resolved at its build time rather than at architecture time.
