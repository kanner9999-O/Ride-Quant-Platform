# ADR-015: Official Phase 1 Module Decomposition and Dependency Graph (Package 1.1)

**PROPOSED — status: Draft, chưa Approved.** ADR này tự nó KHÔNG approve/consolidate Package 1.1 — chỉ khi Product Owner `Approve` ADR này, VÀ Package 1.1 tự nó qua đúng consolidation transaction riêng (`system-decomposition.md` §15), Package 1.1 mới có thể `Consolidated Stable`.

**Context:** [`docs/architecture/phase-1-plan.md`](../architecture/phase-1-plan.md) v0.2 (`Consolidated Stable`) ủy quyền Package 1.1 thiết lập official module inventory + dependency graph cho Phase 1. Package 1.1 candidate v0.2 ([`module-registry.yaml`](../architecture/module-registry.yaml) blob `2dd1e1fae8f886b605896864b432f3f79a3726d1`, [`system-decomposition.md`](../architecture/system-decomposition.md) blob `45d745315ba36ea4ca53b5bb4bcd2aa6ca076293`) đã qua bounded correction (đóng `P11-A-MAJ-01`/`P11-A-MAJ-02`/`P11-A-MIN-01`) và bounded Review A + independent bounded Review B **CLEAN** (Blocker 0/Major 0/Minor 0, Backward Consistency Check NO CONFLICT). `system-decomposition.md` §12 Decision 1 tự xác định: thiết lập CHÍNH THỨC module dependency graph lần đầu tiên là quyết định thuộc diện **ADR Required** ([Governance §4b](../constitution/00-governance.md): "thay đổi Module Taxonomy/dependency graph"). ADR này là cơ chế governance duy nhất hợp lệ để quyết định câu hỏi đó — Package 1.1 KHÔNG được tự approve chính graph nó đề xuất.

**Decision question:** Liệu 22-module inventory + dependency graph tại Package 1.1 v0.2 (blob đã pin ở trên) có trở thành official Phase 1 module decomposition baseline hay không.

**Decision (đề xuất — CHƯA có hiệu lực cho tới khi Approved):**

Chọn **Alternative A** — Approve Package 1.1 v0.2 22-module decomposition làm official baseline, pin CHÍNH XÁC:

```text

```

Pin này là **exact-artifact reference** ([Chapter 10 §10.8](../constitution/10-compatibility-capability-contract.md) pattern) — một update tương lai cho `module-registry.yaml`/`system-decomposition.md` (version mới, blob mới) KHÔNG tự động trở thành official baseline; nó đòi hỏi ADR mới `supersedes` ADR này (Chapter 11 §11.8), hoặc — nếu thay đổi không đổi dependency graph/taxonomy đã pin — một correction transaction thường không cần ADR mới, tùy đúng bản chất thay đổi tại thời điểm đó.

**Alternatives considered:**

```text
A. Approve Package 1.1 22-module decomposition as proposed. [RECOMMENDED]
   Ưu điểm: đã qua bounded correction + Review A/B CLEAN + BCC NO CONFLICT; granularity khớp
   trực tiếp 15 Domain Context đã đăng ký (context-map.yaml) + established reference pipeline
   (docs/architecture/README.md); mọi forbidden_dependencies đã script-verified enforce đúng
   constraint đã pin ở Phase 0/ADR trước.
   Nhược điểm: 22 module là con số tương đối lớn cho Phase 1 khởi đầu — rủi ro governance
   overhead (mỗi module một entry cần maintain).

B. Coarser decomposition — gộp module (ví dụ: gộp Execution Engine + Execution Result Processor
   + Fill Processor thành một "Execution Chain" module; gộp Command/Query/API Surface vào từng
   engine thay vì module riêng).
   Ưu điểm: ít entry hơn, registry đơn giản hơn.
   Nhược điểm: VI PHẠM trực tiếp responsibility boundary đã pin ở Domain Contract layer — Order
   (order.md)/ExecutionResult (execution-result.md)/Fill (fill.md) là ba Domain Context riêng
   biệt đã đăng ký ĐỘC LẬP tại context-map.yaml (order-management, execution-result-management,
   fill-management, mỗi context một owned_contracts riêng) — gộp module sẽ tạo module sở hữu
   NHIỀU Domain Context với NHIỀU capability khác biệt, có nguy cơ god-module (Chapter 7 §7.1
   guardrail) mà không qua đúng hybrid-ADR test 4-điều-kiện cho từng cặp gộp. KHÔNG chọn.

C. Finer decomposition — tách thêm (ví dụ: tách OrderCreationAttempt/OrderSubmissionRequest
   khỏi Order thành module riêng; tách mỗi Workflow Invariant thành module riêng).
   Ưu điểm: bounded hơn nữa, mapping 1:1 chặt hơn với từng sub-entity.
   Nhược điểm: OrderCreationAttempt/OrderSubmissionRequest là sub-entity CỦA order-management
   context (context-map.yaml), KHÔNG phải context riêng — tách thành module riêng sẽ vi phạm
   "module boundary ≠ domain entity boundary" (Chapter 4 §4.4, Package 1.1 §3 nguyên tắc 4: KHÔNG
   one-module-per-domain-entity). Tăng governance overhead không tương xứng lợi ích tại Phase 1
   khởi đầu. KHÔNG chọn.

D. Defer official graph — để Package 1.2–1.6 tự định nghĩa module boundary độc lập, không official
   baseline chung.
   Ưu điểm: tránh ADR ngay bây giờ, "linh hoạt" hơn cho từng package.
   Nhược điểm: VI PHẠM trực tiếp mục đích Package 1.1 (phase-1-plan.md §8 — Package 1.1 CHÍNH LÀ
   nền tảng mọi package khác phụ thuộc); tạo rủi ro competing/conflicting module identity giữa
   Package 1.2–1.6 (mỗi package tự đặt tên module riêng cho cùng một capability), vi phạm I-12
   (Single Source of Truth cho module identity). Defer KHÔNG giải quyết được vấn đề ADR-Required
   đã surface tại system-decomposition.md §12 — nó chỉ trì hoãn, và Governance §4b không cho phép
   "trì hoãn vô thời hạn" một quyết định thuộc diện ADR Required khi quyết định đó đã được đề
   xuất cụ thể. KHÔNG chọn.
```
