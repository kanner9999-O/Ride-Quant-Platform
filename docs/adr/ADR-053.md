# ADR-053: Context Output Event Contract Classification and Compatibility Policy

**Context:** Approved `ADR-051` (`docs/adr/ADR-051.md`) pins Context's own output logical
stream identity (`context-aggregator-context`) and sole writer authority
(`context-aggregator`) — but explicitly reserves two fields to "separate, later, governed
work" (ADR-051 Decision item 8): `event_class` and `compatibility_commitment` for the two
future Event Contracts, `market-context-snapshot` and `market-context-fact-invalidated`
(`docs/domain/context.md` §3/§4). Neither field is selected by any existing authority for
these two specific `contract_id`s. This ADR closes exactly those two fields, and only
those two, so that Draft authoring of the two Event Contract artifacts may proceed safely
afterward.

**Scope boundary (explicit, matching the governing WP's own instruction):** this ADR does
**not** decide Strategy input authority, does not rewrite `docs/domain/context.md`, does
not change `context-aggregator`'s Module Taxonomy classification or
`owns_authoritative_state`, does not touch Stream Registry topology (Approved `ADR-051`,
unchanged), does not perform any lifecycle activation, does not implement runtime, and
does not redesign `event_class` as a generic platform-wide taxonomy — it mints one new,
narrowly-scoped value for exactly these two `contract_id`s.

## 1. `event_class` — the gap, fresh-confirmed

[Chapter 8](../constitution/08-event-model.md) §8.2's own worked example (`event_class:
decision | observation | ...`) and §8.2.5 (an Event Contract "owns" `event_class`,
independently of `schema_version`) together confirm `event_class` is an **open-ended**
enumeration — the Constitution fixes only `decision`'s own normative meaning (§8.4:
"Event Contract khai báo tường minh bằng đúng một field canonical `event_class: decision`"
triggers `decision_time`/`decision_context_cursor` cardinality) and gives `observation` as
an illustrative value, never a closed list. No chapter or Approved ADR selects a value for
`market-context-snapshot`/`market-context-fact-invalidated`.

**Fresh survey of every currently Published Event Contract's own `event_class`** (not
inherited from any prior transaction's conclusion):

```text
candle-closed, candle-corrected                          -> observation
break-of-structure-detected, change-of-character-detected,
  structure-fact-invalidated, structure-recomputed        -> derived_fact
regime-classified, regime-fact-invalidated                -> derived_fact
feature-computed, feature-fact-invalidated (v1.0 and v1.1) -> derived_fact
```

**Neither existing value fits, on the merits — not merely by association with who
currently uses them:**

- **`observation`** is reserved for first-hand capture of external, not-yet-authoritative
  reality — `candle-closed`/`candle-corrected` are root events (`causation_refs: []`,
  `candle-closed`'s own declaration is `mode: vacuous`), never derived from any other
  authoritative fact. `MarketContextSnapshot`/`MarketContextFactInvalidated` are the
  structural opposite: never a root event (`context.md` line 156: `causation_refs` KHÔNG
  BAO GIỜ rỗng), always downstream of seven (or, for a replacement, a variable set of)
  upstream authoritative facts. `observation` does not fit.
- **`derived_fact`** is used, so far, exclusively by Type 1 Compute Engines
  (`structure-engine`, `raw-regime-engine`, `feature-engine`; `module-registry.yaml`:
  each `owns_authoritative_state: true`) whose own producers **compute new domain
  knowledge** from upstream inputs (BOS/CHoCH orientation from Swing/Candle;
  classification from Candle evidence; metrics from upstream facts) — genuinely new
  authoritative conclusions that did not exist before. `context-aggregator` does
  structurally the opposite, by `context.md`'s own explicit, repeated invariant: §17 —
  Context never recomputes, never re-derives, never reproduces Feature's formulas;
  §3's `context_values` invariant (line 162) — every value is a **direct copy** of the
  corresponding upstream fact's own already-published field, with Context "KHÔNG tự tính
  toán lại, KHÔNG diễn giải thêm ý nghĩa" (no recomputation, no added interpretation).
  This is not a labeling risk by association — it is a genuine semantic mismatch:
  `derived_fact`'s established meaning in this repository is "new authoritative
  conclusion computed from inputs," and Context's own Domain Contract forbids exactly
  that operation for its own output.

This confirms Chapter 7 §7.4's own Type 1/Type 2 distinction is the correct lens: Context
performs exactly the operation §7.4 names as permitted for a Projection — "fold/aggregate
event theo type; tính giá trị dẫn xuất thuần túy từ event đã có" (fold/aggregate by event
type; compute values purely derived from already-existing events, i.e. assembly, not
synthesis) — and explicitly contemplates a Projection emitting "operational metadata
event về chính nó" (an operational/record-of-itself event), provided it is never used as
an authoritative source substituting for the original domain event.

## 2. `event_class` — Decision

**Mint `event_class: projection_record`**, scoped exactly to `market-context-snapshot`
and `market-context-fact-invalidated` (`contract_id`s), defined as:

> An immutable, replayable Chapter 8 §8.2 envelope-bearing record produced by a Type 2
> Projection's (`module-registry.yaml`) own deterministic fold/aggregate computation over
> already-authoritative upstream facts, carrying only values copied or derived from those
> facts without introducing new authoritative domain conclusions. A `projection_record`
> event:
> - is **never** itself an authoritative source for the domain concept(s) its inputs
>   belong to (Chapter 7 §7.4: "Projection không bao giờ là authoritative source cho một
>   domain concept");
> - does **not**, by virtue of this classification alone, change its producer's
>   `owns_authoritative_state` value in `module-registry.yaml`;
> - does **not** decide whether any future consumer's own treatment of it constitutes
>   reliance on authoritative input — that remains each future consumer's own, separately
>   governed decision;
> - still carries full Chapter 8 §8.2 envelope/`causation_refs`/replay obligations like
>   any other authoritative event record — this is a genuine, pinned, immutable record,
>   not a lightweight operational signal (e.g. "checkpoint advanced," `module-registry.yaml`
>   `context-aggregator.notes`'s own already-cited category) and not a Decision event
>   (`event_class: decision` remains exclusively Chapter 8 §8.4's own category; Context
>   never emits one, `context.md` §17/§20, Approved `ADR-014`).

**Why this does not resolve, and is not used to resolve, the preserved Context
authority/terminology gap (`ADR-051` item 4, `m3-context-closure-derivation-001.md` §5
D1):** minting a *new* value, rather than reusing `derived_fact` (which would read as a
quiet claim of authoritative-conclusion status) or inventing a value that asserts
non-authoritative status more strongly than existing authority has actually decided,
keeps the gap exactly as open as `ADR-051`/`feature-context-architecture.md` §13/`python/
context-aggregator/README.md` already left it. `projection_record`'s own definition above
is deliberately a **record-integrity** description (immutable, replayable, envelope-
bearing, fold/aggregate-sourced) — the same record-integrity-vs-authoritative-domain-
ownership boundary those artifacts already established — not a ruling on whether
`context.md` §2's own "authoritative event record" wording is correct or should change.
This ADR does not touch that wording and does not require it to be corrected as a
consequence.

## 3. `compatibility_commitment` — the gap, fresh-confirmed

Chapter 10 [§10.3.1](../constitution/10-compatibility-capability-contract.md) fixes the
**choice space** (`backward_only | forward_only | bidirectional | explicit no-commitment`)
and **mandates** every published contract declare one explicitly — absence is an invalid
declaration, `eligible = false` (§10.3.1) — but "does not itself select a value for any
specific contract" (the exact test Approved `ADR-038`'s own Scope classification already
applied, and Approved `ADR-047`'s own Scope classification independently re-applied for
eight different `contract_id`s). Neither `ADR-038` (Feature's own two output contracts
only) nor `ADR-047` (the eight Context-**upstream** `contract_id`s only — Candle ×2,
Structure ×4, Regime ×2) extends to, or was ever asked to decide, Context's own **output**
`contract_id`s. No other Approved ADR addresses them. The gap is genuine and unresolved.

**Fresh-confirmed consumer topology (honestly stated, not inflated to match prior
precedent):** `docs/domain/context-map.yaml`'s `context-projection` entry has **zero**
`provider_context_id: context-projection` relationships registered — no downstream
consumer of Context's own output exists in the context map today (Strategy/Decision are
`Package 0.2-C`, "chưa author," `context.md` §20/§21). This differs from `ADR-038`
(`context-aggregator` already exists as a real, implemented, verified consumer of
Feature's output) and `ADR-047` (verified current consumers listed per row) — unlike
those two ADRs, this ADR cannot cite a verified `>1 module` relationship for Context's
output today.

## 4. `compatibility_commitment` — ADR Scope re-confirmed despite the weaker consumer fact

[Chapter 0 §4b](../constitution/00-governance.md)'s table lists independent, disjunctively
sufficient triggers — "thay đổi Event Schema" is its own category, textually separate
from "quyết định ảnh hưởng >1 module hoặc khó đảo ngược." Selecting the initial
`event_class`/`compatibility_commitment` policy for two brand-new `contract_id`s is
squarely an Event Schema decision in the sense every other such decision in this
repository's own history has already been treated (`ADR-036`, `ADR-038`, `ADR-039`,
`ADR-041`, `ADR-046`, `ADR-047`, `ADR-048`, `ADR-051` — zero counterexamples of an
analogous first-time Event-Contract-policy decision being waved through `ADR_NOT_REQUIRED`
in this repository). The "Event Schema change" trigger fires on its own, independent of
whether a verified current consumer already exists — the absence of one here is a fact
worth recording honestly (§3 above), not a reason the trigger fails to fire.
`ADR_REQUIRED` confirmed.

**G-ADR-004 (packaged jointly with `event_class`, per the governing task's own
instruction — same two artifacts, same publication boundary, one coherent decision, not
one ADR per field):**

```text
1. Existing authority/alignment resolves this without a new decision? NO --
   Chapter 8's event_class enum is open-ended by design; Chapter 10 §10.3.1
   fixes only the choice space + mandatory-declaration rule for
   compatibility_commitment. Neither selects a value for these two
   contract_ids. ADR-038/ADR-047 cover different, named contract_id sets
   only.
2. Genuine architecture decision, not cheaply reversible? YES -- same class
   ADR-038/ADR-047 already treated as ADR-required for the identical kind
   of per-contract_id policy selection.
3. Chapter 0 §4b trigger fires independently? YES -- "thay doi Event
   Schema" fires on its own (see above), disjunctively sufficient without
   needing a verified >1-module relationship.
4. Authored merely to complete a prior transaction (G-ADR-003)? NO --
   ADR-051 explicitly, deliberately scoped these two fields OUT of its own
   Decision (item 8) as "separate, later, governed work" -- this ADR is
   that separate work, derived directly from Chapter 8 §8.2.5/Chapter 10
   §10.3.1's own text requiring an explicit per-contract_id decision, not
   from any gap ADR-051 merely left unfinished.
Result: ADR REQUIRED confirmed, for event_class and compatibility_commitment
jointly, packaged as one artifact (MODEL C precedent, same as ADR-047).
```

## 5. `compatibility_commitment` — Decision

Each of the following two Event Contracts commits to **`backward_only`** compatibility —
Chapter 10 §10.3.1's exact semantic: *"consumer CŨ vẫn đọc/validate đúng dữ liệu MỚI"* (an
existing consumer remains able to correctly read/validate new data under a later contract
version claimed compatible). This is an explicit **policy commitment this ADR adopts**,
consistent with the unanimous precedent already set by every one of the ten currently
Published Event Contracts (Candle ×2 under `ADR-047`, Structure ×4 under `ADR-047`,
Regime ×2 under `ADR-047`, Feature ×2 under `ADR-038`) — all ten already committed
`backward_only`, zero exceptions. This ADR does not assert that any concrete future
schema delta already satisfies this, and does not assert or require any particular
unknown-field-tolerance behavior of any consumer's reader (the same explicit disclaimer
`ADR-047` already states, reused by citation, not re-litigated).

| `contract_id` | owning Domain Contract | producer_module | verified_current_consumers | compatibility_commitment | rationale |
|---|---|---|---|---|---|
| `market-context-snapshot` | Context (`context.md` §3) | `context-aggregator` | **none verified today** (Strategy not yet authored, `context.md` §20/§21) | `backward_only` | Proactive commitment, consistent with this repository's unanimous existing practice of committing `backward_only` for every Published Event Contract regardless of whether a consumer runs yet (`ADR-038` committed for Feature's two contracts before `context-aggregator`'s own runtime integration existed either). Protects whichever future consumer (most plausibly Strategy, per `context-map.yaml`'s own `context-projection` responsibility text) binds to this contract from being broken by a later claimed-compatible evolution. |
| `market-context-fact-invalidated` | Context (`context.md` §4) | `context-aggregator` | **none verified today** | `backward_only` | Same rationale as `market-context-snapshot`; this is its correction/invalidation counterpart (`context.md` §4's `invalidated_fact_ref`/minimal-complete direct-cause-set payload) — the same advancing-consumer protection concern `ADR-047` already applied uniformly to every other fact family's own invalidation event (`structure-fact-invalidated`, `regime-fact-invalidated`, `feature-fact-invalidated`). |

**Distinguishing three separate Chapter-10 concepts (same distinction `ADR-047` already
drew, reused by citation, not re-derived):**

1. **Compatibility commitment (§10.3.1) — decided by this ADR**, the sole subject of the
   table above.
2. **Compatibility classification of a concrete schema delta — NOT decided here.**
   Whether some future field addition/removal/retyping for either `contract_id` actually
   satisfies `backward_only` is a separate, per-change determination made once that
   concrete delta exists — this ADR classifies no delta, because neither Event Contract
   exists yet.
3. **Compatibility Result (§10.4) — NOT created by this ADR, out of scope entirely.** No
   evaluator, grant, or policy-registry mechanism is created; no Compatibility Result is
   issued for any subject.

**Format/reader-policy gap — stated explicitly, not assumed away (same disclaimer
`ADR-038`/`ADR-047` already state, reused by citation):** this ADR selects a direction as
policy. It does not prove any concrete delta compatible, and does not assume tolerant/
unknown-field-accepting reader behavior, a particular serialization format's own
behavior, or any processor implementation detail. The wider JSON Schema/Avro/Protobuf
format-specific reader-policy gap this repository has not yet closed for any contract
remains exactly as open as it already was.

## 6. `causal_state_dependency_declaration` (ADR-048) — checked, NOT a blocker

**Fresh-derived, not assumed by analogy:** Approved `ADR-048`'s own apply-time test
(Chapter 8 §8.2.3: does authoritatively applying the already-emitted effect event require
a processor to read a cause's own domain payload, or only identity/existence/precedence)
is applied directly to each contract's own actual causation shape — not borrowed from any
other module's result merely because the answer happens to match.

- **`market-context-snapshot`**: `causation_refs` is **not** a uniform seven-ref shape.
  Original computation: exactly `context_cutoff_source_ref` + `structure_fact_ref` +
  `volatility_regime_fact_ref` + `directional_persistence_regime_fact_ref` +
  `feature_fact_refs` (three elements) — seven total (`context.md` §3/§9). Correction
  replacement: the current (possibly updated) role refs **plus** the
  `MarketContextFactInvalidated` event being superseded (`context.md` line 156) — a
  different cardinality. For **every** role in both cases: `context.md` §3's own `line
  162` invariant already establishes that `context_values` is a **direct, verbatim copy**
  of each referenced fact's own already-published field, with "KHÔNG tự tính toán lại,
  KHÔNG diễn giải thêm ý nghĩa" — meaning `MarketContextSnapshot`'s own payload already
  carries everything a downstream processor needs; authoritatively applying (accepting)
  a `MarketContextSnapshot` event never requires re-reading any of these seven (or, for a
  replacement, variable) causes' own domain payload. Every role classifies
  `EXTERNAL_NON_STATE_CAUSE` under the actual test, applied directly to this fact's own
  payload-completeness property — not inferred from any other module's classification.
- **`market-context-fact-invalidated`**: `causation_refs` = exactly one
  `invalidated_fact_ref` plus a minimal-complete direct-cause set (one or more refs) per
  role in `affected_upstream_roles` (`context.md` §4, `ADR-046` Decision item 7) — a
  genuinely variable cardinality, never seven. `context.md` §4's own payload is exactly
  `{invalidated_fact_ref, affected_upstream_roles, invalidation_cause/reason}` — identity
  and cause-attribution only, no re-read of any referenced cause's own domain payload
  required to authoritatively apply the invalidation (mark the target
  `MarketContextSnapshot` obsolete). Every role classifies `EXTERNAL_NON_STATE_CAUSE`
  under the same direct application of the test — the same structural pattern already
  independently confirmed for `structure-fact-invalidated`/`regime-fact-invalidated`/
  `feature-fact-invalidated`'s own analogous `invalidated_fact_ref` roles, but verified
  here against Context's own payload shape, not assumed from theirs.

**Conclusion:** `causal_state_dependency_declaration` role classification for both future
Context output Event Contracts is mechanically derivable from already-Approved authority
(`context.md` §3/§4's own fixed payload shapes + `ADR-046`'s causation-shape rules +
`ADR-048`'s apply-time test). This is **not** an architecture blocker and **not** decided
by this ADR — it is ordinary Event-Contract-authoring-time work for the next bounded WP,
exactly as every one of the ten currently Published Event Contracts' own authors already
performed for their own roles, citing `ADR-048` by reference, with no additional ADR.

**Alternatives considered (both decisions):**

1. **Reuse `derived_fact` for `event_class` (rejected).** Would read as a quiet claim that
   Context's output is a new authoritative conclusion, contradicting `context.md` §17's
   own no-recomputation invariant and risking exactly the silent terminology-gap
   resolution `ADR-051` item 4 explicitly forbids.
2. **Reuse `observation` for `event_class` (rejected).** Reserved for root, first-hand,
   non-derived external capture — the structural opposite of a seven-(or variable-)
   causation-ref aggregation.
3. **Invent `projection_record` for `event_class` (chosen).** Smallest-scope value
   consistent with Chapter 7 §7.4's own explicitly permitted Projection-output category
   and the already-established "eligible cursor-bounded ... projection record"
   terminology (`feature-context-architecture.md` §5.2, `python/context-aggregator/
   README.md`) — this ADR formalizes that existing prose convention as a machine-readable
   `event_class` value, rather than inventing unrelated new terminology.
4. **`compatibility_commitment: explicit no-commitment` for either contract (rejected).**
   Permitted by Chapter 10 §10.3.1 as an explicit choice, but no reason distinguishes
   Context's two contracts from the unanimous `backward_only` precedent already set by
   all ten existing Published Event Contracts; choosing a weaker commitment here would be
   an unexplained departure, not a reasoned one.
5. **`compatibility_commitment: forward_only` or `bidirectional` (rejected).** No existing
   Event Contract in this repository has ever selected either value; no Context-specific
   evolution concern was identified that `backward_only` does not already address.
6. **Defer both decisions until a real Strategy consumer exists (rejected as the overall
   approach).** The governing WP that requested this ADR explicitly classified both
   fields as the remaining blocker to safe Draft authoring of the two Event Contracts;
   this ADR does not itself author or publish either contract, so deciding the policy now
   imposes no premature runtime cost and unblocks the next bounded WP, consistent with
   this repository's own established practice of committing compatibility policy ahead
   of a contract's first real consumer.

**Consequences:** This ADR, if Approved, resolves the two remaining architecture fields
`ADR-051` reserved (item 8) — `event_class: projection_record` and
`compatibility_commitment: backward_only` for both `market-context-snapshot` and
`market-context-fact-invalidated`. It does **not** itself: author or publish either Event
Contract (a separate, later, governed WP — the `causal_state_dependency_declaration` role
classification above is that WP's own mechanical task, not performed here); modify
`docs/domain/context.md`, `module-registry.yaml`, or `stream-registry.yaml`; change
`context-aggregator`'s Module Taxonomy classification or `owns_authoritative_state`
(remains Type 2 Projection, `false`); resolve the preserved Context authority/
terminology gap (`ADR-051` item 4, unchanged); decide Strategy's own future treatment of
Context output as authoritative or not; implement runtime; or authorize LIVE.
