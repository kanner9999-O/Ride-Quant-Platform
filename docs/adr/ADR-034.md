# ADR-034: Feature Eligible-Swing Selection Supersession — New `FeatureFactInvalidated.invalidation_cause`

> **v0.2 — bounded Review A correction**, addressed/remediated pending re-review (not self-closed by the correction executor — closure is a Review A re-review determination, never asserted here): `P3-ADR034-A-MAJ-01` (temporal visibility boundary was unpinned — the decision did not distinguish "genuinely not-yet-visible at the original computation cursor" from "already visible but wrongly omitted," and did not acknowledge that verifying the former requires an original-computation-cursor evidence prerequisite this ADR does not itself supply), `P3-ADR034-A-MIN-01` (mutable evidence wording — "current feature-engine implementation" replaced with pinned exact blob/line identities), `P3-ADR034-A-MIN-02` (Scale check's `expected_scale` zeros left unexplained against the strategy/exchange/plugin axes). No change to the decision's substance beyond these three fixes.
>
> **v0.3 — bounded Review A correction, round 2**, addressed/remediated pending re-review: `P3-ADR034-A-MAJ-01` remained open after v0.2 — the "Evidence prerequisite" bullet still permitted authoritative emission based solely on an implementation's own ephemeral, process-local, in-memory tracked state, which is not durable or replay-reconstructable evidence. Removed: the new cause now MUST fail closed unless `R_original` for the invalidated `FeatureComputed` is provable from durable, replay-reconstructable authoritative evidence; is explicitly stated as **semantically authorized by this ADR but operationally NOT EMITTABLE** until that evidence prerequisite exists; and explicitly requires Live/Replay/Backtest/Paper Trading to be able to establish the identical eligibility from the identical durable evidence (feature.md §13 mode parity) — still without deciding *how* `R_original` is persisted or adding any field, which remains `P3-FEATURE-A-MAJ-06`'s separate, already-open scope. `P3-ADR034-A-MIN-01`/`P3-ADR034-A-MIN-02`'s v0.2 substantive fixes are unchanged and carried forward unaltered — no further gap against either was identified in this round. **No change to the decision's substance beyond the MAJ-01 tightening above**: `ADR_REQUIRED` classification, the new-cause semantic (conditions (a)–(d)), `distance_to_last_confirmed_swing`-only scope, direct causation binding, mutual exclusion with `swing_invalidated`, append-only invalidate-and-replace, Alternatives considered, and Structure/Raw-Regime/Context/Strategy ownership boundaries are all unchanged from v0.2.

**Context:** [`feature.md`](../domain/feature.md) §9a defines `distance_to_last_confirmed_swing`'s deterministic Eligible-Swing selection: a 5-step filter pipeline followed by an 8-criterion total order, re-evaluated against the currently-visible `SwingConfirmed`/`SwingInvalidated` fact set. Because that candidate set only ever grows or has members explicitly invalidated — never silently goes stale — a previously-computed `FeatureComputed`'s selected Swing can stop being the §9a winner in two structurally different ways: (a) the Swing fact it used is itself invalidated (`SwingInvalidated`) — already modeled as `invalidation_cause: swing_invalidated` (§4); or (b) the Swing fact it used **remains valid and non-invalidated**, but a different, newly-visible `SwingConfirmed` (a first confirmation, or a corrected revision `N+1` per [`swing.md`](../domain/swing.md) §1a/§10) now wins §9a's total order over it.

Case (b) is exactly the sequence `P3-FEATURE-A-MAJ-04` requires: Swing A(N) used → A(N) invalidated → alternate Swing B becomes the temporary eligible winner, Feature fact becomes `VALID` using B → A's corrected revision A(N+1) later becomes visible and wins §9a's total order over B → the B-based Feature fact must be invalidated and replaced — even though B itself was never invalidated. `feature.md` §4 (Domain Contract identity: `docs/domain/feature.md`, `version: "0.2"`, blob `2262adf9253ea20c8d817d1066f50c4353d2d35d`)'s `invalidation_cause` enum (`candle_corrected`, `regime_fact_invalidated`, `swing_invalidated`) has no value for this: each existing value is bound by an explicit invariant to a specific class of direct authoritative cause event ("invalidation_cause PHẢI khớp đúng loại upstream contract... causation_refs PHẢI trỏ:... event authoritative là nguyên nhân trực tiếp"), and none matches — the direct cause here is a `SwingConfirmed`, not a `SwingInvalidated`, and the currently-used Swing was never invalidated (the corrected-revision mechanics this relies on are pinned in `swing.md` §1a/§10, Domain Contract identity: `docs/domain/swing.md`, `version: "0.2"`, blob `5bbe666ff404209876a721b1e01cb9ac62011062`).

**Implementation defect boundary (exact evidence identity, not a mutable "current implementation" reference):** commit `d728f682d3310d8735763269a228cc248f61bf5d`, `python/feature-engine/src/feature_engine/swing_distance.py` (blob `f4d9643780245218361b9ef1540e1727407e3753`), function `_preempt_settled_window` (lines 677–708) — line 696 sets `invalidation_cause="swing_invalidated"` while line 699's `causation_refs=(existing.head_fact.ref, state.ref)` cites `state.ref`, the WINNING `SwingConfirmed`'s own ref, never a `SwingInvalidated` ref. This is a confirmed, direct violation of §4's causal-fidelity invariant: the payload asserts a `SwingInvalidated` cause that does not exist for this transition. (The neighboring, unrelated `_invalidate_and_reattempt` function's own `invalidation_cause="swing_invalidated"` at line 615 is a *correctly* labeled, different transition — it is triggered by, and cites, an actual `SwingInvalidated` fact; it is not part of this defect and is not affected by this ADR.)

**Scope classification — `ADR Required`.** [Chapter 0 §4b](../constitution/00-governance.md) lists "thay đổi Event Schema" as one of several independently sufficient ADR-required triggers. This is confirmed disjunctive, not conjunctive, by direct Approved-ADR precedent: [ADR-025](./ADR-025.md) states explicitly, "Một update CHỈ được phép proceed KHÔNG CẦN ADR mới khi nó KHÔNG thỏa BẤT KỲ vế ADR Required nào (Platform Invariant/Event Schema/Module Taxonomy/dependency graph/Governance process/>1 module/khó đảo ngược/supersede ADR Locked)" — satisfying `Event Schema` alone, independent of the `>1 module`/`khó đảo ngược` clause, is sufficient. `invalidation_cause` is a closed-enum payload field of the authoritative `FeatureFactInvalidated` event; adding a legally distinct value is a change to that event's schema. [Chapter 8 §8.2](../constitution/08-event-model.md) — "Chapter 8 sở hữu envelope; Event Contract của event_type sở hữu payload schema/semantic" — determines which artifact **hosts** the schema content (here, `feature.md`, the Event Contract), not which **governance process** is required to change it; ownership-of-content and process-requirement are different axes. [ADR-033](./ADR-033.md) treats "event schema" as inclusive of Domain-Contract-owned field-level schema when disclaiming its own scope ("does not alter any contract category, event schema, or Domain Contract semantic. Field-level schema remains Domain Contract authority"), consistent with this reading. No higher-authority rule was found that overrides this classification.

**Decision:** Authorize a new `FeatureFactInvalidated.invalidation_cause` value, semantically: **the direct authoritative cause of this invalidation is a `SwingConfirmed` fact (first confirmation of a `swing_id`, or a corrected revision `N+1` per `swing.md` §1a) that (a) was NOT visible — per `feature.md` §9a step 2 / §12's recorded-time-visibility test, `SwingConfirmed.recorded_time <= R` — at the computation cursor `R_original` under which the now-invalidated `FeatureComputed` was originally produced; (b) IS visible at the later computation cursor `R_later` triggering this re-evaluation; (c) wins `feature.md` §9a's deterministic Eligible-Swing total order at `R_later`; and (d) the Swing fact the invalidated `FeatureComputed` actually used remains valid and non-invalidated at `R_later`.**

Binding rules for the follow-on `feature.md` amendment:

- Applies **only** to `feature_type: distance_to_last_confirmed_swing` — the sole feature type with an Eligible-Swing selection concept.
- `causation_refs` MUST include: `invalidated_fact_ref` (already generic) and the winning `SwingConfirmed` event record whose visibility changed the §9a winner. It MUST NOT cite a `SwingInvalidated` event as direct cause — none exists for this transition.
- Mutually exclusive with `swing_invalidated`: that cause applies when the currently-used Swing fact is itself invalidated; this new cause applies when it remains valid but is out-competed. An implementation must never emit both for the same invalidation.
- **Temporal visibility boundary (`P3-ADR034-A-MAJ-01`) — the cause is legal ONLY under conditions (a)–(d) above, never merely on "a `SwingConfirmed` exists that would have won."** Condition (a) is the load-bearing distinction: a `SwingConfirmed` that was ALREADY visible at `R_original` (`recorded_time <= R_original`) but was not selected by the original computation is explicitly **NOT** eligible for this cause — that is a correctness/integrity defect in the original `FeatureComputed` (§9a's own deterministic algorithm was not correctly applied at `R_original`), a different problem class entirely (a computation-defect correction/replay-repair, not a legitimate temporal-supersession event), and must never be represented, laundered, or hidden behind this `invalidation_cause`.
- **Evidence prerequisite — explicitly NOT solved by this ADR (`P3-ADR034-A-MAJ-01`, round 2 tightening).** Proving condition (a) (and, symmetrically, (b)) requires being able to establish, for a given `FeatureComputed`, the exact computation cursor `R_original` under which it was produced. `feature.md` §3's current `FeatureComputed` payload does not persist an explicit computation-cursor field, and `recorded_time` is an independent axis from cursor `R` (per `feature.md` §12 and the engine's own already-implemented `P3-FEATURE-A-MAJ-06` cursor remediation) — it cannot substitute as proof of what was visible when. This ADR does **not** define, add, or amend any such field, and does **not** decide *how* `R_original` is persisted; that is squarely `P3-FEATURE-A-MAJ-06`'s separate, already-open authority/implementation scope, out of bounds here.

  **This cause MUST fail closed unless `R_original` for the invalidated `FeatureComputed` can be proven from durable, replay-reconstructable authoritative evidence** — evidence that survives process restart and that any execution mode could independently reconstruct from the authoritative event log alone, without relying on a specific running process's private state. An implementation's own ephemeral, process-local, in-memory tracking of "the cursor it happened to use when it produced that fact" is explicitly **NOT sufficient evidence** on its own: it proves nothing to a second process, a restarted process, or a Replay/Backtest/Paper Trading run reconstructing the same fact independently from durable storage. Per `feature.md` §13's mode-parity requirement, Live/Backtest/Paper Trading/Replay must all be able to establish the SAME eligibility for this cause from the SAME durable evidence — never from one mode's own private runtime memory, which would make `invalidation_cause` truthfulness depend on which process instance happens to still be running.

  Until a follow-on transaction (within `P3-FEATURE-A-MAJ-06`'s separate scope) establishes how `R_original` is durably, replay-reconstructably proven or persisted, this new cause is **semantically authorized by this ADR but operationally NOT EMITTABLE**: no implementation may emit it under any circumstance, including from a position that merely holds `R_original` in in-process memory — an implementation MUST fail closed in every case where durable proof is unavailable, which today is every case, until that separate prerequisite is satisfied.
- Preserves `feature.md` §3/§9's existing correction-lineage invariants unmodified (append-only, exact subject/window, no shortcut when the recomputed value is unchanged, exactly one replacement per invalidated fact) — no new correction taxonomy or general-purpose framework; one additional narrowly-scoped value inside the existing three-branch structure.
- Introduces no Feature-to-Feature dependency (`feature.md` §10, untouched) and no change to Structure/Raw-Regime/Context/Strategy ownership.

The exact enum identifier and its final placement/wording in `feature.md` is deferred to the follow-on bounded Domain Contract amendment (see Consequences) — this ADR fixes the **semantic**, not the final prose. This ADR's own working name for the semantic is `eligible_swing_selection_superseded`; the amendment transaction may adopt it verbatim or choose different surface spelling, provided the binding rules above are preserved exactly.

**Alternatives considered:**

1. **Keep `swing_invalidated` for this transition (status quo).** Rejected — directly falsifies `feature.md` §4's causal-fidelity invariant; any consumer/auditor branching on `invalidation_cause` would wrongly conclude the previously-used Swing itself became invalid, corrupting audit trails and any future correction-cascade tooling keyed on cause.
2. **Suppress the B → A(N+1) invalidation/replacement entirely (only reattempt `PENDING_CORRECTION` windows, as Round 1 did).** Rejected — reintroduces `P3-FEATURE-A-MAJ-04` itself: a Feature fact would permanently retain a value based on a Swing §9a no longer selects, violating §3's "no shortcut" invariant and breaking mode parity (§13) — Live/Backtest/Replay would then depend on visibility order rather than the deterministic winner.
3. **Reuse `candle_corrected` or `regime_fact_invalidated`.** Rejected — neither is even topologically plausible (no Candle or Regime involvement); a strictly worse causal misattribution than option 1.
4. **Add one narrowly-scoped new cause for deterministic Eligible-Swing-selection supersession (chosen).** Only option keeping `invalidation_cause` truthful for every transition the engine must perform, staying entirely inside the existing three-branch, `feature_type`-scoped structure — no generic framework — with the smallest possible Event-Schema delta: one enum value + one `causation_refs` binding rule.

**Consequences:** Three bounded, separate follow-on transactions are required, in order: (1) a versioned `feature.md` amendment adding the authorized enum value and its invariants/causation-pin rule to §4 (and any necessary cross-reference from §9a), consistent with the binding rules above (including the temporal-visibility-boundary and defect-vs-supersession distinction) — Review A/B on that Domain Contract delta; (2) a bounded `feature-engine` implementation remediation (`swing_distance.py`) emitting the new cause instead of the currently-mislabeled `swing_invalidated` for this transition — **not emittable** until a separate, already-open `P3-FEATURE-A-MAJ-06`-scoped transaction first establishes how `R_original` is durably, replay-reconstructably persisted/proven, satisfying the evidence prerequisite above; (3) a bounded Review-A re-review of `P3-FEATURE-A-MAJ-04` against the corrected representation. `P3-FEATURE-A-MAJ-04` remains `OPEN` until all three land — this ADR alone does not close it, does not modify `feature.md`, and does not touch implementation. No other module, Domain Contract, or ADR is affected: Structure/Raw-Regime/Context ownership, module Tier classification, Quality Gate status, package/gate lifecycle, and LIVE authorization are all unchanged and unreferenced by this decision.
