# ADR-041: Canonical Exact-Version Resolution for Input Contracts and Stream Registry

**Context:** [Chapter 8](../constitution/08-event-model.md) §8.5.1 fixes the canonical Replay Cursor as pinning `input_contract_ref {contract_id, contract_version}` and `stream_registry_version` — exact, immutable historical identities. §8.1.1 requires every Referenced Authoritative Artifact (Input Contract and Stream Registry named explicitly, §8.3.1/§8.3.4) to be versioned (rule 1: "mọi thay đổi tạo version mới, không sửa tại chỗ"), immutable once referenced (rule 2), and persistently resolvable through the committed horizon (rule 4) — but fixes only the *requirement*, not the *mechanism* for either artifact family. `ADR-039` (Approved) already resolved this exact problem for Event Contracts with a per-version-file direct-path resolver; it does not cover Input Contracts or Stream Registry, and this ADR does not redesign or revisit it.

**Ground truth, independently confirmed at this boundary:** Input Contract artifacts (`docs/architecture/input-contracts/*.yaml`) and the Stream Registry (`docs/architecture/stream-registry.yaml`) are each realized as a **single file, edited in place**, with `contract_version`/`registry_version` as an internal scalar field, not a per-version filename. Direct `git log` inspection of `feature-swing-distance-input.yaml` shows its own document `version:` field advancing `"0.1"` → `"0.4"` across four commits (real `frontier_policy` mechanism content changes each time) while `input_contract_ref.contract_version: v1` stayed the same literal value throughout — the artifact's own governed identity was never bumped despite genuine content change, a direct violation of §8.1.1 rules 1/2 already latent in the repository today. `stream-registry.yaml` has not yet exhibited this drift empirically (two commits: Draft authoring + a mechanically-identical Approval edit), but no artifact establishes a mechanism preventing or governing it structurally once a genuine `registry_version` transition is ever needed (Chapter 8 §8.3.5 fixes the activation-boundary *event* model, never the file-level resolution of a past `registry_version`'s own exact bytes). `authority_resolver.py`'s existing profile-based resolver (`ADR-037`'s own explicitly-cited mechanism) resolves whichever content currently exists at these fixed paths — never the exact historical bytes a past `computation_cursor` may have pinned. No current artifact — Locked Chapter 8, Approved `ADR-037`, Approved `ADR-040`, or the Input Contract/Stream Registry files themselves — supplies a deterministic mapping from an exact historical `{contract_id, contract_version}`/`registry_version` identity to content guaranteed to still be that exact historical content.

**Scope classification — `ADR Required`.** [Chapter 0 §4b](../constitution/00-governance.md)'s disjunctive triggers are satisfied independently of each other: this is the same class of decision `ADR-039` already was for Event Contracts (a canonical resolution/versioning mechanism for a named Referenced Authoritative Artifact family) — hard to reverse (a chosen per-version scheme constrains every future historical reference; changing it later requires migrating every prior pin) and platform-wide in principle (any current or future consumer of Input Contract/Stream Registry authority, not merely `feature-engine`). `G-ADR-004`'s inflation check (below) confirms no existing alignment already resolves this. `G-ADR-003`: this ADR is not authored merely because a prior transaction (Feature's own ADR-037 Replay-preparation implementation) left work open — the gap is derived directly from Chapter 8 §8.1.1 rules 1/2/4 applied to an artifact family `ADR-039` never covered, exactly parallel to how `ADR-039` itself was derived independently from Chapter 8, not from `ADR-037`/`038`'s own gaps. `depends_on: []` accordingly — `ADR-037`/`ADR-040` are the exposing use-case, not this decision's own authority source.

**Decision question:** what canonical version lifecycle + exact-resolution model keeps every referenced Input Contract and Stream Registry version deterministically resolvable at current repository authority throughout the committed horizon?

**Decision (Option 2 — current/active path preserved, plus immutable per-version snapshot artifacts):**

- **Current/active path unchanged, still governs fresh (non-replay) resolution.** `docs/architecture/input-contracts/*.yaml` and `docs/architecture/stream-registry.yaml` remain exactly as Chapter 8 §8.3.1 already locks (Stream Registry's own path is Locked Constitution text — this ADR does not touch or reinterpret it) and as `ADR-040` already characterizes them — freely editable in place, resolved by `authority_resolver.py`'s existing mechanism for callers that need "whichever content is current." No change to this path, its content, or its own governance.
- **New: an immutable per-version snapshot artifact, captured at Publish time, for exact-historical resolution.** When a `contract_version`/`registry_version` is formally pinned for real authoritative reference (a fact's `computation_cursor` may legitimately name it), its exact bytes are captured into a dedicated, frozen file at:
  - Input Contract: `docs/architecture/input-contract-versions/<contract_id>/<contract_version>.yaml`
  - Stream Registry: `docs/architecture/stream-registry-versions/<registry_version>.yaml` (no `contract_id` segment — Chapter 8 §8.3.1 already fixes Stream Registry as a single, unnamed lineage, "Authoritative source duy nhất")
  Resolution is `ADR-039`'s own canonical grammar, reused by direct citation, not redefined: pure literal path substitution, `v<major>.<minor>`, no leading zeros except literal `0`, no aliasing/normalization/case-folding, no path separators/traversal in either token, malformed input fails closed before any path is constructed or any filesystem lookup occurs. No alias, registry/service, or git-history-search fallback exists (`ADR-040`'s own already-Approved prohibition, reused by citation, not re-litigated).
- **Historical/replay resolution always uses the version-snapshot path, never the current/active file.** Any consumer resolving a fact's own `computation_cursor.input_contract_ref`/`.stream_registry_version` (e.g. `feature-engine`'s Replay preparation) must resolve at the version-snapshot path for that exact identity — resolving the current/active file instead is a resolution-mechanism defect this ADR's own Decision does not authorize.
- **Immutable-after-reference; identifier non-reuse.** Once a version snapshot exists, it is frozen byte-for-byte forever (Chapter 11 §11.3 discipline, already applied identically to ADRs and Event Contract version-artifacts, reused by citation) — no in-place edits, no reassigning a `contract_version`/`registry_version` identifier to different content ever again. A content change always mints a **new** version snapshot; the current/active file may still be edited freely in between Publish events, but a *Published* snapshot itself never is.
- **Human version identifier vs. immutable content identity — same split `ADR-039` already fixed, reused by citation.** `contract_version`/`registry_version` is an ordering/legibility identifier only; the version-snapshot file's own git blob hash is its separate, verifiable content identity (§8.1.1 rule 5). Neither substitutes for the other.
- **Current/active vs. historical is a single, uniform distinction, not per-artifact-type variance.** "Current" always means the mutable, in-place file at its already-established path; "historical" always means an immutable snapshot at its own canonical version path — the same two-tier model applies identically to both Input Contracts and Stream Registry, closing the whole artifact-family problem once, not per-instance.
- **Fail-closed behavior — same principle `ADR-039`/`ADR-040` already establish, reused by citation.** A missing, malformed, or mismatched version snapshot; a malformed `contract_version`/`registry_version` token; or a content-identity mismatch on recomputation is a hard resolution failure — no nearest-version substitution, no degraded continuation, no silent fallback to the current/active file.
- **Relationship to `ADR-040`:** version-snapshot artifacts are new Class G members under `ADR-040`'s already-Approved retention model (git-repository-resident; within-horizon commitment = canonical path stays live at `HEAD`; git history is content-identity/audit evidence only, never a fallback resolver) — this ADR adds members to that already-established treatment, exactly as `ADR-039`'s own version-artifacts already did; it does not modify `ADR-040`'s text or its past-horizon archival deferral. The current/active files' own existing lifecycle (Draft, in-place-editable) is unaffected and unrevisited.
- **Bootstrap: existing bare `v1` identities do not carry over.** The Ground-truth finding above shows `input_contract_ref.contract_version: v1` has already denoted at least four distinct byte-states over time — it was never a single, stable, resolvable historical identity, so there is nothing genuine to preserve continuity with. No real authoritative (persisted, Live) fact has ever referenced any of those byte-states (`feature-engine` has never run outside tests). A **separate, future, governed bootstrap transaction** must capture each artifact's then-current content as a fresh **first** version snapshot under this ADR's grammar (`v1.0`, mirroring `ADR-039`'s own "first version starts at v1.0" rule, reused by citation) — this ADR decides that such a transaction is required and what it must produce; it does not itself perform that capture (no migration in this transaction, per explicit instruction).

**Alternatives considered:**

1. **(1) Immutable per-version canonical artifacts only, no current/active file (à la `ADR-039`, applied without change).** Rejected for this artifact family specifically: Chapter 8 §8.3.1 already Locks Stream Registry's own canonical path as the single fixed `/docs/architecture/stream-registry.yaml` — replacing it outright with a per-version-only scheme would directly contradict that Locked text, forcing a Constitution amendment this ADR is not authorized to make. Applying Option 1 to Input Contracts alone (no Locked path conflict there) while using Option 2 for Stream Registry would fragment one artifact-family problem into two different mechanisms, violating this ADR's own anti-proliferation mandate to close the family once.
2. **(2) Current/active path plus immutable historical version artifacts (chosen).** Satisfies §8.1.1 rules 1/2/4 for exact historical resolution without touching or reinterpreting Stream Registry's Locked current-path text, and without changing anything about `ADR-040`'s own already-Approved current-path characterization — purely additive. Reuses `ADR-039`'s own reviewed grammar/fail-closed discipline rather than inventing a new one.
3. **(3) Version/content-index based resolution (a central manifest mapping `{contract_id, contract_version}` → content hash/path).** Rejected — introduces a genuinely new authority surface (the index itself needs its own versioning/immutability/integrity guarantees, an unresolved question this option does not answer for free) for no benefit Option 2 does not already provide directly; more mechanism for an equivalent guarantee.
4. **(4) Git-history lookup.** Rejected outright — `ADR-040` (Approved) already establishes git commit/blob history as content-identity/audit evidence only, never a fallback resolver; adopting it here would directly contradict that already-Approved, already-Locked-in-spirit principle rather than merely be superseded by a better option.

No materially better option was identified beyond these four; Option 2 was chosen specifically because it is the only one requiring zero conflict with already-Locked/Approved authority while still fully satisfying §8.1.1's exact-resolution requirement for both artifact types uniformly.

**Authority compatibility:** `REQUIRES_FOLLOW_ON_SUPERSESSION/AMENDMENT` — narrow scope, not Constitution-level. `ADR-040`'s own existing text characterizes Input Contracts'/Stream Registry's single current-path resolver as already satisfying §8.1.1's retention/resolvability requirement in full; this ADR's own Ground-truth finding shows that characterization conflates *current-active* resolution with *exact-historical-version* resolution, which are now distinct under this Decision. `ADR-040`'s file itself is not modified here (Chapter 11 §11.3 forbids editing an Approved ADR) — a future, separate governed transaction must record a narrow cross-reference/scope-narrowing from this ADR (once Approved) onto `ADR-040`'s own Input-Contract/Stream-Registry retention characterization, the same class of narrow self-declared narrowing already precedented by `ADR-016`'s "Mechanism A" amendment of `ADR-015`. No conflict with Locked Chapter 8 was identified: Stream Registry's own current-path text stays untouched and unreinterpreted by this Decision.

**Consequences:** This ADR fixes the canonical exact-version resolution architecture for Input Contracts and Stream Registry only. It does not itself create any version-snapshot artifact, does not migrate any existing Input Contract or Stream Registry file, does not modify Chapter 8, `ADR-037`/`ADR-038`/`ADR-039`/`ADR-040`, or any Published Event Contract, and does not modify production source/tests/tooling — `output_contract_resolver.py`/`prepare_replay_evidence()` remain exactly as they are; the two open Review-A Major findings against them (`P3-FEATURE-EVID05B-IMPL-A-MAJ-01`/`-MAJ-02`) and `P3-FEATURE-QG-EVID-05(b)` are not closed by this ADR. Bounded, separate follow-on work remains, in order: (0) Review A/Independent Review B/Product Owner decision on this Draft; (1) if Approved, the governed bootstrap transaction that captures each artifact's current content as its first `v1.0` version snapshot (see Bootstrap above); (2) the narrow `ADR-040` cross-reference/scope-narrowing transaction (see Authority compatibility above); (3) only then, `feature-engine`'s own `prepare_replay_evidence()` correction resolving `P3-FEATURE-EVID05B-IMPL-A-MAJ-02` against this newly-available authority, alongside `P3-FEATURE-EVID05B-IMPL-A-MAJ-01`'s independent-per-`contract_id`-version-lineage fix; (4) a bounded Review-A re-review closing both findings and, if warranted, `P3-FEATURE-QG-EVID-05(b)`. This ADR does not change Feature Chapter 13 QG evidence, Feature module approval, the Phase 3 Approval Gate, or `LIVE` authorization — all remain exactly as they stood before this transaction.
