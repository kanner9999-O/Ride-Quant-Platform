# ADR-051: Context Projection Output Stream Identity and Writer Authority

**v0.3 — bounded correction against fresh ChatGPT Review A** (`REVISION_REQUIRED — 0
Blocker / 1 Major / 0 Minor`, Risk `R2`), addressed/remediated pending fresh Review A
re-review (not self-closed by the correction executor — closure is a Review A re-review
determination, never asserted here):

- **`ADR051-A-MAJ-02`** (v0.2 correctly preserved the Context authority/terminology gap in
  Decision item 4, but repeatedly contradicted that same preservation elsewhere by
  claiming the chosen one-stream topology was the "unique"/"mechanical" result of applying
  `ADR-036`'s own partitioning rule — literally scoped to "authoritative fact family" — to
  Context, which implicitly imports the very authoritative-ownership predicate item 4
  leaves open): the Decision's opening paragraph, item 1's heading, item 2 in full, item
  3's writer-authority justification, and Alternatives item 1 are rewritten below to
  state that this ADR selects `ADR-036`'s topology **precedent** (one writer, one coherent
  record family, original fact + its own invalidation counterpart sharing one stream, no
  scope-partitioning) and applies it to Context's own actual bounded facts (same writer,
  same Domain Contract, same lineage family, no independently-established consumer/
  semantic boundary requiring a split) — explicitly **without** claiming Context already
  satisfies `ADR-036`'s authoritative-fact-family predicate, and without reopening item 4.
  Item 3's "authoritative owner of the `context-aggregation` capability" phrase is
  replaced with "sole registered implementation/owner," with an explicit note that
  capability-registration uniqueness (Chapter 3 §3.1) is not `owns_authoritative_state`.

No stream identity, writer authority, the one-stream decision itself, registry-transition
mechanics (item 7), Track A/Track B parallelism (Consequences), Scope classification, or
Alternatives 2–5 are changed by this correction — only the justification wording for the
already-chosen topology, and only where it relied on an authoritative-fact-family premise
Context does not (and is not claimed to) satisfy.

`ADR051-A-MAJ-01`/`ADR051-A-MIN-01`: addressed/remediated pending fresh Review A.

**Context:** `docs/project/m3-context-closure-derivation-001.md` (reviewed boundary
`0a15219ce504e00ff4cb88e4b9428ab042fd37c2`, fresh ChatGPT Review A CLEAN — 0 Blocker / 0
Major / 1 Minor) derived that M3 ("Context Projection / `context-aggregator`") cannot
reach its output-publication boundary until a governed decision pins Context's own
output logical stream identity and writer authority (finding `CONTEXT-CLOSURE-A-MAJ-01`,
closed in that WP's own correction round by reclassifying this as a genuine architecture
escalation rather than a mechanical step). This ADR is that governed decision.

[Chapter 8](../constitution/08-event-model.md) §8.3.1 (Locked) is explicit: *"Tạo/xóa/tách
stream, hoặc đổi writer authority, là thay đổi Event Model → ADR Required, kèm bump
`registry_version`"* — creating a stream or changing writer authority is an Event Model
change, ADR Required, with a `registry_version` bump. §8.3.1 vests stream
identity/topology/writer authority **solely** in `docs/architecture/stream-registry.yaml`
(I-12: one concept, one authoritative source); an Event Contract may only *reference* a
stream via `allowed_streams`, never define one.

`docs/architecture/stream-registry.yaml` (status: Approved, `registry_version: v1.0`,
fresh-read this transaction) contains exactly seven streams: the five analytical streams
`ADR-036` (Approved) established (`market-data-ingestion-candle`,
`structure-engine-swing`, `structure-engine-structure`, `raw-regime-engine-regime`,
`feature-engine-feature`) plus the two Genesis-protected control-plane streams
(`platform-lifecycle`, `platform-audit`). **No Context output stream exists.** `ADR-036`
itself scopes its own Decision explicitly to "the currently-implemented Phase-3 core
analytical chain" (`Market Data Ingestion → Structure/Swing → Raw Regime → Feature`) — it
does not mention, and was never asked to decide, `context-aggregator`'s own output. No
later Approved ADR or registry transition has added one. `docs/architecture/
module-registry.yaml`'s current `context-aggregator` entry declares `emits: [event,
query]` but carries no `writer_authority`/`stream_ref` assignment on any stream (that
assignment lives exclusively in `stream-registry.yaml`, per the authority split Chapter 8
§8.3.1 itself draws) — confirming no stream-level authority has been granted to this
module yet, consistent with no stream existing for it to write to.

**Scope classification — `ADR Required`, independently triggered**, by the same test
`ADR-036` itself applied: establishing a new stream + sole writer authority for it is,
per Chapter 0 §4b and Chapter 8 §8.3.1's own text, a genuine Event-Model change — hard to
reverse once event data accumulates under a given topology, and `context-aggregator`'s own
Module Taxonomy classification (Type 2 Projection) is directly implicated in how this
decision must be framed (see Decision item 4 below). No already-Approved authority pins
Context's concrete output stream identity/writer authority — `ADR-036` explicitly
deferred it by never addressing it, and no Phase 1 design spec has filled the gap.
`ADR_REQUIRED` confirmed by direct inspection, not assumption.

**Decision:** Add exactly **one** new post-Genesis logical stream to the Stream Registry,
`context-aggregator-context`, with sole writer authority `context-aggregator`, carrying
both of Context's output event types (`MarketContextSnapshot`,
`MarketContextFactInvalidated`) — selected using `ADR-036`'s established topology/
partitioning **precedent** (one writer, one coherent record/domain family, an original
fact together with its own correction/invalidation lineage sharing one stream, no
instrument/venue/timeframe stream explosion, a split only where a genuine, independently-
established semantic/consumer boundary justifies it), applied here **without importing**
`ADR-036`'s own authoritative-domain-ownership semantics into `context-aggregator` (item 4
below, unchanged by this correction).

**1. Stream identity (naming, selected using `ADR-036`'s established naming convention as
precedent):** `ADR-036`'s Decision table names every analytical stream
`{module_id}-{domain_family}` — `market-data-ingestion-candle`, `structure-engine-swing`,
`structure-engine-structure`, `raw-regime-engine-regime`, `feature-engine-feature`
(the last of these already demonstrates the pattern tolerates a domain-family suffix that
echoes part of the module_id, exactly as `context-aggregator-context` would for Context —
not a new or unusual construction). `context-aggregator` is the sole module registered
against `implements_capabilities: [context-aggregation]`
(`module-registry.yaml`, fresh-read this transaction) and the domain family is "Market
Context facts" (`docs/domain/context.md`, `context_type: market_context`). Stream
identity: **`context-aggregator-context`**.

**2. One stream, not two — selected using `ADR-036`'s established topology precedent,
grounded in Context's own actual bounded facts, NOT because Context is itself an
authoritative fact family (v0.3 correction, `ADR051-A-MAJ-02`):** `ADR-036`'s own literal
Decision text pins its partitioning unit as "one logical stream per **authoritative** fact
family a writer module owns" — a formulation that is scoped the way it is because every
one of `ADR-036`'s four analytical writers already has `owns_authoritative_state: true`
for the fact family in question. `context-aggregator` does not: it is Type 2 Projection,
`owns_authoritative_state: false`, and whether `MarketContextSnapshot`/
`MarketContextFactInvalidated` constitute an authoritative domain fact at all is an open
question this ADR explicitly does not decide (item 4 below). This Decision therefore does
**not** claim Context already satisfies `ADR-036`'s authoritative-fact-family predicate,
and does **not** claim the one-stream outcome is a mechanical or unique consequence of
applying that literal rule to Context — doing so would smuggle a resolution of the
preserved authority/terminology gap in through the stream-topology decision, exactly what
item 4 forbids.

What `ADR-036` *does* supply, independent of authoritative status, is a **topology
precedent** already consistently applied across all four of its analytical writers: one
writer, one coherent record/domain family, an original fact together with its own
correction/invalidation lineage sharing one stream, with a split reserved for cases where
a genuine, independently-established semantic/consumer boundary justifies it (e.g.
`structure-engine` splits Swing from Structure because they are two distinct Domain
Contracts with different consumer sets — Feature consumes only Swing, per `ADR-036` item
1). Every existing analytical stream already carries multiple event types sharing one
coherent record family under exactly this pattern: `market-data-ingestion-candle` carries
both `CandleClosed` and `CandleCorrected`; `structure-engine-structure` carries all four of
`BreakOfStructureDetected`/`ChangeOfCharacterDetected`/`StructureFactInvalidated`/
`StructureRecomputed`; `raw-regime-engine-regime` carries both `RegimeClassified` and
`RegimeFactInvalidated`; `feature-engine-feature` carries both `FeatureComputed` and
`FeatureFactInvalidated`.

`context-aggregator-context` adopts that same topology pattern for Context's two output
event types, grounded in Context's own actual bounded facts, not in an imported
authoritative-ownership predicate: (a) both event types share the same sole writer,
`context-aggregator`; (b) both belong to the same `context.md` Domain Contract and the
same `context_subject_id`/`effective_window` lineage family (`context.md` §12); (c)
`MarketContextFactInvalidated` is `MarketContextSnapshot`'s own invalidation counterpart,
not an independent record family; (d) no independently-established consumer or semantic
boundary analogous to `structure-engine`'s Swing/Structure split exists for Context's two
event types — splitting them would add stream topology without evidence of a distinct
boundary to justify it. **Option A** (one stream for both event types) is the option this
ADR selects on that basis — a topology choice grounded in Context's own bounded facts and
in `ADR-036`'s precedent for how to partition a coherent record family, not a claim that
Context's output is already proven authoritative or that `ADR-036`'s rule mechanically
forces this single answer. **Option B** (split by event type) is rejected for the same
structural reason `ADR-036` never split Candle's, Structure's, Regime's, or Feature's own
original-fact/invalidation-counterpart pairs: no distinct consumer/semantic boundary
supports it.

**3. Writer authority — sole, `context-aggregator`:** Chapter 8 §8.3.1: "một module có thể
ghi vào nhiều stream, nhưng mỗi stream chỉ có 1 writer authority." `context-aggregator`
is the sole registered implementation/owner of the `context-aggregation` capability
(`module-registry.yaml`, Chapter 3 §3.1's "one authoritative implementation per
capability" registration-uniqueness test — the same single-registered-implementer test
`ADR-036` applied when naming each of its own four analytical writers as sole writer of
its own stream). This is a statement about capability-*registration* uniqueness only — it
does not speak to, and must not be conflated with, `owns_authoritative_state` (item 4
below: `context-aggregator`'s value for that field remains `false`, unchanged). No new
writer-coordination module is introduced (unlike the two protected streams, which needed a
new `stream-registry-authority` module because no existing module owned that
responsibility — here, `context-aggregator` is already the sole registered implementer of
Context aggregation).

**4. Writer-identity basis only — this ADR does not classify, and does not resolve, the
already-preserved Context authoritative-domain-semantic open gap (v0.2 correction,
`ADR051-A-MAJ-01`):** this ADR does **not** change `context-aggregator`'s Module Taxonomy
classification. It remains Type 2 Projection, `owns_authoritative_state: false`
(`module-registry.yaml`, unchanged by this ADR). Granting `context-aggregator` sole
writer authority over `context-aggregator-context` is a stream-identity/topology decision
only — it does **not** make `context-aggregator` `owns_authoritative_state: true`, and
does not itself constitute or require any Module Taxonomy reclassification.

`module-registry.yaml`'s existing `context-aggregator.emits: [event, query]` field and its
own projection-record registration (`notes`: "Type 2 Projection ... KHÔNG BAO GIỜ sở hữu
business decision ... `emits: [event, query]` — event là append-only projection
snapshot/invalidation record ... KHÔNG phải authoritative domain fact theo nghĩa Chapter 7
§7.4 cấm") are used here **only** to establish that `context-aggregator` is the intended,
already-registered writer of `MarketContextSnapshot`/`MarketContextFactInvalidated` — i.e.
that granting it stream-writer authority is consistent with, and not in tension with, its
own already-declared `emits` category. That registration is **not** used, and is **not**
sufficient, as proof that the unresolved authoritative-domain-semantic status of these two
event types has been decided one way or the other.

This ADR explicitly does **not** decide, and leaves exactly as currently preserved:

- whether `MarketContextSnapshot`/`MarketContextFactInvalidated` are Chapter 7 §7.4's
  permitted "operational metadata about itself" category, an authoritative domain fact,
  or something else — that classification question remains open, not resolved here;
- whether a future Strategy/Decision consumer may treat Context's output as authoritative
  input — a future consumer's own treatment of Context output is a separate, later
  decision this ADR does not make or foreclose;
- the already-preserved tension between `module-registry.yaml`'s Type-2/non-authoritative
  framing and `context.md`'s own historical "authoritative event record"/"authoritative
  market-state snapshot" wording and its mention that a future Strategy Contract may
  consume Context events (`docs/architecture/engine/feature-context-architecture.md`
  §5.2/§13's own already-preserved open gap; `m3-context-closure-derivation-001.md` §5
  D1) — prior Product Owner consolidation explicitly preserved this as a non-blocking
  open gap and did **not** choose a new Context authority model; this ADR does not choose
  one either.

Output Event Contract authoring for `MarketContextSnapshot`/`MarketContextFactInvalidated`
(a separate, later, governed step — Decision item 8, Consequences track B) must remain
consistent with the currently controlling `module-registry.yaml`/Chapter 7 boundaries as
they stand today, and must not silently resolve this preserved gap either — any future
resolution of the authority/terminology tension is its own, separately-governed
architecture decision, never a side effect of this stream-identity/writer-authority
assignment or of Event Contract authoring under it.

**5. No scope/instrument/venue/timeframe partitioning — by direct application of
`ADR-036`'s own Alternative 2 rejection, not a new rejection invented here:** `ADR-036`
rejected scope-partitioned streams for the analytical chain because it "would require
creating ... a new stream for every new instrument/venue/timeframe combination, growing
stream count combinatorially," and because it "conflates Stream Registry topology with
`subject_ref` scoping, which Chapter 8 explicitly separates." Both reasons apply
identically here: Context's own five-field `ContextSubjectScope`
(`instrument_id`/`venue_id`/`timeframe`/`context_type`/`context_definition_version`,
`context.md` §1) is exactly the `subject_ref`-level scoping mechanism Chapter 8 §8.2.2
already reserves for payload scoping, not stream topology — the same separation
`structure-engine`/`raw-regime-engine`/`feature-engine` already rely on for their own
per-subject-scoped facts sharing one stream each. `context-aggregator-context` carries
every `market_context` fact regardless of `instrument_id`/`venue_id`/`timeframe`,
unpartitioned, exactly like the four existing analytical streams.

**6. Future `context_type` values — not decided, not pre-empted:** `context.md`'s
`context_type` enum is currently closed at exactly `[market_context]`. If a future
`context_type` is ever authored, whether it shares `context-aggregator-context` or
requires its own stream is a decision for that future, separately-governed transaction —
the same way a hypothetical sixth analytical writer module would require its own future
ADR under `ADR-036`'s own established pattern. This ADR decides only the one `context_type`
that exists today.

**7. Registry-transition mechanics (Chapter 8 §8.3.1/§8.3.5, post-Genesis — this ADR
decides the architecture, not the concrete registry edit):** `stream-registry.yaml` is
currently `registry_version: v1.0` (Genesis). Adding `context-aggregator-context` is a
**post-Genesis** stream creation, so — unlike the Genesis streams `ADR-036` pinned, which
needed no prior activation boundary (§8.3.5's one-time root exception) — the resulting
new registry version must declare `effective_from.event_ref` pointing to a genuine
activation event on the canonical `platform-lifecycle` stream (§8.3.1: *"BẮT BUỘC với mọi
version SAU Genesis"*), authored by `stream-registry-authority` (the sole writer
authority Chapter 8 §8.3.5/`ADR-036` already vest over `platform-lifecycle`, unchanged by
this ADR), per the §8.3.5 validation chain: (a) the activation event must not be the
activating stream's own first event (bootstrap-cycle prohibition); (b) the new
`registry_version` literal follows `ADR-041`'s already-Approved `v<major>.<minor>`
grammar (the next value after `v1.0`, decided at the actual registry-authoring
transaction, not here); (c) every existing stream/writer-authority/sequence-policy/
genesis-position entry in the current Genesis Registry carries forward byte-identical —
this is an additive transition, not a redefinition of anything `ADR-036` already decided.
This ADR does not itself edit `stream-registry.yaml` or author the activation event — per
ADR-036's own precedent (Consequences), the architecture decision is complete here; the
registry-authoring transcription is a separate, later, mechanical step, subject to its
own applicable review.

**8. Boundary vs. Event Contract `allowed_streams` (same boundary `ADR-036` item 6
already drew, reused not redecided):** this ADR pins only the stream's identity and
writer authority — it does not decide, and the future concrete registry entry may not
contain, which event *types* may target `context-aggregator-context`. That eligibility is
declared exclusively by `MarketContextSnapshot`'s and `MarketContextFactInvalidated`'s
own future Event Contracts' `allowed_streams` fields (separate, later, governed work —
explicitly out of this ADR's scope, per the governing task's own instruction not to author
output Event Contract payloads here).

**9. No broker/storage/runtime/deployment choice:** this ADR decides Stream Registry
architecture only (identity, topology, writer authority) — it does not choose, imply, or
constrain message broker technology, storage engine, deployment topology, or any runtime
implementation detail. Those remain Chapter 0 §4b-excluded implementation concerns Chapter
8's own authority split already keeps out of `stream-registry.yaml` entirely.

**Alternatives considered:**

1. **One stream, `context-aggregator-context`, sole writer `context-aggregator` (chosen).**
   Selected using `ADR-036`'s established topology precedent (one writer, one coherent
   record/domain family, an original fact together with its own invalidation/correction
   counterpart(s) sharing one stream), applied to Context's own bounded facts (item 2
   above) **without importing** `ADR-036`'s authoritative-domain-ownership semantics —
   not a new topology rule invented here, and not a claim that Context's output is
   already proven authoritative.
2. **Two streams, one per output event type.** Rejected — `ADR-036` never splits an
   original-fact event type from its own invalidation counterpart across streams for any
   of the four existing analytical writers (Candle, Structure, Regime, Feature all keep
   original + invalidation/correction together); no Context-specific reason (different
   Domain Contract, different consumer set) exists to depart from that precedent here.
3. **Scope-partitioned streams (instrument/venue/timeframe).** Rejected for the identical
   reason `ADR-036` Alternative 2 rejected it for the analytical chain: combinatorial
   stream-count growth, and conflation of Stream Registry topology with `subject_ref`
   scoping (Chapter 8 §8.2.2), which `context.md`'s own `ContextSubjectScope` already
   supplies at the correct layer.
4. **Reuse an existing analytical stream (e.g. `feature-engine-feature`) for Context's
   output.** Rejected — directly violates Chapter 8 §8.3.1's single-writer-per-stream
   invariant (`feature-engine` and `context-aggregator` are two independent writer
   modules; sharing one stream would require an unauthorized cross-module sequence
   coordinator, the same violation `ADR-036` Alternative 3 already rejected for the
   analytical chain).
5. **Defer this ADR until Context's runtime implementation begins.** Rejected as the
   overall approach (the governing WP that requested this ADR explicitly classified the
   decision as the blocking item for category B's output Event Contract authoring) — but
   this ADR does not itself implement anything, so authoring it now imposes no runtime
   cost and unblocks the next bounded WP.

**Consequences:** This ADR **alone does not publish anything** — the required steps before
it has any effect, none of which is performed by this ADR: (1) Review A; (2) Product Owner
decision (Risk Classification expected R2 — same class as `ADR-036`'s own
registry-topology decision: the `>1 module` disjunct is not independently needed here
since only `context-aggregator` is newly granted writer authority, but Chapter 0 §4b's
"thay đổi Event Schema"/Event-Model trigger already applies on its own — Chapter 8
§8.3.1's own text is unconditional that stream creation/writer-authority change is ADR
Required — and the decision is hard to reverse once Context output events accumulate
under this topology).

**If Approved, two tracks follow — correctly sequenced only where a genuine dependency
exists (v0.2 correction, `ADR051-A-MIN-01`: v0.1 over-serialized these):**

- **Track A — mechanical registry transition:** a governed, mechanical
  `stream-registry.yaml` registry-version transition instantiating this ADR's
  already-decided identity/writer authority (new `registry_version`, `effective_from`
  activation event on `platform-lifecycle`, authored by `stream-registry-authority` — no
  new topology/writer decision at that step, same `ADR-023`/`ADR-036`
  mechanical-transcription precedent), together with any corresponding
  `module-registry.yaml` alignment (exact mechanical transcription only, no new decision).
- **Track B — Draft Event Contract authoring:** Draft authoring of
  `market-context-snapshot`/`market-context-fact-invalidated` Event Contracts, citing this
  ADR's own already-Approved stream identity (`allowed_streams:
  [context-aggregator-context]`).

Track A and Track B **may proceed in parallel where safe** — Track B's Draft authoring
depends only on this ADR's own Approved identity/writer decision, not on Track A having
already completed; nothing in Chapter 8 requires an Event Contract to be Drafted only
after its cited stream's own registry transition has concluded. What **does** remain
fail-closed regardless of either track's progress: Event Contract **publication**, any
runtime publication, and any authoritative use of `context-aggregator-context` — none of
these may proceed until the required Stream Registry version/activation genuinely
resolves (i.e. until Track A actually completes and `context-aggregator-context` resolves
as `active` under a concrete, activated `registry_version`). An Event Contract may be
Drafted citing a not-yet-active stream; it may not be Published, and nothing may treat it
as authoritative, until that stream genuinely exists and is active in the Stream
Registry.

This ADR does not itself perform either track: it does not modify
`stream-registry.yaml`, `module-registry.yaml`, `docs/domain/context.md`, any other
Approved ADR, or any code; does not author or publish any Event Contract; does not
implement `context-aggregator` runtime; does not touch Context Input Contract semantics;
does not assign a Quality Tier; does not perform Review A or request Independent Review
B. `context-aggregator` remains `status: candidate`, Type 2 Projection,
`owns_authoritative_state: false`, unchanged.
