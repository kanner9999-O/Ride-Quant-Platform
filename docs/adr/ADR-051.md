# ADR-051: Context Projection Output Stream Identity and Writer Authority

**Context:** `docs/project/m3-context-closure-derivation-001.md` (reviewed boundary
`0a15219ce504e00ff4cb88e4b9428ab042fd37c2`, fresh ChatGPT Review A CLEAN — 0 Blocker / 0
Major / 1 Minor) derived that M3 ("Context Projection / `context-aggregator`") cannot
reach its output-publication boundary until a governed decision pins Context's own
output logical stream identity and writer authority (finding `CONTEXT-CLOSURE-A-MAJ-01`,
closed in that WP's own correction round by reclassifying this as a genuine architecture
escalation rather than a mechanical step). This ADR is that governed decision.

[Chapter 8](../constitution/08-event-model.md) §8.3.1 (Locked) is explicit: *"Tạo/xóa/tách
stream, hoặc đổi writer authority, là thay đổi Event Model → ADR Required, kèm bump
`registry_version`"* — creating a stream or changing writer authority is an Event Model
change, ADR Required, with a `registry_version` bump. §8.3.1 vests stream
identity/topology/writer authority **solely** in `docs/architecture/stream-registry.yaml`
(I-12: one concept, one authoritative source); an Event Contract may only *reference* a
stream via `allowed_streams`, never define one.

`docs/architecture/stream-registry.yaml` (status: Approved, `registry_version: v1.0`,
fresh-read this transaction) contains exactly seven streams: the five analytical streams
`ADR-036` (Approved) established (`market-data-ingestion-candle`,
`structure-engine-swing`, `structure-engine-structure`, `raw-regime-engine-regime`,
`feature-engine-feature`) plus the two Genesis-protected control-plane streams
(`platform-lifecycle`, `platform-audit`). **No Context output stream exists.** `ADR-036`
itself scopes its own Decision explicitly to "the currently-implemented Phase-3 core
analytical chain" (`Market Data Ingestion → Structure/Swing → Raw Regime → Feature`) — it
does not mention, and was never asked to decide, `context-aggregator`'s own output. No
later Approved ADR or registry transition has added one. `docs/architecture/
module-registry.yaml`'s current `context-aggregator` entry declares `emits: [event,
query]` but carries no `writer_authority`/`stream_ref` assignment on any stream (that
assignment lives exclusively in `stream-registry.yaml`, per the authority split Chapter 8
§8.3.1 itself draws) — confirming no stream-level authority has been granted to this
module yet, consistent with no stream existing for it to write to.

**Scope classification — `ADR Required`, independently triggered**, by the same test
`ADR-036` itself applied: establishing a new stream + sole writer authority for it is,
per Chapter 0 §4b and Chapter 8 §8.3.1's own text, a genuine Event-Model change — hard to
reverse once event data accumulates under a given topology, and `context-aggregator`'s own
Module Taxonomy classification (Type 2 Projection) is directly implicated in how this
decision must be framed (see Decision item 4 below). No already-Approved authority pins
Context's concrete output stream identity/writer authority — `ADR-036` explicitly
deferred it by never addressing it, and no Phase 1 design spec has filled the gap.
`ADR_REQUIRED` confirmed by direct inspection, not assumption.

**Decision:** Add exactly **one** new post-Genesis logical stream to the Stream Registry,
`context-aggregator-context`, with sole writer authority `context-aggregator`, carrying
both of Context's output event types (`MarketContextSnapshot`,
`MarketContextFactInvalidated`) — following `ADR-036`'s own already-established,
consistently-applied partitioning rule exactly, not inventing a new one.

**1. Stream identity (naming, by direct mechanical application of `ADR-036`'s own
pattern):** `ADR-036`'s Decision table names every analytical stream
`{module_id}-{domain_family}` — `market-data-ingestion-candle`, `structure-engine-swing`,
`structure-engine-structure`, `raw-regime-engine-regime`, `feature-engine-feature`
(the last of these already demonstrates the pattern tolerates a domain-family suffix that
echoes part of the module_id, exactly as `context-aggregator-context` would for Context —
not a new or unusual construction). `context-aggregator` is the sole module registered
against `implements_capabilities: [context-aggregation]`
(`module-registry.yaml`, fresh-read this transaction) and the domain family is "Market
Context facts" (`docs/domain/context.md`, `context_type: market_context`). Stream
identity: **`context-aggregator-context`**.

**2. One stream, not two — by direct mechanical application of `ADR-036`'s own
partitioning rule (item 1/3 of this ADR, no new rule invented):** `ADR-036` already
establishes, and applies consistently across all four existing analytical writers, that
the partitioning unit is **one stream per writer module per authoritative fact family**,
not one stream per event *type*. Every existing analytical stream already carries
multiple event types sharing one fact family: `market-data-ingestion-candle` carries both
`CandleClosed` and `CandleCorrected`; `structure-engine-structure` carries all four of
`BreakOfStructureDetected`/`ChangeOfCharacterDetected`/`StructureFactInvalidated`/
`StructureRecomputed`; `raw-regime-engine-regime` carries both `RegimeClassified` and
`RegimeFactInvalidated`; `feature-engine-feature` carries both `FeatureComputed` and
`FeatureFactInvalidated`. In every one of these four precedents, an original-fact event
type and its own invalidation/correction/recomputation counterpart(s) share one stream —
exactly the relationship between `MarketContextSnapshot` (original fact) and
`MarketContextFactInvalidated` (its invalidation counterpart, `context.md` §3/§4). There
is no different-consumer-set reason to split them the way `structure-engine` splits Swing
from Structure (`ADR-036` item 1: different Domain Contracts, different consumer sets,
Feature consumes only Swing) — both Context output event types belong to the same Domain
Contract (`context.md`), the same `context_subject_id`/`effective_window` lineage
(`context.md` §12), and the same eventual consumer set. **Option A** (one stream for
both event types) is therefore not merely the smallest alternative but the one uniquely
determined by `ADR-036`'s own already-applied, consistently-used rule. **Option B**
(split by event type) is rejected for the same reason `ADR-036` never split Candle,
Structure, Regime, or Feature this way.

**3. Writer authority — sole, `context-aggregator`:** Chapter 8 §8.3.1: "một module có thể
ghi vào nhiều stream, nhưng mỗi stream chỉ có 1 writer authority." `context-aggregator`
is the sole module registered as authoritative owner of the `context-aggregation`
capability (`module-registry.yaml`, Chapter 3 §3.1 "one authoritative implementation per
capability" — the same test `ADR-036` applied to name its own four analytical writers).
No new writer-coordination module is introduced (unlike the two protected streams, which
needed a new `stream-registry-authority` module because no existing module owned that
responsibility — here, `context-aggregator` already owns Context aggregation outright).

**4. Projection output framing — not a reclassification of `context-aggregator`, not a
new authoritative-domain-fact source (Chapter 7 §7.4, Locked):** this ADR does **not**
change `context-aggregator`'s Module Taxonomy classification. It remains Type 2
Projection, `owns_authoritative_state: false` (`module-registry.yaml`, unchanged by this
ADR). Chapter 7 §7.4's permissive clause is directly on point: a Projection **may**
"phát sinh operational metadata event về chính nó ... notification read-model đã cập
nhật" (emit operational metadata events about itself — including a "read-model updated"
notification) **provided those outputs are never used as an authoritative source in
place of the original domain event.** `MarketContextSnapshot`/`MarketContextFactInvalidated`
published on `context-aggregator-context` are exactly this category: immutable,
cursor-bounded, lineage-preserving **projection output records** of Context's own
as-of/assembly computation over the Structure/Regime/Feature/Candle facts it reads —
never a replacement authoritative source for those upstream domains, and never claimed to
be one. This is the same record-integrity-vs-authoritative-domain-ownership boundary
`docs/architecture/engine/feature-context-architecture.md` §5.2/§13 already established
for Package 1.3-B ("eligible cursor-bounded MarketContextSnapshot projection record," not
"authoritative MarketContextSnapshot") and `python/context-aggregator/README.md` already
adopts for the existing deterministic core — this ADR grants a stream to carry that
same, already-correctly-framed output; it does not reopen or re-litigate that framing,
and does not resolve (because it does not need to, for this narrow decision) the
separate, already-carried-forward, non-blocking open gap between this framing and
`context.md` §2's own unmodified "authoritative event record" envelope wording
(`m3-context-closure-derivation-001.md` §5 D1).

**5. No scope/instrument/venue/timeframe partitioning — by direct application of
`ADR-036`'s own Alternative 2 rejection, not a new rejection invented here:** `ADR-036`
rejected scope-partitioned streams for the analytical chain because it "would require
creating ... a new stream for every new instrument/venue/timeframe combination, growing
stream count combinatorially," and because it "conflates Stream Registry topology with
`subject_ref` scoping, which Chapter 8 explicitly separates." Both reasons apply
identically here: Context's own five-field `ContextSubjectScope`
(`instrument_id`/`venue_id`/`timeframe`/`context_type`/`context_definition_version`,
`context.md` §1) is exactly the `subject_ref`-level scoping mechanism Chapter 8 §8.2.2
already reserves for payload scoping, not stream topology — the same separation
`structure-engine`/`raw-regime-engine`/`feature-engine` already rely on for their own
per-subject-scoped facts sharing one stream each. `context-aggregator-context` carries
every `market_context` fact regardless of `instrument_id`/`venue_id`/`timeframe`,
unpartitioned, exactly like the four existing analytical streams.

**6. Future `context_type` values — not decided, not pre-empted:** `context.md`'s
`context_type` enum is currently closed at exactly `[market_context]`. If a future
`context_type` is ever authored, whether it shares `context-aggregator-context` or
requires its own stream is a decision for that future, separately-governed transaction —
the same way a hypothetical sixth analytical writer module would require its own future
ADR under `ADR-036`'s own established pattern. This ADR decides only the one `context_type`
that exists today.

**7. Registry-transition mechanics (Chapter 8 §8.3.1/§8.3.5, post-Genesis — this ADR
decides the architecture, not the concrete registry edit):** `stream-registry.yaml` is
currently `registry_version: v1.0` (Genesis). Adding `context-aggregator-context` is a
**post-Genesis** stream creation, so — unlike the Genesis streams `ADR-036` pinned, which
needed no prior activation boundary (§8.3.5's one-time root exception) — the resulting
new registry version must declare `effective_from.event_ref` pointing to a genuine
activation event on the canonical `platform-lifecycle` stream (§8.3.1: *"BẮT BUỘC với mọi
version SAU Genesis"*), authored by `stream-registry-authority` (the sole writer
authority Chapter 8 §8.3.5/`ADR-036` already vest over `platform-lifecycle`, unchanged by
this ADR), per the §8.3.5 validation chain: (a) the activation event must not be the
activating stream's own first event (bootstrap-cycle prohibition); (b) the new
`registry_version` literal follows `ADR-041`'s already-Approved `v<major>.<minor>`
grammar (the next value after `v1.0`, decided at the actual registry-authoring
transaction, not here); (c) every existing stream/writer-authority/sequence-policy/
genesis-position entry in the current Genesis Registry carries forward byte-identical —
this is an additive transition, not a redefinition of anything `ADR-036` already decided.
This ADR does not itself edit `stream-registry.yaml` or author the activation event — per
ADR-036's own precedent (Consequences), the architecture decision is complete here; the
registry-authoring transcription is a separate, later, mechanical step, subject to its
own applicable review.

**8. Boundary vs. Event Contract `allowed_streams` (same boundary `ADR-036` item 6
already drew, reused not redecided):** this ADR pins only the stream's identity and
writer authority — it does not decide, and the future concrete registry entry may not
contain, which event *types* may target `context-aggregator-context`. That eligibility is
declared exclusively by `MarketContextSnapshot`'s and `MarketContextFactInvalidated`'s
own future Event Contracts' `allowed_streams` fields (separate, later, governed work —
explicitly out of this ADR's scope, per the governing task's own instruction not to author
output Event Contract payloads here).

**9. No broker/storage/runtime/deployment choice:** this ADR decides Stream Registry
architecture only (identity, topology, writer authority) — it does not choose, imply, or
constrain message broker technology, storage engine, deployment topology, or any runtime
implementation detail. Those remain Chapter 0 §4b-excluded implementation concerns Chapter
8's own authority split already keeps out of `stream-registry.yaml` entirely.

**Alternatives considered:**

1. **One stream, `context-aggregator-context`, sole writer `context-aggregator` (chosen).**
   The unique result of applying `ADR-036`'s own already-established partitioning rule
   (one stream per writer module per authoritative fact family, original fact + its own
   invalidation/correction counterpart(s) sharing one stream) to Context — not a new rule.
2. **Two streams, one per output event type.** Rejected — `ADR-036` never splits an
   original-fact event type from its own invalidation counterpart across streams for any
   of the four existing analytical writers (Candle, Structure, Regime, Feature all keep
   original + invalidation/correction together); no Context-specific reason (different
   Domain Contract, different consumer set) exists to depart from that precedent here.
3. **Scope-partitioned streams (instrument/venue/timeframe).** Rejected for the identical
   reason `ADR-036` Alternative 2 rejected it for the analytical chain: combinatorial
   stream-count growth, and conflation of Stream Registry topology with `subject_ref`
   scoping (Chapter 8 §8.2.2), which `context.md`'s own `ContextSubjectScope` already
   supplies at the correct layer.
4. **Reuse an existing analytical stream (e.g. `feature-engine-feature`) for Context's
   output.** Rejected — directly violates Chapter 8 §8.3.1's single-writer-per-stream
   invariant (`feature-engine` and `context-aggregator` are two independent writer
   modules; sharing one stream would require an unauthorized cross-module sequence
   coordinator, the same violation `ADR-036` Alternative 3 already rejected for the
   analytical chain).
5. **Defer this ADR until Context's runtime implementation begins.** Rejected as the
   overall approach (the governing WP that requested this ADR explicitly classified the
   decision as the blocking item for category B's output Event Contract authoring) — but
   this ADR does not itself implement anything, so authoring it now imposes no runtime
   cost and unblocks the next bounded WP.

**Consequences:** This ADR **alone does not publish anything and does not unblock Context
output Event Contract authoring by itself** — the required follow-on order, none of which
is performed by this ADR: (1) Review A; (2) Product Owner decision (Risk Classification
expected R2 — same class as `ADR-036`'s own registry-topology decision: the `>1 module`
disjunct is not independently needed here since only `context-aggregator` is newly
granted writer authority, but Chapter 0 §4b's "thay đổi Event Schema"/Event-Model trigger
already applies on its own — Chapter 8 §8.3.1's own text is unconditional that stream
creation/writer-authority change is ADR Required — and the decision is hard to reverse
once Context output events accumulate under this topology); (3) if Approved, a
governed, mechanical `stream-registry.yaml` registry-version transition instantiating
this ADR's already-decided identity/writer authority (new `registry_version`,
`effective_from` activation event on `platform-lifecycle`, authored by
`stream-registry-authority` — no new topology/writer decision at that step, same
`ADR-023`/`ADR-036` mechanical-transcription precedent); (4) a corresponding
`module-registry.yaml` alignment (if any field there needs updating to reflect the new
stream-writer relationship — exact mechanical transcription only, no new decision); (5)
only then may `market-context-snapshot`/`market-context-fact-invalidated` Event Contracts
be authored with `allowed_streams: [context-aggregator-context]`. This ADR does not
modify `stream-registry.yaml`, `module-registry.yaml`, `docs/domain/context.md`, any other
Approved ADR, or any code; does not author or publish any Event Contract; does not
implement `context-aggregator` runtime; does not touch Context Input Contract semantics;
does not assign a Quality Tier; does not perform Review A or request Independent Review
B. `context-aggregator` remains `status: candidate`, Type 2 Projection,
`owns_authoritative_state: false`, unchanged.
