**Context:** [`02-platform-invariants.md`](../constitution/02-platform-invariants.md) I-13 requires that concurrent/competing transition attempts on the same entity resolve deterministically through an authoritative version/concurrency contract, and forbids two conflicting transitions from arising from the same authoritative state/version. [`feature.md`](../domain/feature.md) §9 already owns the Domain-Contract-level rule this requires for Feature facts — a replacement's `supersedes_fact_ref` must name the current lineage head, and a head may be superseded at most once (no fork) — and is not redefined here. What is currently missing, confirmed by a fresh authority-gap analysis against this exact finding (`P3-FEATURE-QG-EVID07-A-MAJ-05`, part of the `P3-FEATURE-QG-EVID-07` property-based-mechanism candidate), is the *runtime mechanism* that keeps that rule true once more than one computation actor could exist for the same `feature_subject_id`. [`08-event-model.md`](../constitution/08-event-model.md) §8.3.1's single-writer-authority guarantee (exactly one writer per stream, atomic sequence assignment, no dual-authoritative window) governs stream-level append ordering; it does not, by itself, validate a payload's own domain cross-reference (`supersedes_fact_ref`) against the true current head. [`stream-registry.yaml`](../architecture/stream-registry.yaml) pins `writer_authority.module_id: feature-engine` for stream `feature-engine-feature` — module-level, not per-subject. [`feature-context-architecture.md`](../architecture/engine/feature-context-architecture.md) explicitly excludes "deployment/runtime topology cụ thể" from its own scope (twice) and names the deferral target as `phase-1-plan.md`'s own (non-binding) ADR-scope anticipation map — no artifact anywhere has actually decided this. The current implementation's `RegimePassthroughFeatureEngine`/`SwingDistanceFeatureEngine` classes assume "One instance per Feature subject" in their own docstrings; that assumption motivated this decision, it is not cited here as prior architecture authority.

**Scope classification — `ADR Optional`.** [Chapter 0 §4b](../constitution/00-governance.md): no Platform Invariant edit (I-13's text is unchanged — this is an enforcement mechanism for an already-Locked invariant, not a redefinition); no Event Schema change; no Module Taxonomy/dependency-graph change (`module-registry.yaml`'s `feature-engine` row is unaffected); no Governance-process change; not a Decision Pipeline topology change under [`09-plugin-model.md`](../constitution/09-plugin-model.md) §9.10 (that trigger is scoped to Strategy-Plugin/Decision-Pipeline wiring — plugin type/capability, published contract, module dependency graph, Decision Pipeline topology, authority/permission model, hard-to-reverse lifecycle semantics — not a single Compute Engine's own internal concurrency model); single-module (`feature-engine` only); reversible (an internal execution-topology choice, the same class ADR-032/ADR-033 both treat as build-time, never architecture-document/ADR-mandated, when it has no cross-module effect). Materially significant, however — this is the actual mechanism that makes I-13 hold for a Tier-1 Core Logic module's production runtime — which places it in Chapter 0 §4b's "ADR Optional: thay đổi nội bộ một module không đổi contract nhưng ảnh hưởng đáng kể" category, not "ADR Not Required." Product Owner elected to author this ADR under that Optional classification (a deliberate choice, not a requirement).

**Decision:** The authoritative Feature stream writer remains the existing `feature-engine` module (`stream-registry.yaml`, unchanged). Within that already-existing writer-authority boundary, every authoritative Feature transition for one `feature_subject_id` must be processed through exactly one active authoritative subject owner at a time. This is an internal Feature-Engine execution/ownership discipline — it creates no second authoritative source, and it is the technical realization of `feature.md` §9's existing no-fork/current-head rule, not a redefinition of it.

**Mandatory semantics:**

1. **Per-subject exclusive ownership.** For any `feature_subject_id`, at most one runtime owner may hold authority to validate and emit authoritative Feature transitions at any instant. Different subjects may be owned by different owners concurrently — horizontal scale is by subject partitioning/affinity, not by a single global process.
2. **Serialization against current authoritative lineage state, deterministically arbitrated.** Every authoritative transition attempt for one subject is serialized through its current owner, which validates the attempt against the authoritative current lineage state/head `feature.md` §9 already requires before emitting. When two or more attempts compete for the same subject, the owner MUST arbitrate between them using an order deterministically derivable from already-authoritative inputs — per-stream sequence precedence and causation precedence (Chapter 8 §8.3.4's own hard constraints, `P_stream ∪ P_causation`), and, for events not ordered by either, the subject's own applicable Input Contract `merge_policy`/`concurrent_tie_break` (§8.3.4, unchanged, un-redefined here — this ADR does not create a new platform-wide total order and does not move Input Contract merge-policy authority into Feature Engine; it only requires Feature Engine to preserve and apply the ordering its own already-authoritative upstream inputs already carry). Runtime arrival order, wall-clock time, thread/process scheduling, replica identity, and lock-acquisition timing MUST NOT determine which of two conflicting attempts wins. Once the attempt that is deterministically first under this order advances the authoritative lineage head, any competing attempt still targeting the prior head deterministically fails current-head validation, unless `feature.md` §9's own semantics explicitly permit otherwise — never a race between the two attempts' own runtime completion times.
3. **Fenced ownership handoff.** Routing affinity alone is insufficient. Any ownership transfer — scaling, repartitioning, restart, crash recovery, failover, deployment replacement — must use an explicit fencing/ownership-generation mechanism, or an equivalent mechanism with the same guarantee, such that the old owner loses authoritative emission authority before the new owner gains it. There is never a dual-authoritative window for one subject. No specific broker, database, actor framework, lease implementation, orchestration primitive, or RPC mechanism is mandated — this ADR owns the semantic requirement, not the implementation technique.
4. **Authoritative-state catch-up before activation.** A prospective new owner must reconstruct/catch up the subject's authoritative state from the authoritative event history/committed Feature lineage before becoming eligible to emit authoritative transitions. Process-local memory alone is never sufficient authority after an ownership transfer.
5. **Fail closed on uncertain ownership, state, or precedence.** If the system cannot prove exclusive current ownership, authoritative state catch-up/current-head correctness, or a deterministic precedence between two competing attempts (semantic 2) for a subject, that subject scope fails closed — no best-effort winner selection, no wall-clock election, no "emit both and let a downstream projection reject one later."
6. **Replay determinism.** Runtime owner identity is execution-control metadata/mechanism, never a Feature domain input. Replay result depends only on authoritative event history and domain semantics, never on which process happened to own a subject live. Because arbitration order (semantic 2) is a pure function of already-replay-stable Chapter 8 ordering — never of live runtime timing — replaying the identical authoritative inputs MUST reproduce the identical accepted transition and the identical stale/conflicting-attempt rejection outcome. This ADR does not add owner IDs, epochs, leases, or fencing tokens to Feature Event Schema — any such addition is a separately governed future decision, not this one.
7. **Non-authoritative execution isolation.** Replay/backtest/shadow/simulation execution not authorized to append to the authoritative Feature stream never participates in authoritative subject ownership. Only a path authorized to emit authoritative Feature transitions is governed as an authoritative subject owner under this ADR.

**Does not alter existing authority.** I-13's text is unchanged. `feature.md` is unchanged — §9's no-fork/current-head rule remains the Domain Contract semantic this ADR realizes, not redefines. Feature Event Contracts (`feature-computed`/`feature-fact-invalidated`) are unchanged — no schema field is added. `module-registry.yaml` is unchanged. `stream-registry.yaml`'s writer authority for `feature-engine-feature` remains `feature-engine`, unchanged. [`08-event-model.md`](../constitution/08-event-model.md) (Locked) is unchanged — this ADR specializes execution *within* the already-existing `feature-engine` writer-authority boundary Chapter 8 grants; it does not claim Chapter 8 already supplied a per-subject guarantee (it does not), and does not claim the implementation's own "One instance per Feature subject" docstrings were prior architecture authority (they were the implementation-level assumption that motivated this governed decision).

**Alternatives considered:**

1. **Sticky routing/affinity without fencing.** Rejected — a failover or repartitioning event can produce two owners that both believe they own the same subject (split-brain); affinity alone does not satisfy I-13's "resolve deterministically" requirement.
2. **A single global Feature Engine owner (no per-subject partitioning).** Semantically sufficient — trivially satisfies exclusivity — but rejected as unnecessarily restrictive: it forecloses horizontal scale across independent subjects for no correctness benefit, since different subjects share no lineage state to protect.
3. **Atomic expected-current-head compare-and-set at authoritative append (chosen as a permitted internal technique, not mandated).** A valid way to satisfy semantics 2 and 5. Not prohibited beneath this ADR's boundary — a Feature-Engine-internal implementation may use CAS or an equivalent mechanism. Not adopted as *this ADR's own* chosen architecture, because a general append-time CAS contract belongs to the event-append mechanism itself (Chapter 8-adjacent, platform-wide) and would broaden this decision past Feature Engine's own single-module scope; ADR-043 fixes the semantic architecture (exclusive fenced per-subject owner + authoritative catch-up + serialization), leaving the specific enforcement technique — CAS or otherwise — to Feature Engine's own future implementation, provided it preserves this decision.
